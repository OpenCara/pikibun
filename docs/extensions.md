# Extensions

A workspace's sessions can run [Pi extensions](https://github.com/earendil-works/pi): packages that add tools (web search, say), guard tool calls (blocking destructive commands), add to the system prompt or summarize long conversations. They load through Pi's own loader, so most Pi extensions work as they are; what Pikibun can't run, such as commands, interface widgets or model providers, does nothing or is ignored, and each host's page says which. See [the design](design/host-extensions.md).

- **The workspace chooses.** Under **Settings → Workspaces →** the workspace **→ Extensions**, owners and admins add an extension pinned to an exact version (`npm:<package>@<version>` or `git:<https URL>@<commit>`), turn it on or off, set its settings (the extension's own options; never secrets) and choose how its tools run: **Approval** or **Automatic**. Every member sees them, and where each host stands with them. When two enabled extensions offer a tool of the same name, sessions keep the first one's, and the page warns.
- **Ready to turn on.** Every workspace starts with three popular extensions, turned off, with their tools on **Approval**: `pi-web-access` (web search from many providers, with no key needed through Exa; page, PDF, GitHub and YouTube reading), `pi-web-search` (web search through the session's own model provider: OpenAI, Anthropic, Gemini, xAI and others) and `cc-safety-net` (blocks destructive commands and reads of secret files). Both web extensions offer `web_search`, so turn on one of them. Their settings, such as search provider keys, are files and environment variables on the host (see each package's README). Turn one on, or remove it, like any other.
- **Hosts install.** A host runs an extension only once it is installed there at that version. Its owner installs it from the host's page (**Settings → Hosts →** the host **→ Extensions**), which lists the extensions its workspaces use that it lacks with **Install** or **Update**, or the workspace's page; or on the machine with `pikibun extensions add` (see the [CLI's README](../packages/cli/README.md)). The connector carries out an install within half a minute while it is online. Only the host's owner installs, and `pikibun connect --no-remote-installs` refuses installs from Pikibun.
- **Sessions** run the extensions their host's owner requires (below), then their workspace's enabled extensions their host has at that version, and nothing else; one the host lacks is skipped, and the session's panel says so. An extension installed on the host from a local path is a dev extension: it runs only in the host owner's own sessions there.
- **Required by the host.** A host's owner can require an extension of every session on their host, whatever each workspace chose, their own sessions included: on the host's page (**Settings → Hosts →** the host **→ Extensions**), tick **Require of every session** on one of Pikibun's own (`piki:<name>`) or one installed there, then set its **Settings**, which replace any workspace's. Required extensions run first, and a workspace's other version of the same package gives way to the host's. While the host can't run one it requires (not installed at that version, a connector without it, or one that doesn't load), its sessions take no messages, and their panels say why. This is where guards belong: the [prompt audit](#prompt-audit-pikiprompt-audit), or a tool-call guard such as `npm:cc-safety-net@2.7.2`. Admins see what the host requires; only its owner changes it. It needs a connector from this release or later; on an older one the page says to update it, and sessions run only what their workspace chose.
- **Messages go through extensions' `input` handlers first.** Before a message (or a side ask) is accepted, each extension the session runs that handles Pi's `input` event sees it, in order: it may let it through, change it, or take it, which refuses the message. The person sees what the extension told them (`ctx.ui.notify`) where it is plain text. As Pi's `source`, the host owner's own messages are `interactive` and everyone else's `rpc`. Unlike in Pi, a handler that fails or takes longer than 25 seconds refuses the message rather than let it through.
- **Outside the sandbox.** Extensions run in the host's connector, as its owner's OS user, with their files, credentials and network; the workspace's network access doesn't confine them. Each extension tool call is an approval card decided like a [host command](host-commands.md), by the host's owner or a member granted host commands. It runs without one only where the workspace sets the extension's tools to **Automatic** and the host's owner turns on **Let workspaces run extension tools without approval** for their host, or under the session owner's **Auto-approve** where `host_bash` would. A **Read only** message never runs them. Install only extensions you trust.
- **Web search and page reading** come from extensions: Pikibun's own `web_fetch` and `web_search` tools are retired.
- **Pi's built-in extensions** (`pi:<name>`) come with Pikibun, with nothing to install. Under **Settings → Hosts →** the host **→ Extensions**, its owner and admins turn one on for every session on that host, in every workspace. **Code mode** (`pi:codemode`) lets the model write JavaScript that calls the session's tools, to batch, chain and filter calls. Scripts run in a QuickJS sandbox in the connector, with 256 MiB each and at most 2 at once per session and 8 per host. A script's own computing is stopped after 2 minutes in all; time its tool calls take, approvals included, doesn't count. Each call a script makes is decided like the model's own: its permissions, approval cards and Read-only rules apply. Scripts get no `models.*`. Output past a script's budget is saved whole in the worktree's `codemode-output/` directory, for `read_file`, except in a Read-only message. A workspace extension that offers a `codemode` tool replaces the built-in. Sessions pick up a change from their next message, within a minute; this needs a connector from this release or later.

## Pikibun's built-in extensions: gh, glab and az

Three workspace extensions come with the connector, so hosts never install them (unlike Pi's built-ins above, the workspace chooses them). Each gives sessions one command-line tool, run on the host as its owner is signed in to it, for what the sandbox can't reach: CI runs and their logs, checks, reviews, releases, and the forge's API. See [the design](design/piki-extensions.md).

| Extension | Tool | For | On the host |
|---|---|---|---|
| `piki:gh` | `gh` | GitHub (github.com and Enterprise Server) | [GitHub CLI](https://cli.github.com), `gh auth login` |
| `piki:glab` | `glab` | GitLab | [GitLab CLI](https://gitlab.com/gitlab-org/cli), `glab auth login` |
| `piki:azure-cli` | `az` | Azure DevOps and Azure | [Azure CLI](https://learn.microsoft.com/cli/azure/install-azure-cli), `az login` and `az extension add --name azure-devops` |

- **Added with the first repository.** When a workspace binds its first repository on GitHub, GitLab or Azure DevOps, it gets that forge's extension, enabled, its tools with **Approval**; workspaces that had such a repository already got it when the server was updated. Owners and admins turn it off or remove it like any other, and add the others under **Add extension → Command-line tools**. One that was turned off stays off; one that was removed comes back only with a later first repository of its forge.
- **Every host has them**, from the connector version that brought them: an older one shows **Update the connector**, and its sessions run without them. A host needs the command itself, installed and signed in by its owner; without it, a call says so.
- **The tool** takes the command's arguments as a list, without a shell (`{"args": ["run", "view", "123", "--log-failed", "--repo", "acme/app"]}`), runs in the session's worktree on the host (or a `directory` in it), and returns its output, cut to its start and end when it is long. It acts as the **host owner's** account on that forge, which may not be the session owner's: Pikibun's own `github_comment`, `github_issue` and `github_merge` act as the session owner.
- **Never their tokens.** Commands that would show the command's credentials (`gh auth token`, `--show-token`, `az account get-access-token`, `--expose-token`, `az --debug`) are refused. The command gets the host's `PATH`, `HOME`, proxies and its own sign-in variables (`GH_TOKEN`, `GITLAB_TOKEN`, `AZURE_*`, …), never the connector's other environment.
- **Read-only.** Each has a **read-only** setting (**Edit**): then only commands that read run (lists, views, logs, `GET` requests and GraphQL queries; for `az`, `list`, `show` and `query`, and none that show keys or secrets), and outside the session's worktree, so nothing a session wrote there (a repository's Git configuration, say) can make the command run code. Turn it on before setting the extension's tools to **Automatic**.

## Prompt audit: piki:prompt-audit

A shared host runs other members' messages with its owner's models, next to the owner's files and credentials. The sandbox keeps sessions away from them, but host commands, [sessions on the host](hosts.md#sessions-on-the-host), unsandboxed hosts and extensions run on the machine itself, so a message that talks an agent (or a person approving it) into reading out `~/.pi/agent/auth.json` could still leak the owner's secrets. `piki:prompt-audit` comes with the connector and has a model check each message before it reaches the agent.

- **Turn it on for your host:** on the host's page, under **Extensions**, tick **Require of every session** on **Prompt audit** (`piki:prompt-audit`), then open its **Settings**. From then on every message to a session on the host is audited, except the host owner's own: members' messages and side questions, scheduled prompts, and messages from other sessions, whoever owns the session. (A workspace can also add it like any extension, for its own sessions.)
- **What it refuses:** messages that try to get the agent to read, print or use the host's or its owner's credentials (Pi's provider keys and logins, SSH keys, tokens, credential files, secrets in the environment), read the owner's files outside the session's worktree and repositories, probe the machine's environment, processes or network, or send host data elsewhere or get around the sandbox, its proxy, approvals or the audit itself. Ordinary work, including work that is *about* secrets in the project, is allowed.
- **Settings:** `model`, the model that audits as `provider/modelId` (the session's model when empty; a small, fast model keeps sending quick and cheap); `policy`, what else counts as sensitive on this host in your own words (such as `Never read ~/work/clients or the database in /srv/data`), which it refuses too; `audit`, `others` (default) or `all` to audit the host owner's own messages as well. Each audit is one request to the model, on the host owner's provider account, and takes at most 20 seconds. A message with images needs a model that reads images.
- **It fails closed.** A message it flags is refused before it is queued, and so is one it can't check: its model is unavailable, fails, takes too long or gives no clear verdict. The sender sees a fixed reason naming the kind of thing flagged, such as *it asks for credentials, keys or tokens*. The auditor's own explanation is model text that a crafted message could steer, so it isn't shown to the sender: the connector writes it to its log on the host (`prompt audit: refused a message (credentials): …`).
- **Its limits:** it judges each message on its own. It doesn't see earlier messages, or what the agent later reads in files, web pages or tool output, so it is one more safeguard, not a replacement for the sandbox and approvals; a tool-call guard such as `npm:cc-safety-net` checks what the agent actually runs. The message goes to the model between markers, as data it is told not to obey, but like any check by a model, a determined attempt may get past it.
- **In Pi itself.** It is an ordinary Pi extension on the `input` event: in Pi it audits messages that don't come from the terminal (`rpc` and `extension` sources), and the settings are its flags.
