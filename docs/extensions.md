# Extensions

A workspace's sessions can run [Pi extensions](https://github.com/earendil-works/pi): packages that add tools (web search, say), guard tool calls (blocking destructive commands), add to the system prompt or summarize long conversations. They load through Pi's own loader, so most Pi extensions work as they are; what Pikibun can't run, such as commands, interface widgets or model providers, does nothing or is ignored, and each host's page says which. See [the design](design/host-extensions.md).

- **The workspace chooses.** Under **Settings → Workspaces →** the workspace **→ Extensions**, owners and admins add an extension pinned to an exact version (`npm:<package>@<version>` or `git:<https URL>@<commit>`), turn it on or off, set its settings (the extension's own options; never secrets) and choose how its tools run: **Approval** or **Automatic**. Every member sees them, and where each host stands with them. When two enabled extensions offer a tool of the same name, sessions keep the first one's, and the page warns; so it does for an extension's tool named like one of Pikibun's own, which sessions keep, even while it is turned off.
- **What each offers, and every tool sessions get.** Each extension on the page shows what it is (its package's description, or Pikibun's for its own) and the tools it offers, by name, with what each does when you open it; a tool sessions leave out for a clash is struck through. Above them, **Tools sessions can use** lists every tool the workspace's sessions get: Pikibun's own that are on, the built-in `codemode`, and the tools of its enabled extensions, each with what it does, the extension it comes with, and whether its calls wait for **Approval** or run **Automatic**. An extension's description and tools come from a host that has it installed at that version, so they show once one has reported it; the add and edit sheet shows them too. Each host offers what it can of the list: not the browser without Chromium there, nor an extension it hasn't installed, and its owner may add extensions they require.
- **Ready to turn on.** Every workspace starts with three popular extensions, turned off, with their tools on **Approval**: `pi-web-access` (web search from many providers, with no key needed through Exa; page, PDF, GitHub and YouTube reading), `pi-web-search` (web search through the session's own model provider: OpenAI, Anthropic, Gemini, xAI and others) and `cc-safety-net` (blocks destructive commands and reads of secret files). Both web extensions offer `web_search`, so turn on one of them. Their settings, such as search provider keys, are files and environment variables on the host (see each package's README). Turn one on, or remove it, like any other.
- **Hosts install.** A host runs an extension only once it is installed there at that version. Its owner installs it from the host's page (**Settings → Hosts →** the host **→ Extensions**), which lists the extensions its workspaces use that it lacks with **Install** or **Update**, or the workspace's page; or on the machine with `pikibun extensions add` (see the [CLI's README](../packages/cli/README.md)). The connector carries out an install within half a minute while it is online. Only the host's owner installs, and `pikibun connect --no-remote-installs` refuses installs from Pikibun.
- **Sessions** run the extensions their host's owner requires (below), then their workspace's enabled extensions their host has at that version, and nothing else; one the host lacks is skipped, and the session's panel says so. An extension installed on the host from a local path is a dev extension: it runs only in the host owner's own sessions there.
- **Required by the host.** A host's owner can require an extension of every session on their host, whatever each workspace chose, their own sessions included: on the host's page (**Settings → Hosts →** the host **→ Extensions**), tick **Require of every session** on one of Pikibun's own (`piki:<name>`) or one installed there, then set its **Settings**, which replace any workspace's. Required extensions run first, and a workspace's other version of the same package gives way to the host's. While the host can't run one it requires (not installed at that version, a connector without it, or one that doesn't load, whole or in part), or its connector hasn't yet heard from Pikibun what is required, its sessions take no messages, and their panels say why. A connector that can't reach Pikibun keeps requiring what it last heard. This is where guards belong: the [prompt audit](#prompt-audit-pikiprompt-audit), or a tool-call guard such as `npm:cc-safety-net@2.7.2`. Admins see what the host requires; only its owner changes it. It needs a connector from this release or later; on an older one the page says to update it, and sessions run only what their workspace chose.
- **Messages go through extensions' `input` handlers first.** Once a message (or a side ask) is queued, and before it reaches the agent, each extension the session runs that handles Pi's `input` event sees it, in order: it may let it through, change it, or take it, which refuses the message. Sending isn't held up meanwhile; the message, and the ones queued behind it, wait until the handlers are done. A refused message never runs: the transcript says so where it was sent, with what the extension told the sender (`ctx.ui.notify`), and the queue marks it `refused`. As Pi's `source`, the host owner's own messages are `interactive` and everyone else's `rpc`. Unlike in Pi, a handler that fails or takes longer than a minute refuses the message rather than let it through.
- **Outside the sandbox.** Extensions run in the host's connector, as its owner's OS user, with their files, credentials and network; the workspace's network access doesn't confine them. Each extension tool call is an approval card decided like a [host command](host-commands.md), by the host's owner or a member granted host commands. It runs without one only where the workspace sets the extension's tools to **Automatic** and the host's owner turns on **Let workspaces run extension tools without approval** for their host, or under the session owner's **Auto-approve** on the owner's own host, or one whose owner granted them automatic host commands. A **Read only** message never runs them. Install only extensions you trust.
- **Web search and page reading** come from extensions: Pikibun's own `web_fetch` and `web_search` tools are retired.
- **Pi's built-in extensions** (`pi:<name>`) come with Pikibun, with nothing to install. Under **Settings → Hosts →** the host **→ Extensions**, its owner and admins turn one on for every session on that host, in every workspace. **Code mode** (`pi:codemode`) is always on: it's how sessions chain and filter tool calls, as shell pipelines did, so it runs in every session whatever the host's configuration lists. Its checkbox (**Older connectors too**) still decides it on hosts whose connector predates this release, which go by the host's list. It lets the model write JavaScript that calls the session's tools, to batch, chain and filter calls. Scripts run in a QuickJS sandbox in the connector, with 256 MiB each and at most 2 at once per session and 8 per host. A script's own computing is stopped after 2 minutes in all; time its tool calls take, approvals included, doesn't count. Each call a script makes is decided like the model's own: its permissions, approval cards and Read-only rules apply. Scripts get no `models.*`. Output past a script's budget is saved whole in the worktree's `codemode-output/` directory, for `read_file`, except in a Read-only message. A workspace extension that offers a `codemode` tool replaces the built-in. Sessions pick up a change from their next message, within a minute; this needs a connector from this release or later.

## Pikibun's built-in extensions: gh, glab and az

Three workspace extensions come with the connector, so hosts never install them (unlike Pi's built-ins above, the workspace chooses them). Each gives sessions one command-line tool for CI runs and their logs, checks, reviews, releases, and the forge's API. It runs **in the session's sandbox, as the session's owner**: the sandbox holds no token, and the session's proxy adds the owner's access in Pikibun to the forge's API requests (see [Network access](hosts.md#network-access)). See [the design](design/piki-extensions.md).

| Extension | Tool | For | Acts with the session owner's | On the host |
|---|---|---|---|---|
| `piki:gh` | `gh` | GitHub (github.com) | GitHub sign-in | [GitHub CLI](https://cli.github.com) |
| `piki:glab` | `glab` | GitLab (gitlab.com) | GitLab access token under **Git accounts** | [GitLab CLI](https://gitlab.com/gitlab-org/cli) |
| `piki:azure-cli` | `az` | Azure DevOps | Azure DevOps access token for the organization, under **Git accounts** | [Azure CLI](https://learn.microsoft.com/cli/azure/install-azure-cli) and `az extension add --name azure-devops` |

- **Added with the first repository.** When a workspace binds its first repository on GitHub, GitLab or Azure DevOps, it gets that forge's extension, enabled, its tools with **Approval**; workspaces that had such a repository already got it when the server was updated. Owners and admins turn it off or remove it like any other, and add the others under **Add extension → Command-line tools**. One that was turned off stays off; one that was removed comes back only with a later first repository of its forge.
- **Every host has them**, from the connector version that brought them: an older one shows **Update the connector**, and its sessions run without them. A host needs the command itself, installed where its sandboxes find it (in `/usr`, such as `/usr/bin` or `/usr/local/bin`); without it, a call says so. Nobody signs in to it on the host.
- **The tool** takes the command's arguments as a list, without a shell (`{"args": ["run", "view", "123", "--log-failed", "--repo", "acme/app"]}`), runs in the session's worktree (or a `directory` in it), and returns its output, cut to its start and end when it is long. Each call is still an approval card decided like a host command.
- **Reads, always; writes, only when a person approved the call, on the session owner's own host.** It reads the workspace's repositories: on GitHub with a read-only token of the workspace's GitHub App that covers the repositories the session owner can read, on any host; on GitLab and Azure DevOps with the owner's own access token, which can't be limited to the workspace's repositories, so only on the session owner's own hosts. A call whose card a person approved, or that ran under the session owner's **Auto-approve**, may also write as the session owner (comment, open or merge a pull request, rerun a pipeline) with their GitHub sign-in or access token, which Pikibun gives only to the session owner's own hosts. On a host someone else shared, its writes are refused: use `github_comment`, `github_issue`, `github_merge` and `git_push` there. A call that ran because the workspace runs the tools **Automatic** never writes.
- **The host's own sign-in** is used only where the session runs on its host itself ([unsandboxed hosts](hosts.md#running-without-the-sandbox) and sessions on the host's environment), as every command there runs as the host's OS user, or in the host owner's **own** sessions where they started the connector with `PIKIBUN_PIKI_HOST_SIGN_IN=1`: for Azure resources (`az vm`, …), which need an Azure sign-in, or the experimental macOS and Windows sandboxes, where `gh` and `glab` can't verify the proxy yet. Then the command runs on the host as its owner is signed in to it (`gh auth login`, `glab auth login`, `az login`). Another member's session never gets it.
- **Never their tokens.** Commands that would show the command's credentials (`gh auth token`, `--show-token`, `az account get-access-token`, `--expose-token`, `az --debug`) are refused. In the sandbox the token variables (`GH_TOKEN`, `GITLAB_TOKEN`, `AZURE_DEVOPS_EXT_PAT`) hold only a placeholder. On the host the command gets the host's `PATH`, `HOME`, proxies and its own sign-in variables, never the connector's other environment.
- **Read-only.** Each has a **read-only** setting (**Edit**): then only commands that read run (lists, views, logs, `GET` requests and GraphQL queries; for `az`, `list`, `show` and `query`, and none that show keys or secrets), never with the owner's credential to write, and with the worktree read-only (on the host, outside the worktree, so nothing a session wrote there, a repository's Git configuration say, can make the command run code there). Turn it on before setting the extension's tools to **Automatic**.

## Session tools

Pikibun's own tools are becoming extensions, one by one ([#163](https://github.com/OpenCara/pikibun/issues/163)), so a workspace chooses them like any other. Each such **session-tool extension** turns one or more of the session's own tools on or off; the tools themselves don't change.

| Extension | Tools |
|---|---|
| `piki:schedule` | `schedule` |
| `piki:git` | `git`, `git_push` |
| `piki:node` | `node` |
| `piki:python` | `python` |
| `piki:rust` | `rust` |
| `piki:go` | `go` |
| `piki:dotnet` | `dotnet` |
| `piki:make` | `make` |
| `piki:browser` | `browser` |
| `piki:tunnel` | `tunnel`: off until turned on |
| `piki:github` | `github_read`, `github_comment`, `github_issue`, `github_merge` |
| `piki:notion` | `source_read`, for Notion sources |
| `piki:google-drive` | `source_read`, for Google Drive sources |
| `piki:dropbox` | `source_read`, for Dropbox sources |
| `piki:onedrive` | `source_read`, for OneDrive / SharePoint sources |
| `piki:feishu` | `source_read`, for Feishu / Lark sources |
| `piki:tencent-docs` | `source_read`, for Tencent Docs sources |
| `piki:sessions` | `sessions` |
| `piki:files` | `identity`, `list_files`, `read_file`, `search`, `write_file`, `edit_file`, `move_file`, `copy_file`, `delete_file`: always on |

- **On unless turned off.** The workspace page lists them under **Extensions** whether or not the workspace ever chose them; owners and admins switch each **On** or off there. Sessions stop offering a tool that is off from their next message, and a call to it by name (from a code mode script, say) is refused. `piki:tunnel` is the other way round: off until the workspace turns it on, since putting a server online is a choice a workspace makes; where a session can't learn its workspace's choice, it stays off.
- **The session's own.** Their tools run as before: with the session's permissions, approval cards and Read-only rules, decided by the session's people, never as extension tool cards decided like host commands. So they have no **Approval**/**Automatic** choice and no settings, and a host's owner can't require them.
- **Nothing to install.** Every connector of this release has them. One that predates a session-tool extension offers its tools whatever the workspace chose. Where a session can't learn its workspace's choice for the moment, its tools stay on.
- **No shell.** `bash` and `host_bash`, and with them `piki:shell` and `piki:host-shell`, are gone (#163): sessions clone and commit with `git`, build and test with `node` and `python`, move, copy and delete with the file tools, and chain tools with code mode. A workspace's old choice for those two still reaches connectors from before their removal, which offer them unless turned off; workspace pages no longer list them.
- **`git` runs Git.** The `git` tool takes Git's arguments as a list and runs exactly `git <arguments>` in a clone, with no shell, pager, editor or password prompt, so its card shows one Git command rather than a script. It runs only version-control subcommands, and refuses the options that make Git run another program. Its calls are approved as commands are (the owner's **Auto-approve** and auto-approved members included), even for subcommands that only read: a repository's own Git configuration, which the agent can write, can make `git status` run a program.
- **`node` runs Node.js.** The `node` tool runs one program of Node.js's (`node`, `npm`, `npx`, `pnpm`, `yarn`, `corepack`) with its arguments as a list, in a clone, without a shell, colours or prompts. Commands that act on a package registry as an account (`publish`, `login`, `token`, `owner`, `dist-tag`, ...) are refused: sessions have no registry account. It runs the connector's own Node.js (24 or newer, which the connector needs anyway), with its `npm` and `npx` (and `corepack` where it bundles it: Node.js 25 and newer don't), ahead of any other: only its `node`, those package managers (and `pnpm` and `yarn` where installed globally) and its C headers are given to the sandbox, read-only, never the directory they are in: in the Linux sandbox below `/opt/pikibun/node` where the sandbox doesn't already see them (nvm, Volta, a tarball), and the macOS sandbox may read and run them. Elsewhere (the desktop app, which runs on Electron, Windows, and unsandboxed hosts) it runs the Node.js on the commands' PATH. A version a project asks for (`.nvmrc`, `engines`) isn't provisioned yet (#163). Its calls are approved as `bash` commands are, since `pnpm test` or `node script.js` run whatever the project or script says.
- **`python` runs Python.** The `python` tool runs one of `python3`, `pip`, `pip3`, `uv`, `uvx`, `poetry` and `pytest` with its arguments as a list, without a shell, colours or prompts. With `venv` (`.venv`, made with `python3 -m venv .venv`) the environment's own programs run first, so packages install there rather than into the host's Python. Publishing and storing package index credentials (`uv publish`, `uv auth`, `poetry publish`, `twine upload` however launched, `poetry config` of tokens) are refused. Its calls are approved as commands are. It isn't offered in the Windows sandbox yet, whose container reaches no Python; Linux hosts lacking `python3-venv` are told so where they show their prerequisites.
- **`rust`, `go` and `dotnet` run their ecosystems.** Each runs one of its programs (`cargo`, `rustc`, `rustup`, `rustfmt`; `go`, `gofmt`; `dotnet`) with its arguments as a list, in a clone, without a shell, colours, progress bars or telemetry, the toolchain's usual directories (`/usr/local/cargo/bin`, `/usr/local/go/bin`, `/usr/share/dotnet`, ...) looked in after the sandbox's PATH. Commands that act on a package registry as an account are refused: `cargo publish`, `login`, `logout`, `owner` and `yank` (also as `cargo +toolchain` or through `rustup run`), `dotnet nuget push` and `delete`, and adding or updating a NuGet source with a password. Go publishes by tagging a repository, so `go` refuses nothing. Their calls are approved as commands are. The toolchain must be installed where the sandbox sees it, not in a home directory: Rust from the distribution's packages (`/usr/bin`), or a system-wide rustup as the official `rust` image has it (proxies in `/usr/local/cargo/bin`, toolchains in `/usr/local/rustup`, which `rust` calls then use as `RUSTUP_HOME` unless the session's environment names another; read-only, so a toolchain file naming one that isn't installed fails), Go in `/usr/local/go` or `/usr/lib/go`, .NET in `/usr/share/dotnet`, `/usr/lib/dotnet` or `/usr/local/share/dotnet`. On macOS, Homebrew's toolchains, or Go's and .NET's installers' (`/usr/local/go`, `/usr/local/share/dotnet`) and a system-wide rustup in `/usr/local`, which the macOS sandbox may read and run; a rustup in a home directory isn't seen there either. The session keeps its own cargo home. None is offered in the Windows sandbox yet.
- **`make` runs make.** The `make` tool runs `make` with its arguments as a list, in a clone, as the others run their programs. It refuses nothing: a Makefile's recipes are shell commands the project wrote (or the agent did), which the card's `make` stands for, as `npm test` does for a package's scripts, so approve it as you would the recipes. It is the system's make, or GNU make from Homebrew in `/usr/local/bin`; not in the Windows sandbox.
- **Programs the host lacks.** In the Linux sandbox, which sees only the host's `/usr` and the connector's Node.js, which of these tools' programs a session can run is known before it runs any: a program the host hasn't installed for the whole system (`pnpm` or `yarn` not installed globally, `corepack` on Node.js 25 or newer, `uv`, `poetry`, a rustup in `~/.cargo`, ...) is named, with the step that installs it on the host, in the agent's instructions and under **Extensions** in the session panel (**Missing programs**), as the browser without Chromium is. A call to one is refused before anyone is asked to approve it, saying the same, so the agent tells its people what the host's owner installs rather than finding out from `command not found`; a `python` call with `venv` is never refused, as the environment may have the program. Sessions find a program installed in `/usr` from their next message; one installed into a Node.js outside `/usr` (nvm, Volta), from their next session. Elsewhere (macOS, Windows, unsandboxed hosts) commands see the host's own PATH, and nothing is checked beforehand.
- **`browser` to see a web page.** The `browser` tool drives a headless Chromium in the session's sandbox; see [The browser](#the-browser-pikibrowser).
- **`tunnel` to put a web app online.** The `tunnel` tool runs the session's web server in its sandbox and puts it online at a public address; see [The tunnel](#the-tunnel-pikitunnel).
- **The brokered tools and the file tools.** `piki:github`, the document-source extensions and `piki:sessions` switch the tools that act as the session owner through Pikibun, and `piki:git` switches `git_push` with `git`. `piki:files` holds the tools every session needs to read and write its files: it is always on, and turning it off is refused.
- **One per kind of document source.** `piki:notion`, `piki:google-drive`, `piki:dropbox`, `piki:onedrive`, `piki:feishu` and `piki:tencent-docs` each switch `source_read` for their kind: sessions offer `source_read` while any of them is on, and list and read only the sources of the kinds that are on. They replace `piki:sources`, which switched every kind at once: a workspace that turned it off has each kind off until it turns that kind on. Hosts on connectors from before the split have only `piki:sources`, which is on there while any kind is on.
- **No place taken.** They don't count towards a workspace's 32 extensions.
- **Defined by Pikibun, not by the connector.** `node`, `rust`, `go`, `dotnet`, `make` and `source_read` are described by the server as data, and connectors run them with their own engine, so tools of these kinds that Pikibun adds reach hosts as soon as the server has them, without a connector update. Their switches work the same way. See [the design](design/tool-definitions.md).

## The browser: piki:browser

The `browser` tool lets the agent look at and test web pages: the app it is building, a page it was pointed to, a flow that should work. It drives a headless Chromium **in the session's Linux sandbox**, as one sandboxed command per call, so its approval card shows exactly what runs and its network is the session's. See [the design](design/piki-extensions.md#a-browser-pikibrowser).

- **One call, one visit.** A call opens `url` (http, https, a `file:` page such as a build in the worktree, or `about:blank`; without one, the page the last call left), then runs `actions` in order: `goto`, `click` and `hover` (a CSS selector, `text=<visible text>`, or coordinates), `type` (with `submit` to press Enter), `press` a key, `select` an option, `scroll`, `wait` for a selector, text or a time, `evaluate` JavaScript in the page and return its value, `screenshot` (also `full_page`), `back`, `forward` and `reload`. A failed action stops the rest. The answer is the page as the call left it: a screenshot the model sees, its URL, title and HTTP status, its visible text, the elements it can act on with a selector for each, console messages, uncaught errors and failed requests.
- **The app under test, served for the call.** A sandboxed command's processes and `localhost` end with it, so a call that tests a web app starts its server too: `serve: {program: "pnpm", args: ["dev", "--port", "5173"], directory: "app", port: 5173}` runs from before the page opens (once the port answers) until the call ends, and its output comes back with the page. It is one of the `node` and `python` tools' programs, checked as those tools check them (so no `npm publish`) and started without a shell, with their environment: the connector's own Node.js first, or a Python virtual environment named by `venv`.
- **A profile that persists, pages that don't.** Each call starts Chromium afresh with the session's own profile in its home, so cookies and storage (a sign-in) last from one call to the next, while open pages, their scripts' state and form input don't: do a whole flow in one call. The HTTP cache is off, so each call sees what the server serves now.
- **Approved as commands are.** Pages run their own scripts, `evaluate` runs the agent's, and `serve` starts the app, so each call is a program operation of its own, decided as the `git`, `node` and `python` tools' calls are (the owner's **Auto-approve** and allowing `browser` for the session included), and a **Read only** message asks first. It stops at the host's [command time limit](hosts.md#host-configuration), and reports, with a screenshot, a few seconds before it.
- **Its network is the session's.** Other hosts go through the session's proxy, so the workspace's [network access](hosts.md#network-access) applies: a refused host, or plain `http://` outside the sandbox, says so in the answer. Chromium checks certificates against its own roots.
- **The Browser tab.** Each call leaves its screenshots and a report in the worktree's `browser-output/` directory (the last 30 calls), which the session panel's [Browser tab](sessions.md) shows and `read_file` reads.
- **Only in the session's sandbox.** Chromium runs in the session's Linux sandbox, never on the host itself, where the protocol that drives it would reach the host's files and network as its user. So sessions that run on the host ([unsandboxed hosts](hosts.md#running-without-the-sandbox) and [sessions on the host](hosts.md#sessions-on-the-host)) and, for now, the experimental macOS and Windows sandboxes aren't offered the tool. In the sandbox, Chromium can't keep its own sandbox around the pages it runs: a page that exploits it gets what the session has (its files, its branch, the workspace's network), never the host.
- **Needs Chromium on the host.** The host's owner has the connector find one installed there, gives its path, or has the connector download one, on the host's page; see [A browser for sessions](hosts.md#a-browser-for-sessions). Sessions on a host without one, or on an older connector, aren't offered the tool, and say why: a warning above the chat box as the session starts, a row in its panel's **Extensions** section, and a sentence to its agent. Like the other session tools it is on unless a workspace turns `piki:browser` off.

## The tunnel: piki:tunnel

The `tunnel` tool puts the web server a session builds online at a public `https://` address, so people can open it in a browser or on a phone: a web app, a preview of a branch. The server runs **in the session's Linux sandbox**, as a session service that keeps running after the call that started it; Cloudflare's `cloudflared` runs **in the host's connector**, never in the sandbox, and gets an address of Cloudflare's for it (a quick tunnel, `https://<name>.trycloudflare.com`). See [the design](design/tunnel.md).

- **Off until turned on.** Owners and admins turn **Tunnel** (`piki:tunnel`) on under **Settings → Workspaces →** the workspace **→ Extensions**. A host's owner can refuse it on their host whatever its workspaces chose (**Off**, below).
- **`start`, `status`, `stop`.** `tunnel {action: "start", serve: {program: "pnpm", args: ["preview", "--port", "4173"], directory: "app", port: 4173}}` starts the server: one of the `node` and `python` tools' programs, checked as those tools check them and started without a shell, exactly as the browser's `serve`. Once its port answers on the sandbox's `localhost` (within `timeout_seconds`, 60 by default), the connector opens the tunnel, and the call answers with the address. A new `start` replaces the one online. `status` gives the address, whether `cloudflared` is connected, the uptime and the server's last 40 lines of output; `stop` takes it offline. The server should accept any `Host` header (Vite: `--host` and `server.allowedHosts`).
- **Each start is a decision.** It publishes from the host's network, so each `start` is an approval card decided like a [host command](host-commands.md), by the host's owner or a member granted host commands: never automatically, not under the session owner's **Auto-approve**, nor where the workspace runs extension tools **Automatic**. A **Read only** message refuses it. `status` and `stop` ask nobody.
- **Online until something stops it**: the tool's `stop` or the session panel's **Stop** button (anyone who may write to the session), a new `start`, someone stopping the session's work, the session closing (a restart, a backup, its host stopping) or being archived, the server exiting, `cloudflared` failing, or the host's [service lifetime](hosts.md#host-configuration) (4 hours by default) at most. One per session.
- **Visible.** While it is online the session panel shows the address, who started it and until when, with a **Stop** button; the session list marks the session **Online**; the audit log records `session.tunnel.started` and `session.tunnel.stopped`, with the address, who started or stopped it, and why it stopped.
- **Only the declared port, publicly.** Requests to the address reach the server's port in the sandbox and nothing else, of the sandbox or the host. Anyone with the address can open it: Cloudflare's quick tunnels have no access gate, no uptime guarantee, and a new address at each start.
- **The sandbox stays as it is.** The server has the session's files, network and limits, as its commands do; its network still reaches only the session's [proxy](hosts.md#network-access). No tunnel credential enters the sandbox.
- **Needs cloudflared on the host, and the Linux sandbox.** The host's owner has the connector find one installed, gives its path, or has it download one, on the host's page; see [Tunnels for sessions](hosts.md#tunnels-for-sessions). Sessions on a host without one, on the host itself, in the experimental macOS and Windows sandboxes, or on an older connector aren't offered the tool, and their panel's **Extensions** section and agent say why.

## Prompt audit: piki:prompt-audit

A shared host runs other members' messages with its owner's models, next to the owner's files and credentials. The sandbox keeps sessions away from them, but host commands, [sessions on the host](hosts.md#sessions-on-the-host), unsandboxed hosts and extensions run on the machine itself, so a message that talks an agent (or a person approving it) into reading out `~/.pi/agent/auth.json` could still leak the owner's secrets. `piki:prompt-audit` comes with the connector and has a model check each message before it reaches the agent.

- **Turn it on for your host:** on the host's page, under **Extensions**, tick **Require of every session** on **Prompt audit** (`piki:prompt-audit`), then open its **Settings**. From then on every message to a session on the host is audited, except the host owner's own: members' messages and side questions, scheduled prompts, and messages from other sessions, whoever owns the session. (A workspace can also add it like any extension, for its own sessions.)
- **What it refuses:** messages that try to get the agent to read, print or use the host's or its owner's credentials (Pi's provider keys and logins, SSH keys, tokens, credential files, secrets in the environment), read the owner's files outside the session's worktree and repositories, probe the machine's environment, processes or network, or send host data elsewhere or get around the sandbox, its proxy, approvals or the audit itself. Ordinary work, including work that is *about* secrets in the project, is allowed.
- **Settings:** `model`, the model that audits as `provider/modelId` (the session's model when empty; a small, fast model keeps sending quick and cheap); `policy`, what else counts as sensitive on this host in your own words (such as `Never read ~/work/clients or the database in /srv/data`), which it refuses too; `audit`, `others` (default) or `all` to audit the host owner's own messages as well. Each audit is one request to the model, on the host owner's provider account, and takes at most 45 seconds. A message with images needs a model that reads images.
- **It fails closed.** A message it flags is refused before it reaches the agent, and so is one it can't check: its model is unavailable, fails, takes too long or gives no clear verdict. The transcript shows a fixed reason naming the kind of thing flagged, such as *it asks for credentials, keys or tokens*, where the message was sent. The auditor's own explanation is model text that a crafted message could steer, so it isn't shown to the sender: the connector writes it to its log on the host (`prompt audit: refused a message (credentials): …`).
- **Its limits:** it judges each message on its own. It doesn't see earlier messages, or what the agent later reads in files, web pages or tool output, so it is one more safeguard, not a replacement for the sandbox and approvals; a tool-call guard such as `npm:cc-safety-net` checks what the agent actually runs. The message goes to the model between markers, as data it is told not to obey, but like any check by a model, a determined attempt may get past it.
- **In Pi itself.** It is an ordinary Pi extension on the `input` event: in Pi it audits messages that don't come from the terminal (`rpc` and `extension` sources), and the settings are its flags.
