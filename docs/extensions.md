# Extensions

A workspace's sessions can run [Pi extensions](https://github.com/earendil-works/pi): packages that add tools (web search, say), guard tool calls (blocking destructive commands), add to the system prompt or summarize long conversations. They load through Pi's own loader, so most Pi extensions work as they are; what Pikibun can't run, such as commands, interface widgets or model providers, does nothing or is ignored, and each host's page says which. See [the design](design/host-extensions.md).

- **The workspace chooses.** Under **Settings → Workspaces →** the workspace **→ Extensions**, owners and admins add an extension pinned to an exact version (`npm:<package>@<version>` or `git:<https URL>@<commit>`), turn it on or off, set its settings (the extension's own options; never secrets). Every member sees them, and where each host stands with them. When two enabled extensions offer a tool of the same name, sessions keep the first one's, and the page warns; so it does for an extension's tool named like one of Pikibun's own, which sessions keep, even while it is turned off.
- **What each offers, and every tool sessions get.** Each extension on the page shows what it is (its package's description, or Pikibun's for its own) and the tools it offers, by name, with what each does when you open it; a tool sessions leave out for a clash is struck through. Above them, **Tools sessions can use** lists every tool the workspace's sessions get: Pikibun's own that are on, the built-in `codemode`, and the tools of its enabled extensions, each with what it does, the extension it comes with. An extension's description and tools come from a host that has it installed at that version, so they show once one has reported it; the add and edit sheet shows them too. Each host offers what it can of the list: not the browser without Chromium there, nor an extension it hasn't installed, and its owner may add extensions they require.
- **Ready to turn on.** Every workspace starts with three popular extensions, turned off: `pi-web-access` (web search from many providers, with no key needed through Exa; page, PDF, GitHub and YouTube reading), `pi-web-search` (web search through the session's own model provider: OpenAI, Anthropic, Gemini, xAI and others) and `cc-safety-net` (blocks destructive commands and reads of secret files). Both web extensions offer `web_search`, so turn on one of them. Their settings, such as search provider keys, are files and environment variables on the host (see each package's README). It also starts with two of Pikibun's own, turned off, which come with the connector, so hosts install nothing: the [prompt audit](#prompt-audit-pikiprompt-audit) (`piki:prompt-audit`) and [context files](#context-files-pikicontext-files) (`piki:context-files`). Turn one on, or remove it, like any other.
- **Hosts install.** A host runs an extension only once it is installed there at that version. Its owner installs it from the host's page (**Settings → Hosts →** the host **→ Extensions**), which lists the extensions its workspaces use that it lacks with **Install** or **Update**, or the workspace's page; or on the machine with `pikibun extensions add` (see the [CLI's README](../packages/cli/README.md)). The connector carries out an install within half a minute while it is online. Only the host's owner installs, and `pikibun connect --no-remote-installs` refuses installs from Pikibun.
- **Sessions** run the extensions their host's owner requires (below), then their workspace's enabled extensions their host has at that version, and nothing else; one the host lacks is skipped, and the session's panel says so. An extension installed on the host from a local path is a dev extension: it runs only in the host owner's own sessions there.
- **Required by the host.** A host's owner can require an extension of every session on their host, whatever each workspace chose, their own sessions included: on the host's page (**Settings → Hosts →** the host **→ Extensions**), tick **Require of every session** on one of Pikibun's own (`piki:<name>`) or one installed there, then set its **Settings**, which replace any workspace's. Required extensions run first, and a workspace's other version of the same package gives way to the host's. While the host can't run one it requires (not installed at that version, a connector without it, or one that doesn't load, whole or in part), or its connector hasn't yet heard from Pikibun what is required, its sessions take no messages, and their panels say why. A connector that can't reach Pikibun keeps requiring what it last heard. This is where guards belong: the [prompt audit](#prompt-audit-pikiprompt-audit), or a tool-call guard such as `npm:cc-safety-net@2.7.2`. Admins see what the host requires; only its owner changes it. It needs a connector from this release or later; on an older one the page says to update it, and sessions run only what their workspace chose.
- **Messages go through extensions' `input` handlers first.** Once a message (or a side ask) is queued, and before it reaches the agent, each extension the session runs that handles Pi's `input` event sees it, in order: it may let it through, change it, or take it, which refuses the message. Sending isn't held up meanwhile; the message, and the ones queued behind it, wait until the handlers are done. A refused message never runs: the transcript says so where it was sent, with what the extension told the sender (`ctx.ui.notify`), and the queue marks it `refused`. As Pi's `source`, the host owner's own messages are `interactive` and everyone else's `rpc`. Unlike in Pi, a handler that fails or takes longer than a minute refuses the message rather than let it through.
- **Outside the sandbox.** Extensions run in the host's connector, as its owner's OS user, with their files, credentials and network; the workspace's network access doesn't confine them. So their tools run like [host commands](host-commands.md): in sessions of the host's owner and of members they granted host commands, for messages of theirs, and for everyone else only where the host's owner turns on **Let every session run extension tools** for their host. Elsewhere a call is refused; nobody is asked. A **Read only** message never runs them. Install only extensions you trust.
- **No model calls with the host's keys.** An installed extension sees the session's model and the host's list of models, without their headers, but can't call a model or read a key through Pi's model registry (`ctx.modelRegistry`): such a call fails with a reason that says so. Pikibun's own extensions built into the connector, such as the [prompt audit](#prompt-audit-pikiprompt-audit), still call models. This needs a connector from the next release; older ones hand installed extensions the host's registry as before.
- **Web search and page reading** come from extensions: Pikibun's own `web_fetch` and `web_search` tools are retired.
- **Pi's built-in extensions** (`pi:<name>`) come with Pikibun, with nothing to install. Under **Settings → Hosts →** the host **→ Extensions**, its owner and admins turn one on for every session on that host, in every workspace. **Code mode** (`pi:codemode`) is always on: it's how sessions chain and filter tool calls, as shell pipelines did, so it runs in every session whatever the host's configuration lists. Its checkbox (**Older connectors too**) still decides it on hosts whose connector predates this release, which go by the host's list. It lets the model write JavaScript that calls the session's tools, to batch, chain and filter calls. Scripts run in a QuickJS sandbox in the connector, with 256 MiB each and at most 2 at once per session and 8 per host. A script's own computing is stopped after 2 minutes in all; time its tool calls take doesn't count. Each call a script makes runs as the model's own would: the session's tool group and Read-only rules apply. Scripts get no `models.*`. Output past a script's budget is saved whole in the worktree's `codemode-output/` directory, for `read_file`, except in a Read-only message. A workspace extension that offers a `codemode` tool replaces the built-in. Sessions pick up a change from their next message, within a minute; this needs a connector from this release or later.

## Pikibun's built-in extensions: gh, glab and az

Three workspace extensions come with the connector, so hosts never install them (unlike Pi's built-ins above, the workspace chooses them). Each gives sessions one command-line tool for CI runs and their logs, checks, reviews, releases, and the forge's API. It runs **in the session's sandbox, as the session's owner**: the sandbox holds no token, and the session's proxy adds the owner's access in Pikibun to the forge's API requests (see [Network access](hosts.md#network-access)). See [the design](design/piki-extensions.md).

| Extension | Tool | For | Acts with the session owner's | On the host |
|---|---|---|---|---|
| `piki:gh` | `gh` | GitHub (github.com) | GitHub sign-in | [GitHub CLI](https://cli.github.com) |
| `piki:glab` | `glab` | GitLab (gitlab.com) | GitLab access token under **Git accounts** | [GitLab CLI](https://gitlab.com/gitlab-org/cli) |
| `piki:azure-cli` | `az` | Azure DevOps | Azure DevOps access token for the organization, under **Git accounts** | [Azure CLI](https://learn.microsoft.com/cli/azure/install-azure-cli) and `az extension add --name azure-devops` |

- **Added with the first repository.** When a workspace binds its first repository on GitHub, GitLab or Azure DevOps, it gets that forge's extension, enabled (and, as below, `piki:git` with its first repository anywhere and `piki:github` with its first on GitHub); workspaces that had such a repository already got it when the server was updated. Owners and admins turn it off or remove it like any other, and add the others under **Add extension → Command-line tools**. One that was turned off stays off; one that was removed comes back only with a later first repository of its forge.
- **Every host has them**, from the connector version that brought them: an older one shows **Update the connector**, and its sessions run without them. A host needs the command itself, installed where its sandboxes find it (in `/usr`, such as `/usr/bin` or `/usr/local/bin`); without it, a call says so. Nobody signs in to it on the host.
- **The tool** takes the command's arguments as a list, without a shell (`{"args": ["run", "view", "123", "--log-failed", "--repo", "acme/app"]}`), runs in the session's worktree (or a `directory` in it), and returns its output. A long output is saved whole in the worktree's `tool-output/` (the newest 40 are kept, older ones are deleted), and the agent gets its start and end, with a line between them naming that file. Each call still runs only where an extension's tools may run.
- **Reads, always; writes, outside Read only, on the session owner's own host.** It reads the workspace's repositories: on GitHub with a read-only token of the workspace's GitHub App that covers the repositories the session owner can read, on any host; on GitLab and Azure DevOps with the owner's own access token, which can't be limited to the workspace's repositories, so only on the session owner's own hosts. A call from a message that may act, by the host's owner or a member they granted host commands, may also write as the session owner (comment, open or merge a pull request, rerun a pipeline) with their GitHub sign-in or access token, which Pikibun gives only to the session owner's own hosts. On a host someone else shared, its writes are refused: use `github_comment`, `github_issue`, `github_merge` and `git_push` there. A call that ran only because the host's owner lets every session run extension tools never writes.
- **The host's own sign-in** is used only where the session runs on its host itself ([unsandboxed hosts](hosts.md#running-without-the-sandbox) and sessions on the host's environment), as every command there runs as the host's OS user, or in the host owner's **own** sessions where they started the connector with `PIKIBUN_PIKI_HOST_SIGN_IN=1`: for Azure resources (`az vm`, …), which need an Azure sign-in, or the experimental macOS and Windows sandboxes, where `gh` and `glab` can't verify the proxy yet. Then the command runs on the host as its owner is signed in to it (`gh auth login`, `glab auth login`, `az login`). Another member's session never gets it.
- **Never their tokens.** Commands that would show the command's credentials (`gh auth token`, `--show-token`, `az account get-access-token`, `--expose-token`, `az --debug`) are refused. In the sandbox the token variables (`GH_TOKEN`, `GITLAB_TOKEN`, `AZURE_DEVOPS_EXT_PAT`) hold only a placeholder. On the host the command gets the host's `PATH`, `HOME`, proxies and its own sign-in variables, never the connector's other environment.
- **Read-only.** Each has a **read-only** setting (**Edit**): then only commands that read run (lists, views, logs, `GET` requests and GraphQL queries; for `az`, `list`, `show` and `query`, and none that show keys or secrets), never with the owner's credential to write, and with the worktree read-only (on the host, outside the worktree, so nothing a session wrote there, a repository's Git configuration say, can make the command run code there). Turn it on before setting the extension's tools to **Automatic**.
- **`gh` before `github_read`.** Where a session has both `gh` and [`piki:github`](github.md)'s tools, its agent reads issues and pull requests and waits for CI with `gh`, since every `github_read` read counts against the session owner's own GitHub rate limit. It keeps `github_read` for waiting for any other change (`wait: "change"`), and `github_comment`, `github_issue` and `github_merge` for the writes `gh` refuses.

## Session tools

Pikibun's own tools are becoming extensions, one by one ([#163](https://github.com/OpenCara/pikibun/issues/163)), so a workspace chooses them like any other. Each such **session-tool extension** turns one or more of the session's own tools on or off; the tools themselves don't change.

| Extension | Tools |
|---|---|
| `piki:schedule` | `schedule` |
| `piki:git` | `git`, `git_push` |
| `piki:node` | `node` |
| `piki:python` | `python` |
| `piki:rust` | `rust` |
| `piki:go` | `go` |
| `piki:dotnet` | `dotnet` |
| `piki:make` | `make` |
| `piki:browser` | `browser` |
| `piki:tunnel` | `tunnel` |
| `piki:github` | `github_read`, `github_comment`, `github_issue`, `github_merge` |
| `piki:notion` | `source_read`, for Notion sources |
| `piki:google-drive` | `source_read`, for Google Drive sources |
| `piki:dropbox` | `source_read`, for Dropbox sources |
| `piki:onedrive` | `source_read`, for OneDrive / SharePoint sources |
| `piki:feishu` | `source_read`, for Feishu / Lark sources |
| `piki:tencent-docs` | `source_read`, for Tencent Docs sources |
| `piki:sessions` | `sessions` |
| `piki:files` | `identity`, `ls`, `read`, `grep`, `find`, `write`, `edit`, `move_file`, `copy_file`, `delete_file`: always on. The six with Pi's names take Pi's parameters and answer as Pi's own tools do, so an extension's `tool_call` and `tool_result` handlers for `read`, `write`, `edit`, `ls`, `grep` and `find` (`isToolCallEventType("write", event)`, `isReadToolResult`) match them. An extension's own tool with one of their names, or with their old names (`read_file`, `write_file`, `edit_file`, `list_files`, `search`), is left out |

- **Added with a source, or by hand.** None is in a new workspace but `piki:files`. A workspace gets `piki:git` with its first repository, `piki:github` with its first GitHub repository, and a document source's extension (`piki:notion`, ...) with its first source of that kind, turned on, as it gets [`piki:gh`](#pikibuns-built-in-extensions-gh-glab-and-az); owners and admins add the others (Node.js, Python, the browser, scheduled prompts, ...) under **Extensions → Add extension → Pikibun tools**. The workspace page lists those it has under **Extensions**; **Remove** turns one off. One that was removed comes back only with a later first source of its kind, or added by hand. Sessions stop offering a tool that is off from their next message, and a call to it by name (from a code mode script, say) is refused. Workspaces from before this change kept the tools they had: each got, turned on, every one it hadn't turned off, but `piki:github` only with a GitHub repository and a document source's only with a source of that kind (neither offers anything without one); `piki:tunnel` was already off until added.
- **The session's own.** Their tools run as the session's tools do: within the tool groups of the session's owner and the message's sender, and the Read-only rules, never as extension tools that run like host commands. So they have no settings, and a host's owner can't require them.
- **Nothing to install.** Every connector of this release has them. One that predates a session-tool extension offers its tools whatever the workspace chose. Pikibun tells every connector which ones the workspace has turned on and which off, so older connectors, which take one a workspace doesn't name as on, leave out those it hasn't added too. Where a session can't learn its workspace's choice for the moment, its tools stay on.
- **No shell.** `bash` and `host_bash`, and with them `piki:shell` and `piki:host-shell`, are gone (#163): sessions clone and commit with `git`, build and test with `node` and `python`, move, copy and delete with the file tools, and chain tools with code mode. A workspace's old choice for those two still reaches connectors from before their removal, which offer them unless turned off; workspace pages no longer list them.
- **`git` runs Git.** The `git` tool takes Git's arguments as a list and runs exactly `git <arguments>` in a clone, with no shell, pager, editor or password prompt, so its record shows one Git command rather than a script. It runs only version-control subcommands, and refuses the options that make Git run another program. Its calls run as commands do, even subcommands that only read: a repository's own Git configuration, which the agent can write, can make `git status` run a program.
- **`node` runs Node.js.** The `node` tool runs one program of Node.js's (`node`, `npm`, `npx`, `pnpm`, `yarn`, `corepack`) with its arguments as a list, in a clone, without a shell, colours or prompts. Commands that act on a package registry as an account (`publish`, `login`, `token`, `owner`, `dist-tag`, ...) are refused: sessions have no registry account. It runs the connector's own Node.js (24 or newer, which the connector needs anyway), with its `npm` and `npx` (and `corepack` where it bundles it: Node.js 25 and newer don't), ahead of any other: only its `node`, those package managers (and `pnpm` and `yarn` where installed globally) and its C headers are given to the sandbox, read-only, never the directory they are in: in the Linux sandbox below `/opt/pikibun/node` where the sandbox doesn't already see them (nvm, Volta, a tarball), and the macOS sandbox may read and run them. Elsewhere (Windows and unsandboxed hosts) it runs the Node.js on the commands' PATH. A version a project asks for (`.nvmrc`, `engines`) isn't provisioned yet (#163). Its calls run as commands do, since `pnpm test` or `node script.js` run whatever the project or script says.
- **`python` runs Python.** The `python` tool runs one of `python3`, `pip`, `pip3`, `uv`, `uvx`, `poetry` and `pytest` with its arguments as a list, without a shell, colours or prompts. With `venv` (`.venv`, made with `python3 -m venv .venv`) the environment's own programs run first, so packages install there rather than into the host's Python. Publishing and storing package index credentials (`uv publish`, `uv auth`, `poetry publish`, `twine upload` however launched, `poetry config` of tokens) are refused. Its calls run as commands do. It isn't offered in the Windows sandbox yet, whose container reaches no Python; Linux hosts lacking `python3-venv` are told so where they show their prerequisites.
- **`rust`, `go` and `dotnet` run their ecosystems.** Each runs one of its programs (`cargo`, `rustc`, `rustup`, `rustfmt`; `go`, `gofmt`; `dotnet`) with its arguments as a list, in a clone, without a shell, colours, progress bars or telemetry, the toolchain's usual directories (`/usr/local/cargo/bin`, `/usr/local/go/bin`, `/usr/share/dotnet`, ...) looked in after the sandbox's PATH. Commands that act on a package registry as an account are refused: `cargo publish`, `login`, `logout`, `owner` and `yank` (also as `cargo +toolchain` or through `rustup run`), `dotnet nuget push` and `delete`, and adding or updating a NuGet source with a password. Go publishes by tagging a repository, so `go` refuses nothing. Their calls run as commands do. The toolchain must be installed where the sandbox sees it, not in a home directory: Rust from the distribution's packages (`/usr/bin`), or a system-wide rustup as the official `rust` image has it (proxies in `/usr/local/cargo/bin`, toolchains in `/usr/local/rustup`, which `rust` calls then use as `RUSTUP_HOME` unless the session's environment names another; read-only, so a toolchain file naming one that isn't installed fails), Go in `/usr/local/go` or `/usr/lib/go`, .NET in `/usr/share/dotnet`, `/usr/lib/dotnet` or `/usr/local/share/dotnet`. On macOS, Homebrew's toolchains, or Go's and .NET's installers' (`/usr/local/go`, `/usr/local/share/dotnet`) and a system-wide rustup in `/usr/local`, which the macOS sandbox may read and run; a rustup in a home directory isn't seen there either. The session keeps its own cargo home. None is offered in the Windows sandbox yet.
- **`make` runs make.** The `make` tool runs `make` with its arguments as a list, in a clone, as the others run their programs. It refuses nothing: a Makefile's recipes are shell commands the project wrote (or the agent did), which the call's `make` stands for, as `npm test` does for a package's scripts. It is the system's make, or GNU make from Homebrew in `/usr/local/bin`; not in the Windows sandbox.
- **Programs the host lacks.** In the Linux sandbox, which sees only the host's `/usr` and the connector's Node.js, which of these tools' programs a session can run is known before it runs any: a program the host hasn't installed for the whole system (`pnpm` or `yarn` not installed globally, `corepack` on Node.js 25 or newer, `uv`, `poetry`, a rustup in `~/.cargo`, ...) is named, with the step that installs it on the host, in the agent's instructions and under **Extensions** in the session panel (**Missing programs**), as the browser without Chromium is. A call to one is refused before it runs, saying the same, so the agent tells its people what the host's owner installs rather than finding out from `command not found`; a `python` call with `venv` is never refused, as the environment may have the program. Beside each, the host's owner has **Chat**: it starts a private session in their [private workspace](workspaces.md#your-private-workspace) on that host, [on the host itself](hosts.md#sessions-on-the-host) where it can run there, and opens it, with an opening message that names the programs and how each is installed, and asks its agent to look at the host, install them for the whole system and check them; where a step needs root, it runs it with `sudo -A`, which [asks you for your password](hosts.md#sessions-on-the-host) in a box of its own, and where you decline, it gives the commands to run in a terminal instead. In the sandbox (a host whose connector can't run sessions on the host), it can only work out those commands. The browser without Chromium and the tunnel without cloudflared offer the same, there and on the host's page. Sessions find a program installed in `/usr` from their next message; one installed into a Node.js outside `/usr` (nvm, Volta), from their next session. Elsewhere (macOS, Windows, unsandboxed hosts) commands see the host's own PATH, and nothing is checked beforehand.
- **`browser` to see a web page.** The `browser` tool drives a headless Chromium in the session's sandbox; see [The browser](#the-browser-pikibrowser).
- **`tunnel` to put a web app online.** The `tunnel` tool runs the session's web server in its sandbox and puts it online at a public address; see [The tunnel](#the-tunnel-pikitunnel).
- **The brokered tools and the file tools.** `piki:github`, the document-source extensions and `piki:sessions` switch the tools that act as the session owner through Pikibun, and `piki:git` switches `git_push` with `git`. `piki:files` holds the tools every session needs to read and write its files: it is always on, and turning it off is refused.
- **One per kind of document source.** `piki:notion`, `piki:google-drive`, `piki:dropbox`, `piki:onedrive`, `piki:feishu` and `piki:tencent-docs` each switch `source_read` for their kind: sessions offer `source_read` while any of them is on, and list and read only the sources of the kinds that are on. They replace `piki:sources`, which switched every kind at once: a workspace that turned it off has each kind off until it turns that kind on. Hosts on connectors from before the split have only `piki:sources`, which is on there while any kind is on.
- **No place taken.** They don't count towards a workspace's 32 extensions.
- **Defined by Pikibun, not by the connector.** `node`, `rust`, `go`, `dotnet`, `make` and `source_read` are described by the server as data, and connectors run them with their own engine, so tools of these kinds that Pikibun adds reach hosts as soon as the server has them, without a connector update. Their switches work the same way. See [the design](design/tool-definitions.md).

## The browser: piki:browser

The `browser` tool lets the agent look at and test web pages: the app it is building, a page it was pointed to, a flow that should work. It drives a headless Chromium **in the session's Linux sandbox**, as one sandboxed command per call, so its record shows exactly what runs and its network is the session's. See [the design](design/piki-extensions.md#a-browser-pikibrowser).

- **One call, one visit.** A call opens `url` (http, https, a `file:` page such as a build in the worktree, or `about:blank`; without one, the page the last call left), then runs `actions` in order: `goto`, `click` and `hover` (a CSS selector, `text=<visible text>`, or coordinates), `type` (with `submit` to press Enter), `press` a key, `select` an option, `scroll`, `wait` for a selector, text or a time, `evaluate` JavaScript in the page and return its value, `screenshot` (also `full_page`), `back`, `forward` and `reload`. A failed action stops the rest. The answer is the page as the call left it: a screenshot the model sees, its URL, title and HTTP status, its visible text, the elements it can act on with a selector for each, console messages, uncaught errors and failed requests.
- **The app under test, served for the call.** A sandboxed command's processes and `localhost` end with it, so a call that tests a web app starts its server too: `serve: {program: "pnpm", args: ["dev", "--port", "5173"], directory: "app", port: 5173}` runs from before the page opens (once the port answers) until the call ends, and its output comes back with the page. It is one of the `node` and `python` tools' programs, checked as those tools check them (so no `npm publish`) and started without a shell, with their environment: the connector's own Node.js first, or a Python virtual environment named by `venv`.
- **A profile that persists, pages that don't.** Each call starts Chromium afresh with the session's own profile in its home, so cookies and storage (a sign-in) last from one call to the next, while open pages, their scripts' state and form input don't: do a whole flow in one call. The HTTP cache is off, so each call sees what the server serves now.
- **Run as commands are.** Pages run their own scripts, `evaluate` runs the agent's, and `serve` starts the app, so each call is a program operation of its own, run as the `git`, `node` and `python` tools' calls are, and refused in a **Read only** message. It stops at the host's [command time limit](hosts.md#host-configuration), and reports, with a screenshot, a few seconds before it.
- **Its network is the session's.** Other hosts go through the session's proxy, so the workspace's [network access](hosts.md#network-access) applies: a refused host, or plain `http://` outside the sandbox, says so in the answer. Chromium checks certificates against its own roots.
- **The Browser tab.** Each call leaves its screenshots and a report in the worktree's `browser-output/` directory (the last 30 calls), which the session panel's [Browser tab](sessions.md) shows and `read` reads.
- **Only in the session's sandbox.** Chromium runs in the session's Linux sandbox, never on the host itself, where the protocol that drives it would reach the host's files and network as its user. So sessions that run on the host ([unsandboxed hosts](hosts.md#running-without-the-sandbox) and [sessions on the host](hosts.md#sessions-on-the-host)) and, for now, the experimental macOS and Windows sandboxes aren't offered the tool. In the sandbox, Chromium can't keep its own sandbox around the pages it runs: a page that exploits it gets what the session has (its files, its branch, the workspace's network), never the host.
- **Needs Chromium on the host.** The host's owner has the connector find one installed there, gives its path, or has the connector download one, on the host's page; see [A browser for sessions](hosts.md#a-browser-for-sessions). Sessions on a host without one, or on an older connector, aren't offered the tool, and say why: a warning above the chat box as the session starts, a row in its panel's **Extensions** section, and a sentence to its agent. Like the other session tools it is on once a workspace adds `piki:browser`.

## The tunnel: piki:tunnel

The `tunnel` tool puts the web server a session builds online at a public `https://` address, so people can open it in a browser or on a phone: a web app, a preview of a branch. The server runs **in the session's Linux sandbox**, as a session service that keeps running after the call that started it; Cloudflare's `cloudflared` runs **in the host's connector**, never in the sandbox, and gets an address of Cloudflare's for it (a quick tunnel, `https://<name>.trycloudflare.com`). See [the design](design/tunnel.md).

- **Off until added.** Owners and admins add **Tunnel** (`piki:tunnel`) under **Settings → Workspaces →** the workspace **→ Extensions → Add extension → Pikibun tools**. A host's owner can refuse it on their host whatever its workspaces chose (**Off**, below).
- **`start`, `status`, `stop`.** `tunnel {action: "start", serve: {program: "pnpm", args: ["preview", "--port", "4173"], directory: "app", port: 4173}}` starts the server: one of the `node` and `python` tools' programs, checked as those tools check them and started without a shell, exactly as the browser's `serve`. Once its port answers on the sandbox's `localhost` (within `timeout_seconds`, 60 by default), the connector opens the tunnel, and the call answers with the address. A new `start` replaces the one online. `status` gives the address, whether `cloudflared` is connected, the uptime and the server's last 40 lines of output; `stop` takes it offline. The server should accept any `Host` header (Vite: `--host` and `server.allowedHosts`).
- **Only for the host's people.** It publishes from the host's network, so each `start` runs like a [host command](host-commands.md): only in sessions of the host's owner and of members they granted host commands, for messages of theirs, never where the host's owner merely lets every session run extension tools. A **Read only** message refuses it. `status` and `stop` ask nobody.
- **Online until something stops it**: the tool's `stop` or the session panel's **Stop** button (anyone who may write to the session), a new `start`, someone stopping the session's work, the session closing (a restart, a backup, its host stopping) or being archived, the server exiting, `cloudflared` failing, or the host's [service lifetime](hosts.md#host-configuration) (4 hours by default) at most. One per session.
- **Visible.** While it is online the session panel shows the address, who started it and until when, with a **Stop** button; the session list marks the session **Online**; the audit log records `session.tunnel.started` and `session.tunnel.stopped`, with the address, who started or stopped it, and why it stopped.
- **Only the declared port, and only through its link.** Requests to the address reach the server's port in the sandbox and nothing else, of the sandbox or the host. By default (`access: "link"`) the address the call answers with carries a secret (`?pikibun_tunnel=…`): a browser that opens the link is sent on to the page without it and keeps the secret as a cookie for a day, and anything without it, the bare address included, gets `401`. The connector checks it and takes it out of the cookies the server receives. Anyone the link is shared with, and everyone who can read the session (its panel shows the link), can open it. `access: "public"` opens the address to anyone, for clients that can't follow a link, such as a webhook. Cloudflare's quick tunnels have no uptime guarantee, and a new address at each start.
- **The sandbox stays as it is.** The server has the session's files, network and limits, as its commands do; its network still reaches only the session's [proxy](hosts.md#network-access). No tunnel credential enters the sandbox.
- **Needs cloudflared on the host, and the Linux sandbox.** The host's owner has the connector find one installed, gives its path, or has it download one, on the host's page; see [Tunnels for sessions](hosts.md#tunnels-for-sessions). Sessions on a host without one, on the host itself, in the experimental macOS and Windows sandboxes, or on an older connector aren't offered the tool, and their panel's **Extensions** section and agent say why.

## Pull request flow: piki:pr-flow

Has the agent carry each change to a repository through a pull request (a merge request on GitLab), from the first edit to the merge, with a review window the workspace chooses. It comes with the connector, and a workspace adds it like any extension: **Settings → Workspaces →** the workspace **→ Extensions → Add extension → Workflows → Pull request flow**, then **Edit** for its settings.

- **A draft at the first change.** As soon as the session starts changing files in a clone of one of the workspace's repositories, the agent commits, pushes to the session's branch and opens a draft pull request (`git_push` with `pull_request.draft: true`; see [Drafts](pushes.md)).
- **Ready for review once done.** When the change is complete, its tests pass and its last commit is pushed, it marks the draft ready for review (`draft: false`), with a title and body for the finished change.
- **The review window: `review-minutes`** (30 by default, up to a week). From when the pull request is ready, the agent waits that long for reviews (on GitHub with `github_read`'s `wait`). It judges each review point: it fixes the valid ones, pushes, and answers each point, saying why for one it judges invalid and leaves as it is. Each pushed fix starts the window again, for a re-review. It merges once the pull request is approved with nothing left to address, or once the window ends with nothing new to address, but never over a reviewer's request for changes it didn't make: that it leaves open, and tells the person.
- **`review-minutes` of 0 merges at once** (with `auto-merge` off, hands it over at once), as soon as the pull request is ready, without waiting for reviews.
- **`merge-method`**: `squash` (the default), `merge` or `rebase`. **`wait-for-checks`** (on): let the pull request's checks finish, and fix failing ones, before merging; with it off and a window of 0, it merges the moment the pull request is ready.
- **`auto-merge`** (on): merge the pull request once it is approved, or once its window ends with nothing new to address. Turn it off to leave merges to people: the agent still opens the draft, makes it ready and works the review window (fixing and answering review points, letting checks finish), but where it would merge it tells the person, with the link, that the pull request is ready for them to merge, and leaves it open. It doesn't queue an automatic merge either (`gh pr merge --auto`, ...), unless the person asks.
- **Its steps are the session's own tools**: commits and pushes, `git_push` (opening, readying), `github_comment` (answers), `github_merge` (the merge) run at once, within the tool groups of the session's owner and the message's sender. A forge refusing the merge (branch protection, required reviews or checks) stops it there. On GitLab and Azure DevOps it reads reviews and merges with `glab` or `az` (`piki:glab`, `piki:azure-cli`); on hosts whose sessions push with Git itself, it opens and readies with `gh` or `glab` too. It follows a pull request opened, readied or merged through `git_push`, `github_merge`, `gh`, `glab` or `az` (a `gh`, `glab` or `az` call that readies or merges means the pull request of the clone it runs in). On GitHub, one merged or closed some other way (by a person, say) it learns of when the agent reads it with `github_read`. Elsewhere it doesn't learn of one merged some other way (on Bitbucket, which has no such tool, or by a person); its notes may then still speak of a review window until the agent finds out. A push restarts the review window only when it moves the pull request's own branch.
- **How it guides the agent.** It adds no tool: it adds the flow to each message's instructions, with where the session's pull requests stand, and a note to a tool's result where a step is due (the first change without a pull request, a draft opened, a pull request made ready, with the time its window ends, a push after that, a merge). The person's own words come first: ask for no pull request, or not to merge, and the agent leaves those steps out.

## Auto mode: piki:auto-mode

Lets members leave the model and its reasoning to Pikibun: it adds **Auto** to the **Model** menu, of a new session and of a session. You still pick the host. A workspace's owners and admins add it under **Settings → Workspaces →** the workspace **→ Extensions → Add extension → Pikibun features → Auto mode**; turning it off or removing it takes **Auto** out of the menus again. It has no settings, and no host installs anything.

- **A model judges each message.** When a message sent with **Auto** starts to run, the lightest model you may use on the session's host reads it and says what kind of task it is, by the table in Anthropic's guide [Which Claude model should you build with?](https://claude.dev/blog/which-claude-model-should-you-build-with/): everyday engineering and debugging, well-scoped coding (a bug fix, work to a clear spec), chat and questions, side tasks (searching, reading logs, summarizing), classification and extraction, documents and spreadsheets, routine reviews and drafts, computer use and screenshots, major refactors and migrations, or deep research, and whether it is harder than most of its kind. It runs on the session's host, the host the message goes to anyway, with its owner's sign-ins.
- **The guide picks the model.** Each kind starts where the guide starts it: everyday engineering on the Opus class at medium effort, well-scoped coding and documents on the Sonnet class at medium, chat on the Sonnet class at low, side tasks and classification on the Haiku class, major refactors and deep research on the Fable class at medium, and anything unclear on the Opus class at medium. A harder task gets one more level of reasoning first, as the guide advises, before a bigger model. Where the host has no model of that class, Auto takes the next one up at a level less reasoning, or else the next one down at a level more. Other providers' models count by their size: a mini or a flash as the Haiku class, a frontier model (a Pro, GPT-5) as the Opus class.
- **A short follow-up keeps the model.** "Go ahead" or "yes, try again" stays on the model and reasoning the conversation already uses, so a big task isn't handed to a small model halfway.
- **The conversation says what it chose.** After your message, a line such as *Auto: Claude Sonnet 5.5, medium reasoning, for well-scoped coding: a bug fix in one module. Judged by Claude Haiku 5.5.* shows the choice and why; in a session the model menu reads **Auto ·** and the model in use.
- **Rules when the judge can't answer.** If the judging model fails, takes more than 20 seconds or answers with something else, Auto reads the kind from words in your message instead and the line says *Chosen by rules*. A host whose connector predates this always chooses by those rules. Your message is never held back for Auto.
- **Only among your models.** Auto chooses among the models the host offers you and hasn't disabled; nothing in a message can make it pick another. Pick a model yourself whenever you know better: in a session, **Auto** stays on until you pick a model or leave the session.

## Prompt audit: piki:prompt-audit

A shared host runs other members' messages with its owner's models, next to the owner's files and credentials. The sandbox keeps sessions away from them, but host commands, [sessions on the host](hosts.md#sessions-on-the-host), unsandboxed hosts and extensions run on the machine itself, so a message that talks an agent into reading out `~/.pi/agent/auth.json` could still leak the owner's secrets. `piki:prompt-audit` comes with the connector and has a model check each message before it reaches the agent.

- **Turn it on for your host:** on the host's page, under **Extensions**, tick **Require of every session** on **Prompt audit** (`piki:prompt-audit`), then open its **Settings**. From then on every message to a session on the host is audited, except the host owner's own: members' messages and side questions, scheduled prompts, and messages from other sessions, whoever owns the session. (Every workspace also has it, turned off, among its extensions: its owners and admins turn it on for its own sessions.)
- **What it refuses:** messages that try to get the agent to read, print or use the host's or its owner's credentials (Pi's provider keys and logins, SSH keys, tokens, credential files, secrets in the environment), read the owner's files outside the session's worktree and repositories, probe the machine's environment, processes or network, or send host data elsewhere or get around the sandbox, its proxy or the audit itself. Ordinary work, including work that is *about* secrets in the project, is allowed.
- **Settings:** `model`, the model that audits as `provider/modelId` (the session's model when empty; a small, fast model keeps sending quick and cheap); `policy`, what else counts as sensitive on this host in your own words (such as `Never read ~/work/clients or the database in /srv/data`), which it refuses too; `audit`, `others` (default) or `all` to audit the host owner's own messages as well. Each audit is one request to the model, on the host owner's provider account, and takes at most 45 seconds. A message with images needs a model that reads images.
- **It fails closed.** A message it flags is refused before it reaches the agent, and so is one it can't check: its model is unavailable, fails, takes too long or gives no clear verdict. The transcript shows a fixed reason naming the kind of thing flagged, such as *it asks for credentials, keys or tokens*, where the message was sent. The auditor's own explanation is model text that a crafted message could steer, so it isn't shown to the sender: the connector writes it to its log on the host (`prompt audit: refused a message (credentials): …`).
- **Its limits:** it judges each message on its own. It doesn't see earlier messages, or what the agent later reads in files, web pages or tool output, so it is one more safeguard, not a replacement for the sandbox and tool groups; a tool-call guard such as `npm:cc-safety-net` checks what the agent actually runs. The message goes to the model between markers, as data it is told not to obey, but like any check by a model, a determined attempt may get past it.
- **In Pi itself.** It is an ordinary Pi extension on the `input` event: in Pi it audits messages that don't come from the terminal (`rpc` and `extension` sources), and the settings are its flags.

## Context files: piki:context-files

Pi adds a project's `AGENTS.md` or `CLAUDE.md` to its system prompt; Pikibun's sessions don't run Pi's own agent session, so they load neither unless this extension is on. `piki:context-files` comes with the connector, and every workspace has it, turned off, among its extensions: its owners and admins turn it on under **Settings → Workspaces →** the workspace **→ Extensions**, and set what it adds under **Edit**.

- **`context-files`** names the files, separated by commas or new lines: a path in each clone (`AGENTS.md|CLAUDE.md`, the default, uses the first a clone has; wildcards in a file's name, such as `docs/ai/*.md`), `host:<name>` for a file the host's owner keeps in the host's context directory (`~/.pi/agent/context-files`, or `PI_CONTEXT_FILES_DIR`), or an `https://` page. **`context-max-chars`** (60,000 by default) caps what each message gets.
- **Each message gets them**, read again each time, as a **Project context** section of its system prompt; a repository cloned during a message gets its files in the result of the call that cloned it.
- **It reads only what it should.** Repository files that link outside their repository or into `.git` are refused, host files come only from the context directory, and pages only over `https://`, never from a private network address. Whatever the files say reaches the agent as instructions, as `AGENTS.md` does in Pi: name only files you trust. See its [README](../extensions/context-files/README.md).

## Newer versions of Pikibun's extensions without a connector update

`piki:pr-flow` and `piki:context-files` are also Pi packages on npm (`@pikibun/pi-pr-flow`, `@pikibun/pi-context-files`). A connector started with `pikibun connect --managed-extensions` can run the version Pikibun pins, installed from npm, in place of the copy built into it, so a fix to one reaches the host without a connector update. Workspaces and hosts keep naming them as before (`piki:pr-flow`), with no version and nothing to install by hand. Pikibun pins none yet, so until its first pins the option changes nothing. See [the design](design/extension-loading.md).

- **Pikibun chooses the version.** Each release of Pikibun names one version of each, with npm's own digest of it. The connector hears of them when it syncs its extensions, every half minute.
- **The newest version the host can vouch for runs.** For each extension the host runs the newest of: the pinned version, once it has passed the checks below; the newest version it has run before, while it is still installed; and the copy built into its connector. So a pin never takes a host back to an older version, a host that can't reach npm keeps what it ran, and a connector update still brings a newer built-in copy. The connector installs a pinned version only when it is at least as new as the other two.
- **Checked before it runs.** The connector installs it as it installs other extensions (no install scripts) into `extensions/managed/` in its state directory, and runs it only if it is a `@pikibun/` package, npm installed that one package at the pinned version and nothing else, its digest is the pinned one, it needs no newer connector, and every module loads. Otherwise the pin isn't used: the host writes why to its log (`Managed extensions: …`) and tries again 10 minutes later, or at its next start. An extension that only comes from npm, with no copy built in and none run before, is missing on that host: its page says why (an update the connector needs, say), and a session or a host that needs it goes without, as for any extension the host lacks.
- **When it changes.** A session runs the version that was current when it first used the extension, and keeps it, so nothing changes under a running message, and nothing restarts. When the connector next starts, it deletes the versions that are neither pinned nor the newest it has run.
- **Where it shows.** The host's page shows the version the host runs. `pikibun extensions list` lists them as managed, they don't count among the host's installed extensions, and `pikibun extensions remove` refuses them.
- **Off unless you ask for it.** They run in the connector, outside the sandbox, as every extension does today, and a new version reaches every host within a sync, so for now only a host whose owner starts the connector with `--managed-extensions` runs them. Without it, with `--no-remote-installs` (which refuses them as it refuses other installs from Pikibun), or run from source (`pnpm connect`), a connector runs only the copies built into it, whatever is pinned or installed. The prompt audit, and the extensions that switch the session's own tools or run a forge's command, always run as built into the connector.
