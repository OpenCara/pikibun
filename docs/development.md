# Development

Requires Node 24 and pnpm.

```sh
pnpm install
cp apps/server/.env.example apps/server/.env   # see below
pnpm build                                      # the web client into dist/client
pnpm dev:server                                 # API and web client on :8787
pnpm dev:client                                # or the app in a window of this desktop, with hot reload
```

For local development, set in `apps/server/.env`: `APP_ORIGIN=http://localhost:8787`, `DATABASE_URL=sqlite:./data/dev.sqlite` (the default `/data` path is the container's), `SESSION_SECRET`, `VAULT_KEY`, and the test mode that allows plain HTTP on localhost: `TEST_AUTH_ENABLED=true`, a `TEST_AUTH_SECRET` of at least 32 characters and a future `TEST_AUTH_EXPIRES_AT` (such as `2030-01-01T00:00:00Z`). Sign in with a GitHub OAuth app whose callback is `http://localhost:8787/api/auth/github/callback`, or as a test user by running this in the browser console on `http://localhost:8787`, then reloading:

```js
await fetch("/api/auth/test", { method: "POST", headers: { Authorization: "Bearer YOUR_TEST_AUTH_SECRET", "Content-Type": "application/json" }, body: JSON.stringify({ displayName: "Dev" }) });
```

- `pnpm typecheck` (also typechecks the apps), `pnpm test` (set `TEST_DATABASE_URL=postgres://…` to also run the provider suite against Postgres), `pnpm test:coverage` (the same tests with Node's own coverage of `apps`, `packages` and `extensions`: a summary after the results, and `lcov.info` for editors and coverage services), `pnpm build` (the NSH web client, as `pnpm build:client`), `pnpm build:server` (bundled server in `dist/server`), `pnpm build:cli` (the connector package).
- The sandbox's Python programs are `.py` files in `apps/runner/src/sandbox-python` (the helper every sandboxed step of the Linux and macOS sandboxes runs, and the `git` shim). The connector embeds them through `apps/runner/src/sandbox-python.generated.ts`: after changing one, run `pnpm python:embed` (`tests/sandbox-python.test.ts` fails while it is out of date). `pnpm python:check` lints them with Ruff and type-checks them with Pyright, both from npm, for Python 3.9 (macOS's own `python3`). `tests/sandbox-conformance.test.ts` holds every implementation of a session's files (those two helpers, the Windows sandbox's Node helper and the unsandboxed host's TypeScript) to one table of cases: a new file operation, or a fix to one, adds its cases there.
- `pnpm connect …` runs the connector from source, with the same options as `pikibun connect`; add `--allow-insecure-loopback` to pair with a local `http://` server.
- `pnpm test:connected` runs the end-to-end suite against a real server and connector (Linux with bubblewrap).
- `pnpm dev:native [--port 8787] [--no-host] [--pairing]` runs a local test-mode server for developing the apps: a test user with an app token, a workspace and, unless `--no-host`, this machine as a host offering the deterministic fixture model (not an LLM) with one session. `--pairing` adds a pairing code for an app to pair this machine with. It writes what the apps need to `.local/dev-native.json`; Ctrl-C stops it and deletes its data.
- Releasing: each part has its own release line and version, started by pushing its tag on a commit in `main` (e.g. `git tag server-v1.4.0 && git push origin server-v1.4.0`). A suffix such as `-beta.1` makes a prerelease. Nothing needs committing first: each workflow checks the tag is on `main`, runs CI and sets the tag's version in the package it builds (`scripts/set-release-version.mjs`), so the committed versions need not match.

  | Tag | Workflow | Publishes |
  | --- | --- | --- |
  | `cli-v1.2.3` | `release.yml` | `pikibun` on npm, with provenance; a prerelease goes to the `next` dist-tag |
  | `server-v1.2.3` | `release-server.yml` | The server image (web app and backend) to `ghcr.io/opencara/pikibun`, then deploys a release (not a prerelease) to the deployment server once the image is pushed; no GitHub release |
  | `app-v1.2.3` | `release-app.yml` | The NSH client on a GitHub release, "Pikibun 1.2.3": the Windows installer (x64 `.exe`, signed through SignPath), the signed and notarized macOS app (arm64 `.dmg`), Linux (x86_64 `.tar.gz`) and the signed Android `.apk`; iOS to TestFlight |

  Two pins travel with releases and are raised by hand in the commit a tag is put on: `APP_CLI_VERSION` (`apps/nsh/src/lib/this-computer.ts`), the `pikibun` CLI release an `app-v` release installs for **This computer**, and `PINNED_CLOUDFLARED` (`apps/runner/src/cloudflared.ts`), the cloudflared version and SHA-256 digests a `cli-v` release downloads for tunnels (take the digests from the release's assets: `gh api repos/cloudflare/cloudflared/releases/tags/<version> --jq '.assets[] | {name, digest}'`).

  NSH's app line makes each release the latest, and a prerelease only from a tag with a suffix (the removed Electron app's `desktop-v` line is no longer built or released). It generates notes since its own previous tag. The apps' version is the tag's without a prerelease suffix, and their build number is the run's. Pull requests that change how the app is packaged (`release-app.yml`, `apps/nsh/nsh.json`, its icon, `apps/nsh/windows/`, `scripts/nsh.mjs`) build every platform without the release's secrets: Android is signed with a throwaway key made for the run, so its signing is tested too, macOS is ad hoc signed, and Windows is unsigned. The Windows job checks its installer's product name and version (which SignPath requires), and installs and uninstalls it to test it. npm needs either a trusted publisher on npmjs.com for `OpenCara/pikibun`, workflow `release.yml` (keep that file name), environment `release`, or an `NPM_TOKEN` repository secret.
- Deploying the server: once a `server-v` release's image is on GHCR, `deploy-server.yml` joins the tailnet as an ephemeral, tagged node, connects to the deployment server over Tailscale SSH and runs [`scripts/deploy-server.sh`](../scripts/deploy-server.sh) there. It pulls the image by digest, writes it to `PIKIBUN_IMAGE` in the deploy directory's `.env`, recreates the `pikibun` service with `docker compose up -d --no-build` and waits for the container to report healthy. The image's web client is NSH alone; the script writes it to `STATIC_DIR`, drops any `STATIC_CLIENT` left from the React client, and removes any separate preview origin (`PREVIEW_ORIGIN`, `PREVIEW_STATIC_DIR`). Actions then checks the public client at `DEPLOY_URL`, its startup assets and CSP, and the API's release version; a healthy backend serving the wrong client does not pass. Prereleases are not deployed; **Actions → Deploy server → Run workflow** deploys any published version, to redeploy or go back to one. A failed deploy is not rolled back by itself: migrations ran when the new container started, so go back only to a version that reads the migrated database. Configure it in the `production` environment, and add required reviewers there to approve each deploy; without the settings nothing is deployed:
  - Variables `DEPLOY_HOST` (the server's tailnet name, such as `nerd.tail7e2cef.ts.net`), `DEPLOY_USER` (in the `docker` group), and optionally `DEPLOY_PORT` (22), `DEPLOY_PATH` (the directory with `docker-compose.yml` and `.env`, `pikibun` from the user's home by default), `DEPLOY_URL` (the production public origin) and `TS_TAGS` (`tag:ci` by default).
  - Secrets `TS_OAUTH_CLIENT_ID` and `TS_OAUTH_SECRET` (a Tailscale OAuth client, **Settings → OAuth clients**, with the **Auth Keys** write scope and the tags in `TS_TAGS`) and `DEPLOY_SSH_KNOWN_HOSTS` (the server's Tailscale SSH host keys, `ssh-keyscan -p PORT HOST` from a tailnet device, checked against the server's own fingerprints).
  - In the tailnet policy: `TS_TAGS` owned in `tagOwners`, the server tagged too (Tailscale SSH doesn't let tagged devices into user-owned ones), and an `ssh` rule with `"action": "accept"` from `TS_TAGS` to the server's tag for `DEPLOY_USER`, plus an access rule or grant to its port 22. No SSH key is needed: Tailscale SSH admits the runner by its tag.
  - The server's `docker-compose.yml` runs `image: ${PIKIBUN_IMAGE:-pikibun}`, as this repository's does, and the user can pull from `ghcr.io/opencara/pikibun` (public, or after `docker login ghcr.io`).
- Signing the `app-v` release: the secrets and variables below live in the `release` environment, each platform's all or nothing. An `app-v` tag's run fails for macOS or Android while its signing is not configured; Windows is released unsigned, with a warning, until SignPath is set up. Without iOS's, the iOS job only checks that the app packages.
  - An App Store Connect API key (Users and Access › Integrations; the App Manager role is enough), shared by macOS (notarization) and iOS: `APP_STORE_CONNECT_API_KEY` (the `.p8` file's contents), `APP_STORE_CONNECT_API_KEY_ID` and `APP_STORE_CONNECT_API_ISSUER_ID`.
  - macOS, the app signed with Developer ID and the hardened runtime, and it and its `.dmg` notarized and stapled: `MAC_CERTIFICATE_P12` (a **Developer ID Application** certificate and its key, exported as `.p12`, base64: `base64 -i cert.p12`), `MAC_CERTIFICATE_PASSWORD`, and the variable `MAC_SIGNING_IDENTITY`, the certificate's name without its `Developer ID Application:` prefix (e.g. `OpenCara (TEAMID)`).
  - iOS, uploaded to TestFlight: an app record for the bundle ID `com.pikibun.app` (the client's `id` in `apps/nsh/nsh.json`) in App Store Connect, `IOS_CERTIFICATE_P12` (an **Apple Distribution** certificate as base64 `.p12`) with `IOS_CERTIFICATE_PASSWORD`, and `IOS_PROVISIONING_PROFILE` (an App Store provisioning profile for `com.pikibun.app`, base64). Every `app-v` tag goes to TestFlight, to the internal testers at once: its Info.plist answers export compliance (`ITSAppUsesNonExemptEncryption` false, as the app uses only the system's HTTPS), so no build waits as Missing Compliance. Submitting a build for App Store review stays manual. App Store Connect takes a version's builds only in increasing build numbers, and this workflow's run numbers started again from 1: the first `app-v` version must be above any version uploaded before.
  - Android: `ANDROID_KEYSTORE` (a release keystore, base64; `keytool -genkeypair -keystore release.jks -alias upload -keyalg RSA -keysize 2048 -validity 10000`), `ANDROID_KEYSTORE_PASSWORD` and `ANDROID_KEY_ALIAS`. Keep the keystore: every later APK must be signed with it to update an installed one. An APK released before the key was set carries Android's debug key, so installing a release-signed one over it needs that one uninstalled first.
  - Windows, through [SignPath Foundation](https://signpath.org)'s free signing for open source (its terms: [signpath.org/terms](https://signpath.org/terms.html)): once the project is accepted, in SignPath.io, the GitHub.com trusted build system linked to the project `pikibun` (and the SignPath GitHub App installed on the repository), the signing policy `release-signing` with origin verification for the `app-v` tags, and the artifact configuration `windows-installer` from [`.github/signpath/windows-installer.xml`](../.github/signpath/windows-installer.xml). Then the secret `SIGNPATH_API_TOKEN` (the API token of a SignPath user with the submitter role on that policy) and the variable `SIGNPATH_ORGANIZATION_ID`; the variables `SIGNPATH_PROJECT_SLUG`, `SIGNPATH_SIGNING_POLICY_SLUG` and `SIGNPATH_ARTIFACT_CONFIGURATION_SLUG` name other slugs. Each release's signing request waits, up to four hours, for an approver to approve it in SignPath. Only the installer is signed: `Pikibun.exe` is Native Shell's prebuilt runner, and SignPath Foundation's certificate signs only binaries built from this repository. The release notes then carry the [code signing policy](../README.md#code-signing-policy) SignPath Foundation requires. SmartScreen may still warn about the first downloads until the signature builds a reputation.

## Layout

- `apps/server`: the control plane (Hono on Node); `src/local` runs it on one person's own computer (`pikibun serve`). `src/authority` is the [authority](design/authority.md), which the rest of the server uses only through `src/authority/index.ts`. It holds who people and hosts are (`auth.ts` for GitHub and session sign-in, `password-auth.ts` for password accounts, `admin.ts` for the server administration API, `hosts.ts`), who may do what (`access.ts`, `host-access.ts`, `runner-access.ts`, `authorize.ts`), approvals, the credentials (`git/` for the Git providers and accounts, `push/` for push identities and credentials, `network.ts`, `api-access.ts`, `github-broker.ts`, `sources/`) and the audit log. `src/password-accounts-cli.ts` provides `--create-admin` and `--reset-password`; `src/db` holds the database providers and the SQLite→Postgres dialect translation; `src/storage` the backup storage providers; `src/workspace-databases` the owner-connected session databases; `src/data-export.ts` the session and workspace exports; `src/connector-hub.ts` the WebSocket relay to connected hosts.
- `apps/nsh`: the client for the web, phones, tablets and desktops on [Native Shell](https://nsh.dev). `pnpm build:client` builds it into `dist/client`, which `pikibun.com` serves (see [the web client](self-hosting.md#the-web-client)). See [its README](../apps/nsh/README.md) for `pnpm dev:client`, `pnpm test:client`, `pnpm test:client-live` and `pnpm test:client-web`; `scripts/nsh.mjs` fetches the pinned CLI they use.
- `apps/runner`: the connector runtime that runs on each host, published as the `pikibun` CLI from `packages/cli` (with the server, for `pikibun serve`).
- `packages/shared`: types and policy shared by all of the above. `packages/client`: the API client, live session updates and chat-option rules the client uses.
- `docs/design`: design notes, such as the [repository cache](design/repository-cache.md).
