# Development

Requires Node 24 and pnpm.

```sh
pnpm install
cp apps/server/.env.example apps/server/.env   # see below
pnpm dev:server                                 # API on :8787
pnpm dev                                        # web UI on :5173, proxying /api to :8787
```

For local development, set in `apps/server/.env`: `APP_ORIGIN=http://localhost:5173`, `DATABASE_URL=sqlite:./data/dev.sqlite` (the default `/data` path is the container's), `SESSION_SECRET`, `VAULT_KEY`, and the test mode that allows plain HTTP on localhost: `TEST_AUTH_ENABLED=true`, a `TEST_AUTH_SECRET` of at least 32 characters and a future `TEST_AUTH_EXPIRES_AT` (such as `2030-01-01T00:00:00Z`). Sign in with a GitHub OAuth app whose callback is `http://localhost:5173/api/auth/github/callback`, or as a test user by running this in the browser console on `http://localhost:5173`, then reloading:

```js
await fetch("/api/auth/test", { method: "POST", headers: { Authorization: "Bearer YOUR_TEST_AUTH_SECRET", "Content-Type": "application/json" }, body: JSON.stringify({ displayName: "Dev" }) });
```

- `pnpm typecheck` (also typechecks the apps), `pnpm test` (set `TEST_DATABASE_URL=postgres://…` to also run the provider suite against Postgres), `pnpm build` (production React web app and NSH preview), `pnpm build:web` (React only), `pnpm build:preview` (NSH only), `pnpm build:server` (bundled server in `dist/server`), `pnpm build:cli` (the connector package).
- The sandbox's Python programs are `.py` files in `apps/runner/src/sandbox-python` (the helper every sandboxed step of the Linux and macOS sandboxes runs, and the `git` shim). The connector embeds them through `apps/runner/src/sandbox-python.generated.ts`: after changing one, run `pnpm python:embed` (`tests/sandbox-python.test.ts` fails while it is out of date). `pnpm python:check` lints them with Ruff and type-checks them with Pyright, both from npm, for Python 3.9 (macOS's own `python3`). `tests/sandbox-conformance.test.ts` holds every implementation of a session's files (those two helpers, the Windows sandbox's Node helper and the unsandboxed host's TypeScript) to one table of cases: a new file operation, or a fix to one, adds its cases there.
- `pnpm connect …` runs the connector from source, with the same options as `pikibun connect`; add `--allow-insecure-loopback` to pair with a local `http://` server.
- `pnpm test:connected` runs the end-to-end suite against a real server and connector (Linux with bubblewrap).
- `pnpm dev:native [--port 8787] [--no-host] [--pairing]` runs a local test-mode server for developing the apps: a test user with an app token, a workspace and, unless `--no-host`, this machine as a host offering the deterministic fixture model (not an LLM) with one session. `--pairing` adds a pairing code for the desktop app. It writes what the apps need to `.local/dev-native.json`; Ctrl-C stops it and deletes its data.
- Releasing: each part has its own release line and version, started by pushing its tag on a commit in `main` (e.g. `git tag server-v1.4.0 && git push origin server-v1.4.0`). A suffix such as `-beta.1` makes a prerelease. Nothing needs committing first: each workflow checks the tag is on `main`, runs CI and sets the tag's version in the package it builds (`scripts/set-release-version.mjs`), so the committed versions need not match.

  | Tag | Workflow | Publishes |
  | --- | --- | --- |
  | `cli-v1.2.3` | `release.yml` | `pikibun` on npm, with provenance; a prerelease goes to the `next` dist-tag |
  | `server-v1.2.3` | `release-server.yml` | The server image (web app and backend) to `ghcr.io/opencara/pikibun`, then deploys a release (not a prerelease) to the deployment server once the image is pushed; no GitHub release |
  | `desktop-v1.2.3` | `release-desktop.yml` | Production Electron desktop app: macOS arm64 DMG and Windows x64 installer |
  | `app-v1.2.3` | `release-app.yml` | The experimental NSH client on a preview GitHub release: a Windows installer and portable zip (x64), the macOS app (arm64), Linux (x86_64 `.tar.gz`) and Android (`.apk`); iOS to TestFlight |

  The desktop line creates the stable GitHub release (latest); NSH's app line creates prereleases and never replaces it as latest. Both generate notes since their own previous tag. The apps' version is the tag's without a prerelease suffix, and their build number is the run's. Pull requests that change how the app is packaged (`release-app.yml`, `apps/nsh/nsh.json`, its icon, `apps/nsh/windows/`, `scripts/nsh.mjs`) build every platform unsigned, and the Windows job installs and uninstalls its installer to test it. npm needs either a trusted publisher on npmjs.com for `OpenCara/pikibun`, workflow `release.yml` (keep that file name), environment `release`, or an `NPM_TOKEN` repository secret.
- Deploying the server: once a `server-v` release's image is on GHCR, `deploy-server.yml` joins the tailnet as an ephemeral, tagged node, connects to the deployment server over Tailscale SSH and runs [`scripts/deploy-server.sh`](../scripts/deploy-server.sh) there. It pulls the image by digest, writes it to `PIKIBUN_IMAGE` in the deploy directory's `.env`, recreates the `pikibun` service with `docker compose up -d --no-build` and waits for the container to report healthy. Both production React and NSH preview are in that same image. When `DEPLOY_PREVIEW_URL` is configured, the script also writes it to the server's `PREVIEW_ORIGIN`. Actions then checks both public clients, their startup assets and CSPs, and each API's release version; a healthy backend serving the wrong client does not pass. Prereleases are not deployed; **Actions → Deploy server → Run workflow** deploys any published version, to redeploy or go back to one. A failed deploy is not rolled back by itself: migrations ran when the new container started, so go back only to a version that reads the migrated database. Configure it in the `production` environment, and add required reviewers there to approve each deploy; without the settings nothing is deployed:
  - Variables `DEPLOY_HOST` (the server's tailnet name, such as `nerd.tail7e2cef.ts.net`), `DEPLOY_USER` (in the `docker` group), and optionally `DEPLOY_PORT` (22), `DEPLOY_PATH` (the directory with `docker-compose.yml` and `.env`, `pikibun` from the user's home by default), `DEPLOY_URL` (the production public origin), `DEPLOY_PREVIEW_URL` (the optional NSH preview origin, `https://preview.pikibun.com` for this deployment) and `TS_TAGS` (`tag:ci` by default).
  - Secrets `TS_OAUTH_CLIENT_ID` and `TS_OAUTH_SECRET` (a Tailscale OAuth client, **Settings → OAuth clients**, with the **Auth Keys** write scope and the tags in `TS_TAGS`) and `DEPLOY_SSH_KNOWN_HOSTS` (the server's Tailscale SSH host keys, `ssh-keyscan -p PORT HOST` from a tailnet device, checked against the server's own fingerprints).
  - In the tailnet policy: `TS_TAGS` owned in `tagOwners`, the server tagged too (Tailscale SSH doesn't let tagged devices into user-owned ones), and an `ssh` rule with `"action": "accept"` from `TS_TAGS` to the server's tag for `DEPLOY_USER`, plus an access rule or grant to its port 22. No SSH key is needed: Tailscale SSH admits the runner by its tag.
  - Preview DNS and tunnel/proxy routing must already point to the same listener as production; see [preview setup](self-hosting.md#native-shell-preview). Deploying a stable `server-v` tag updates both hosts together; this does not require separate preview or desktop release tags.
  - The server's `docker-compose.yml` runs `image: ${PIKIBUN_IMAGE:-pikibun}`, as this repository's does, and the user can pull from `ghcr.io/opencara/pikibun` (public, or after `docker login ghcr.io`).
- Signing the `app-v` release: the secrets and variables below live in the `release` environment, each platform's all or nothing. Without them, the macOS app is released ad hoc signed (Gatekeeper blocks it on other Macs until it's opened with right-click › Open), the APK carries Android's debug key, the iOS job only checks that the app packages, and the Windows installer is unsigned.
  - An App Store Connect API key (Users and Access › Integrations; the App Manager role is enough), shared by macOS (notarization) and iOS: `APP_STORE_CONNECT_API_KEY` (the `.p8` file's contents), `APP_STORE_CONNECT_API_KEY_ID` and `APP_STORE_CONNECT_API_ISSUER_ID`.
  - macOS, signed with Developer ID and the hardened runtime, notarized and stapled: `MAC_CERTIFICATE_P12` (a **Developer ID Application** certificate and its key, exported as `.p12`, base64: `base64 -i cert.p12`), `MAC_CERTIFICATE_PASSWORD`, and the variable `MAC_SIGNING_IDENTITY`, the certificate's name without its `Developer ID Application:` prefix (e.g. `OpenCara (TEAMID)`).
  - iOS, uploaded to TestFlight: an app record for the bundle ID `com.pikibun.app` (the client's `id` in `apps/nsh/nsh.json`) in App Store Connect, `IOS_CERTIFICATE_P12` (an **Apple Distribution** certificate as base64 `.p12`) with `IOS_CERTIFICATE_PASSWORD`, and `IOS_PROVISIONING_PROFILE` (an App Store provisioning profile for `com.pikibun.app`, base64). Every `app-v` tag goes to TestFlight; submitting a build for App Store review stays manual. App Store Connect takes a version's builds only in increasing build numbers, and this workflow's run numbers started again from 1: the first `app-v` version must be above any version uploaded before.
  - Android: `ANDROID_KEYSTORE` (a release keystore, base64; `keytool -genkeypair -keystore release.jks -alias upload -keyalg RSA -keysize 2048 -validity 10000`), `ANDROID_KEYSTORE_PASSWORD` and `ANDROID_KEY_ALIAS`. Keep the keystore: every later APK must be signed with it to update an installed one.
  - Windows: `WIN_CERTIFICATE_P12` (a code-signing certificate and its key as base64 `.p12`) and `WIN_CERTIFICATE_PASSWORD` sign `Pikibun.exe` and the installer. Without them SmartScreen warns before the first launch (**More info → Run anyway**).

## Layout

- `apps/server`: the control plane (Hono on Node); `src/local` runs it on one person's own computer (`pikibun serve` and the desktop app). `src/authority` is the [authority](design/authority.md), which the rest of the server uses only through `src/authority/index.ts`. It holds who people and hosts are (`auth.ts` for GitHub and session sign-in, `password-auth.ts` for password accounts, `admin.ts` for the server administration API, `hosts.ts`), who may do what (`access.ts`, `host-access.ts`, `runner-access.ts`, `authorize.ts`), approvals, the credentials (`git/` for the Git providers and accounts, `push/` for push identities and credentials, `network.ts`, `api-access.ts`, `github-broker.ts`, `sources/`) and the audit log. `src/password-accounts-cli.ts` provides `--create-admin` and `--reset-password`; `src/db` holds the database providers and the SQLite→Postgres dialect translation; `src/storage` the backup storage providers; `src/workspace-databases` the owner-connected session databases; `src/data-export.ts` the session and workspace exports; `src/connector-hub.ts` the WebSocket relay to connected hosts.
- `apps/web`: the production React web client at `pikibun.com`, built by `pnpm build:web` into `dist/web`.
- `apps/desktop`: the production Electron app, showing the React web client and running this computer's connector and optional local server. `pnpm --filter @pikibun/desktop dev` builds and opens it; `desktop-v` tags release it.
- `apps/nsh`: the experimental client for the web, phones, tablets and desktops on [Native Shell](https://nsh.dev). `pnpm build:preview` builds it into `dist/preview`, served only at the configured `PREVIEW_ORIGIN` (`https://preview.pikibun.com` in production). See [its README](../apps/nsh/README.md) for `pnpm dev:preview`, `pnpm test:client`, `pnpm test:client-live` and `pnpm test:client-web`; `scripts/nsh.mjs` fetches the pinned CLI they use.
- `apps/runner`: the connector runtime that runs on each host, published as the `pikibun` CLI from `packages/cli` (with the server, for `pikibun serve`).
- `packages/shared`: types and policy shared by all of the above. `packages/client`: the API client, live session updates and chat-option rules shared by the web and the apps.
- `docs/design`: design notes, such as the [repository cache](design/repository-cache.md).
