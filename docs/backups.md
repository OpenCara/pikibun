# Backups, restores and moving sessions

## Backups, restores and exports

A session's conversation and files live on its host. A backup copies them to the server's backup storage (`STORAGE_URL`) or, when the workspace owner has connected one, to the workspace's [session database](self-hosting.md#workspace-session-databases). A server with neither keeps no backups.

- Only the session owner can create, download or restore backups, from **Details → Backups** or the session menu (**Create backup**), and only while the session is idle. Listing and downloading work while the host is offline.
- A backup holds the session's conversation, its files and the owner's personal environment values, so whoever can read the backup store can read them. It leaves out package managers' caches and temporary files in the session's home folder (`.cache`, `.npm`, `.pnpm-store`, `.yarn`, `.bun`, `.local/share/pnpm`, `.cargo/registry` and `.cargo/git`, `go/pkg/mod`, `.m2/repository`, `.gradle/caches`, `.nuget/packages` and `.tmp`): a restored or moved session downloads them again when it next installs. Hosts with an older connector keep them. When backups go to a database another member connected, you confirm that database before each backup.
- In a session that clones on demand, a backup keeps each clone's **local work** rather than the clone itself: its branches, which branch is checked out, commits its `origin` doesn't have, and its uncommitted changes and untracked files (ignored files aren't kept). The restored session clones each repository again through its egress proxy, with the session owner's access, before its work resumes, and puts that work back: the same branch checked out, the changes uncommitted again. A clone that can't be cloned again (for example, its repository was removed from the workspace) is retried when the session next opens, and the agent is told where its work is kept meanwhile. Clones of repositories outside the workspace keep only their local work too, and can't be restored automatically.
- **Conversation only** (next to **Create backup**, or **Back up conversation only** in the session menu; `POST /api/sessions/:id/backup` with `conversationOnly: true`) keeps just the session's conversation and its state: Pi's database, its runs and the record of what its tools ran. The session's files and its clones' local work aren't kept, so the backup is much smaller, and a session restored from it starts with an empty worktree. Its agent is told that the files and clones its earlier messages mention weren't restored, so it clones what it needs again (a later restore from a full backup drops that note). Work that isn't pushed is lost in such a restore. These backups are marked **Conversation only** in the backup list, and as `conversationOnly: true` in the `backup.created` activity and the session export. They need a current connector on the session's host (`conversationBackups` capability). Automatic backups are always full backups.
- **Some sessions can't be backed up in full**, and the host says why: a backup holds at most 24 MiB, its conversation and files together (encoded, so somewhat less of the files themselves), and at most 10,000 files outside the session's clones, with no symlinks, special files or hardlinked files among them. The clones' local work that their origins don't have counts toward the 24 MiB (push it to keep the backup small), and so does the rest of the session's home folder. Nothing changes then: remove the files you don't need, or back up the conversation only. Until the session fits, its automatic backups fail and are retried every 15 minutes, and it can't move to another host either.
- **Restore into new private session** creates a new private session from a backup, optionally with a **New session title**, and never overwrites the source. It doesn't run any operation again, and it needs the original host to be available. Retrying reuses the same request, so it opens the same restored session instead of creating another.

Exports are JSON records without secrets; a session's conversation is in its backups:

- Session owners export a session (details, people, pushes, backup list and activity) under **Details → Export**.
- Workspace owners and admins export a workspace (settings, members, models, published agents, repositories, push access, its session database connection and activity, with their own sessions in full and the records of every other session there, which they manage) under **Settings → Workspaces → Data export**. The rest of another member's session (its people, approvals, pushes and activity) is in its owner's export of it.

## Packing archived sessions

A session's files stay on its host when it is archived: clones, dependencies such as `node_modules`, and caches in its home folder, often tens of thousands of files. To save the host's disk, and its inodes above all, an archived session's files are packed into one compressed file on the host. The session shows **Files packed**.

- **Automatically, a week after archiving.** Every few minutes the server asks the hosts of sessions archived 7 days ago or more to pack them, as each session's owner would. Sessions archived before this arrived got their week from when it did. A host that is offline is asked once it is back; one that is busy, an hour later; one whose connector is too old to keep the clones' ignored files (below, `packIgnoredFiles` capability), once it is updated. A session the host refuses to pack (below) is left as it is for good, audited as `session.pack_refused` with the reason. Unarchiving calls it off, and archiving again starts a new week. A workspace's owners and admins turn this off under **Settings → Workspaces →** the workspace **→ Archived sessions** (`PUT /api/workspaces/:id/packing` with `{"automatic": false}`); its archived sessions are then packed only by their owners. Why it works this way is in the [design note](design/automatic-packing.md).
- **Sooner, by its owner**: session menu → **Pack files**, or `POST /api/sessions/:id/pack`.
- **What a pack keeps** is what a full [backup](#backups-restores-and-exports) keeps, without its conversation, which stays on the host as it is: each clone's local work (its branches, commits its `origin` doesn't have, and its uncommitted changes and untracked files), and the session's other files. Unlike a backup, it also keeps the files a clone's `.gitignore` ignores, such as `.env` files and local databases, up to 16 MiB and 5,000 files a clone, except dependencies and build output, which installing and building again bring back: anything in a directory named `node_modules`, `bower_components`, `.pnpm-store`, `.yarn`, `.venv`, `venv`, `__pycache__`, `.pytest_cache`, `.mypy_cache`, `.ruff_cache`, `.tox`, `.nox`, `.gradle`, `target`, `dist`, `build`, `out`, `.next`, `.nuxt`, `.svelte-kit`, `.turbo`, `.parcel-cache`, `.cache`, `coverage` or `.nyc_output`, and `*.pyc`, `*.pyo`, `*.log` and `*.tsbuildinfo` files (`PACK_REBUILDABLE_DIRS` in `apps/runner/src/sandbox-python/helper.py`). Hosts with an older connector leave out every ignored file. Like a backup, a pack leaves out package managers' caches and temporary files in the session's home folder. Install dependencies again when you need them.
- **Unarchiving unpacks it first**: the host writes the files back, the session is unarchived, and its host opens it again, now with network access, so its clones are cloned again through its egress proxy, with its owner's access, before its work resumes, as after a restore. Reflogs and tags created locally on pushed commits aren't kept. Whoever unarchives it (its owner, or the workspace's owner or an admin), the host unpacks and reopens it as its owner, and it must be online.
- **Some sessions can't be packed**, and the host says why: one with more than 10,000 files outside its clones, or more than 24 MiB, the limits of a backup; one with symlinks or special files outside its clones; one with a clone a pack couldn't bring back in full, since packing deletes the original: stashed changes (`git stash`), refs other than branches and tags (notes, say), tags on commits its origin doesn't have (push them first), ignored files beyond what a pack keeps of them, or a Git repository among its ignored files deeper than clones are looked for; one whose clones borrow from the host's [repository cache](hosts.md#repository-cache-preview), which an archived session can't read, so sessions on a cache host can't be packed yet; one that runs directly on its host or on a host without the sandbox; a session on macOS or native Windows, or on a host started with `--resources` (each session has its own volume there, so packing would free nothing); and one that is still working. Nothing changes then.
- A pack is written in full before the session's files go, and unpacked files are written in full before the pack goes, so a host that stops halfway keeps one or the other. If the server doesn't hear back from the host, the session still shows as packed, and unarchiving unpacks whatever the host packed.
- Packing needs a current connector on the session's host (`sessionPacking` capability). Packing and unpacking are audited as `session.packed` (with `automatic: true` when the server asked) and `session.unpacked`; turning automatic packing on or off as `workspace.packing.updated`.

## Moving a session to another host

While both hosts are connected, a session's owner can move it to a model on another host in its workspace (session panel → **Move to another host**, or `POST /api/sessions/:id/migrate` with `requestId` and `modelId`). The source host's live snapshot, the same one a backup takes, goes straight to the new host, so no `STORAGE_URL` is needed:

- The new host restores it into a new session with the same conversation, files, repository pins, visibility and title (or a new title), running that host's model. Its agent keeps the original's tools that the new host can carry. Session grants aren't copied.
- Once the new host confirms, the original session is archived: its history stays readable and its owner can unarchive it.
- A session that clones on demand moves as its backups restore: each clone is cloned again on the new host and its local work put back. It needs a sandboxed new host with a current connector (`cloneBackups` capability).
- The session must be idle. Until the move finishes, both sessions only accept reads, so nothing sent after the snapshot is lost. The control plane holds the snapshot until then; retrying with the same `requestId` needs only the new host, and `POST /api/sessions/:id/migrations/:migrationId/cancel` gives up on the move, archiving the unfinished copy.
- Moving to a host someone else owns needs `trustedConnectorId`, as starting a session there does. The new host must run a current connector on Linux (`hostMigration` capability).
