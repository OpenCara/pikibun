# Models and tools

You can use the models of your own hosts and of hosts shared with the workspace, except those the host's owner or an admin [disabled](hosts.md#models). A session starts from a host and one of its models, and its agent gets every tool that host supports and its workspace has, with no extra instructions. The access you choose for each message (see [Chat options](sessions.md#chat-options)) decides what runs without asking.

The tools an agent can use:

| Tool | What it does | Needs |
|---|---|---|
| `identity` | Tells the agent the session owner's identity and `APP_` environment | Nothing |
| `list_files`, `read_file` | List and read session files; images (PNG, JPEG, GIF, WebP) go to the model as images. `read_file` with `offset` and `limit` reads only those lines of a text file | Nothing |
| `search` | Search the worktree's text files for a regular expression or literal text, like `grep -rn`: narrowed by `path` and `glob`, with up to 5 lines of `context` and up to 500 results. It never follows links, skips `.git` directories as it walks (a `path` inside `.git` reads it, as `read_file` can), skips `node_modules` unless `all` is set, and skips binary files and files over 1 MB | Nothing |
| `write_file`, `edit_file` | Write a whole file, or replace exact text in place | Refused in **Read only** messages |
| `move_file`, `copy_file`, `delete_file` | Move or rename, copy, or delete a file, directory or link in the worktree, as `mv`, `cp -r` and `rm` would, without a shell. A link is moved, copied or deleted itself, never what it points to; a destination is never replaced and a directory never goes inside itself; a non-empty directory is deleted only with `recursive`. A copy makes at most 10,000 entries and 50 MB of files. None of them touches `.git` or copies a repository's `.git` (clone it again); deleting a clone's directory deletes its `.git` with it | Refused in **Read only** messages |
| `git` | Run Git in the sandbox without a shell: its arguments as a list (`["commit", "-m", "Fix it"]`) and the clone's `directory`. Only version-control subcommands (clone, status, diff, log, commit, switch, fetch, merge, rebase, push, ...), and none of the options that run another program (`rebase --exec`, `clone --upload-pack` or `--config`, `--template`, Git's own `-c` and `-C`). Its record shows the exact Git command. It comes with [`piki:git`](extensions.md#session-tools), which a workspace gets with its first repository | Refused in **Read only** messages |
| `node` | Run Node.js or a package manager in the sandbox without a shell: `program` (`node`, `npm`, `npx`, `pnpm`, `yarn` or `corepack`), its arguments as a list (`["test"]`) and the clone's `directory`. It runs the connector's own Node.js (24 or newer) where the sandbox can be given it (Linux and macOS, with the CLI connector), otherwise the one on the commands' PATH, with no colours or prompts, and none of the commands that act on a package registry as an account (`publish`, `login`, `token`, `owner`, ...). It comes with [`piki:node`](extensions.md#session-tools), which a workspace adds | Refused in **Read only** messages |
| `python` | Run Python or its package and test tools in the sandbox without a shell: `program` (`python3`, `pip`, `pip3`, `uv`, `uvx`, `poetry` or `pytest`), its arguments as a list (`["-m", "pytest", "-q"]`), the clone's `directory`, and optionally `venv`, a virtual environment there (`.venv`) whose programs it runs first. No colours or prompts, and none of the commands that act on a package index as an account (`uv publish`, `poetry publish`, `twine upload`, `poetry config` of credentials). It comes with [`piki:python`](extensions.md#session-tools), which a workspace adds | Refused in **Read only** messages |
| `rust`, `go`, `dotnet` | Run Rust's, Go's or .NET's programs in the sandbox without a shell: `program` (`cargo`, `rustc`, `rustup` or `rustfmt`; `go` or `gofmt`; `dotnet`), its arguments as a list (`["test"]`) and the clone's `directory`. Commands that act on a package registry as an account (`cargo publish`, `login`, `owner`, `yank`, `dotnet nuget push` and `delete`, a NuGet source's password) are refused. Each ecosystem must be installed where the sandbox sees it, such as distribution packages or a system-wide rustup in `/usr/local` ([details](extensions.md#session-tools)). Each comes with [`piki:rust`, `piki:go` or `piki:dotnet`](extensions.md#session-tools), which a workspace adds | Refused in **Read only** messages |
| `make` | Run make in the sandbox without a shell of its own: its arguments as a list (`["test"]`) and the clone's `directory`. A Makefile's recipes are shell commands, which the call's `make` stands for, as `npm test` does for a package's scripts. It comes with [`piki:make`](extensions.md#session-tools), which a workspace adds | Refused in **Read only** messages |
| `browser` | Drive a headless Chromium in the sandbox: open a page, run actions (click, type, press, select, scroll, wait, evaluate JavaScript, screenshot), and get back its screenshot, text, interactive elements, console messages and failed requests; `serve` starts the web app under test for the call: one of the `node` and `python` tools' programs, without a shell. Each call's screenshots show in the session panel's **Browser** tab. Runs only in the Linux sandbox, with Chromium the host's owner set up (found, at a path, or downloaded); it comes with [`piki:browser`](extensions.md#the-browser-pikibrowser), which a workspace adds | Refused in **Read only** messages |
| `tunnel` | Put the web server the agent works on online at an `https://` address through a Cloudflare quick tunnel, opened only through its link unless `access: "public"`: `start` runs `serve` (one of the `node` and `python` tools' programs, without a shell) in the sandbox as a service that keeps running after the call, `status` gives the address and the server's last output, `stop` takes it offline. Runs only in the Linux sandbox, with cloudflared the host's owner set up; it comes with [`piki:tunnel`](extensions.md#the-tunnel-pikitunnel), which a workspace adds | Each `start`: only for the host's owner and members they granted host commands; refused in **Read only** messages |
| `git_push` | Push a clone's checked-out commit to a branch, optionally opening a pull request, or tag a commit already on a branch; it comes with [`piki:git`](extensions.md#session-tools) | Refused in **Read only** messages |
| `github_read` | Read a GitHub issue or pull request. With `wait`, read it again every 30 seconds until something happens, instead of sleeping in a shell: `"checks"` until every check of the head commit has completed (or the pull request is closed, or its head has had no checks for 2 minutes), `"change"` until a comment, review, review comment, push, check or its state changes. It waits up to `timeout_seconds` (600 by default, at most 1800), and its result's `waited` says how the wait ended. Each read counts against the session owner's GitHub rate limit, so where the session also has `gh`, the agent reads and waits for checks with `gh` and keeps this for `"change"` ([GitHub](github.md)); it comes with [`piki:github`](extensions.md#session-tools), which a workspace gets with its first GitHub repository | Nothing, during a shared message |
| `github_comment` | Comment on a GitHub issue or pull request (`github_comment`, `github_issue` and `github_merge` go with `github_read`, under [`piki:github`](extensions.md#session-tools)) | Refused in **Read only** messages |
| `github_merge` | Merge a GitHub pull request | Refused in **Read only** messages |
| `github_issue` | Open a GitHub issue | Refused in **Read only** messages |
| `source_read` | Read an item of one of the workspace's [document sources](repositories.md#document-sources), with the session owner's connection; it reads a kind of source while the workspace has that kind's extension ([`piki:notion`, `piki:google-drive`, ...](extensions.md#session-tools)), which comes with its first source of that kind | Nothing, during a shared message |
| `schedule` | List, create, change or delete the session's [scheduled prompts](sessions.md#scheduled-prompts); it comes with [`piki:schedule`](extensions.md#session-tools), which a workspace adds | A message from the session owner; refused in **Read only** messages for changes |
| `sessions` | List, read, message, start, stop and archive the workspace's other sessions, as the message's sender (see [Working across sessions](sessions.md#working-across-sessions)); it comes with [`piki:sessions`](extensions.md#session-tools), which a workspace adds | A shared message; refused in **Read only** messages for changes, and to pass content between sessions whose readers differ unless the session's owner allows it |
| Extension tools | Whatever the workspace's [extensions](extensions.md) offer, run on the host outside the sandbox | A message of the host's owner, or of a member they [granted host commands](hosts.md#host-admins-and-host-command-grants), in a session of theirs; anyone's where the host's owner lets every session run extension tools. Never in **Read only** messages |

A workspace's page lists the tools its sessions can use, with what each does and where it comes from, under **Settings → Workspaces →** the workspace **→ Extensions → Tools sessions can use** (see [Extensions](extensions.md)).

There is no shell tool: `bash` and `host_bash` were removed (#163). Sessions run Git, Node.js and Python with their own tools, move, copy and delete with the file tools, and chain tools with code mode. Saved agents, and past records, that name them stay readable.

Nothing waits for anyone's approval: a call runs, or is refused with its reason. Whatever a message's access, a session runs only the tools of its owner's [tool group](workspaces.md#tool-groups); see [What a session may do](approvals.md). Side asks offer only the read-only tools.

Sessions started from a saved agent, before agents were removed, keep that agent's instructions and tools; any other tool they call runs as the session's other tools do.
