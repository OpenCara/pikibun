# Models and tools

You can use the models of your own hosts and of hosts shared with the workspace, except those the host's owner or an admin [disabled](hosts.md#models). A session starts from a host and one of its models, and its agent gets every tool that host supports and its workspace has, with no extra instructions. The access you choose for each message (see [Chat options](sessions.md#chat-options)) decides what runs without asking.

The tools an agent can use:

| Tool | What it does | Needs |
|---|---|---|
| `identity` | Tells the agent the session owner's identity and `APP_` environment | Nothing |
| `ls`, `read` | List and read session files, with the names, parameters and answers of Pi's own `ls` and `read` ([Pi's names and contracts](design/pi-tool-names.md)). `ls` gives one entry a line, `/` after a directory, 500 unless `limit`; links are listed as they are, never followed. `read` gives a text file as it is, cut at 2,000 lines or 50 KB with a note that says where to continue, and `offset` and `limit` read only those lines; images (PNG, JPEG, GIF, WebP) go to the model as images. A code mode script's `read` gets the whole selection, uncut. They were `list_files` and `read_file` before | Nothing |
| `grep` | Search the worktree's text files for a regular expression or literal text, like `grep -rn`, with the name, parameters and answers of Pi's own `grep`: narrowed by `path` and by `glob` (from `path`; one without `/` matches file names at any depth), `ignoreCase`, up to 5 lines of `context` and up to 500 matches (`limit`, 100 by default). Each match is `path:line: text`, each context line `path-line- text`, paths from where it searched. It never follows links, skips `.git` directories as it walks (a `path` inside `.git` reads it, as `read` can), skips `node_modules` unless `all` is set, and skips binary files and files over 1 MB; it doesn't read `.gitignore`. It was `search` before | Nothing |
| `find` | Find files and directories by glob, without a shell, with the name, parameters and answers of Pi's own `find`: a pattern without `/` matches names at any depth (`*.ts`, `*.{ts,tsx}`), one with `/` matches paths below `path` (`src/**/*.spec.ts`), and an all-lowercase pattern matches either case. One path a line, from `path`, with `/` after a directory; 1,000 unless `limit`, at most 5,000. It skips `.git` directories, and `node_modules` unless `all` is set; links are listed, never followed, and it doesn't read `.gitignore`. A tool group that has **Search files** has it too | Nothing |
| `write`, `edit` | Write a whole file, or replace text in place, as Pi's own `write` and `edit` do: `edit` runs Pi's own edit, which keeps the file's line endings and byte order mark, tries again ignoring trailing whitespace and quote and dash styles when the exact text isn't found, and answers with the diff. They were `write_file` and `edit_file` before | Refused in **Read only** messages |
| `move_file`, `copy_file`, `delete_file` | Move or rename, copy, or delete a file, directory or link in the worktree, as `mv`, `cp -r` and `rm` would, without a shell. A link is moved, copied or deleted itself, never what it points to; a destination is never replaced and a directory never goes inside itself; a non-empty directory is deleted only with `recursive`. A copy makes at most 10,000 entries and 50 MB of files. None of them touches `.git` or copies a repository's `.git` (clone it again); deleting a clone's directory deletes its `.git` with it | Refused in **Read only** messages |
| `show_image` | Show an image to the people in the chat: `path` is a PNG, JPEG, GIF or WebP file in the worktree, fitted to the conversation model's image limits as `read`'s images are. It shows beside the agent's message in the transcript, not folded into its tool row, and the model sees it too. To only show a worktree image, video or audio file, the agent writes it in its reply as Markdown instead, `![caption](out/demo.mp4)` (see [Images, videos and audio in the chat](sessions.md#images-videos-and-audio-in-the-chat)); an image from an `https` link may not load, so it downloads one into the worktree first. It goes with `read`: a [tool group](workspaces.md#tool-groups) without `read` has no `show_image` either | Allowed in **Read only** messages and side questions |
| `git` | Run Git in the sandbox without a shell: its arguments as a list (`["commit", "-m", "Fix it"]`) and the clone's `directory`. Only version-control subcommands (clone, status, diff, log, commit, switch, fetch, merge, rebase, push, ...), and none of the options that run another program (`rebase --exec`, `clone --upload-pack` or `--config`, `--template`, Git's own `-c` and `-C`). Its record shows the exact Git command. It comes with [`piki:git`](extensions.md#session-tools), which a workspace gets with its first repository | Refused in **Read only** messages |
| `node` | Run Node.js or a package manager in the sandbox without a shell: `program` (`node`, `npm`, `npx`, `pnpm`, `yarn` or `corepack`), its arguments as a list (`["test"]`), the clone's `directory` and, optionally, `env`, environment variables for the program (not `PATH` or `LD_`/`DYLD_` ones). It runs the connector's own Node.js (24 or newer) where the sandbox can be given it (Linux and macOS, with the CLI connector), otherwise the one on the commands' PATH, with no colours or prompts, and, in the sandbox, none of the commands that act on a package registry as an account (`publish`, `login`, `token`, `owner`, ...): those run only on the host's own machine, with its user's sign-in, for the host's owner and members they granted host commands. It comes with [`piki:node`](extensions.md#session-tools), which a workspace adds | Refused in **Read only** messages |
| `python` | Run Python or its package and test tools in the sandbox without a shell: `program` (`python3`, `pip`, `pip3`, `uv`, `uvx`, `poetry` or `pytest`), its arguments as a list (`["-m", "pytest", "-q"]`), the clone's `directory`, and optionally `venv`, a virtual environment there (`.venv`) whose programs it runs first. No colours or prompts, and, in the sandbox, none of the commands that act on a package index as an account (`uv publish`, `poetry publish`, `twine upload`, `poetry config` of credentials), which run only on the host's own machine as `node`'s do. It comes with [`piki:python`](extensions.md#session-tools), which a workspace adds | Refused in **Read only** messages |
| `rust`, `go`, `dotnet` | Run Rust's, Go's or .NET's programs in the sandbox without a shell: `program` (`cargo`, `rustc`, `rustup` or `rustfmt`; `go` or `gofmt`; `dotnet`), its arguments as a list (`["test"]`) and the clone's `directory`. Commands that act on a package registry as an account (`cargo publish`, `login`, `owner`, `yank`, `dotnet nuget push` and `delete`, a NuGet source's password) are refused in the sandbox, and run only on the host's own machine as `node`'s do. Each ecosystem must be installed where the sandbox sees it, such as distribution packages or a system-wide rustup in `/usr/local` ([details](extensions.md#session-tools)). Each comes with [`piki:rust`, `piki:go` or `piki:dotnet`](extensions.md#session-tools), which a workspace adds | Refused in **Read only** messages |
| `make` | Run make in the sandbox without a shell of its own: its arguments as a list (`["test"]`) and the clone's `directory`. A Makefile's recipes are shell commands, which the call's `make` stands for, as `npm test` does for a package's scripts. It comes with [`piki:make`](extensions.md#session-tools), which a workspace adds | Refused in **Read only** messages |
| `browser` | Drive a headless Chromium in the sandbox: open a page, run actions (click, type, press, select, scroll, wait, evaluate JavaScript, screenshot), and get back its screenshot, text, interactive elements, console messages and failed requests; `serve` starts the web app under test for the call: one of the `node` and `python` tools' programs, without a shell, or with `desktop` an app with no web page on a [desktop](extensions.md#desktops-for-apps-without-a-web-page). Each call's screenshots show in the session panel's **Browser** tab. Runs only in the Linux sandbox, with Chromium the host's owner set up (found, at a path, or downloaded); it comes with [`piki:browser`](extensions.md#the-browser-pikibrowser), which a workspace adds | Refused in **Read only** messages |
| `tunnel` | Put the web server the agent works on online at an `https://` address through a Cloudflare quick tunnel, opened only through its link unless `access: "public"`: `start` runs `serve` (one of the `node` and `python` tools' programs, without a shell) in the sandbox as a service that keeps running after the call, `status` gives the address and the server's last output, `stop` takes it offline. People use what is online in the session panel's **App** tab; `serve.desktop` puts an app with no web page online as a [desktop](extensions.md#desktops-for-apps-without-a-web-page). Runs only in the Linux sandbox, with cloudflared the host's owner set up; it comes with [`piki:tunnel`](extensions.md#the-tunnel-pikitunnel), which a workspace adds | Each `start`: only for the host's owner and members they granted host commands; refused in **Read only** messages |
| `git_push` | Push a clone's checked-out commit to a branch, optionally opening a pull request, or tag a commit already on a branch; it comes with [`piki:git`](extensions.md#session-tools) | Refused in **Read only** messages |
| `github_read` | Read a GitHub issue or pull request. With `wait`, read it again every 30 seconds until something happens, instead of sleeping in a shell: `"checks"` until every check of the head commit has completed (or the pull request is closed, or its head has had no checks for 2 minutes), `"change"` until a comment, review, review comment, push, check or its state changes, other than the session's own comments and pushes and the checks on a commit it pushed. It waits up to `timeout_seconds` (600 by default, at most 1800), and its result's `waited` says how the wait ended. Each read counts against the session owner's GitHub rate limit, so where the session also has `gh`, the agent reads and waits for checks with `gh` and keeps this for `"change"` ([GitHub](github.md)); it comes with [`piki:github`](extensions.md#session-tools), which a workspace gets with its first GitHub repository | Nothing, during a shared message |
| `github_comment` | Comment on a GitHub issue or pull request (`github_comment`, `github_issue` and `github_merge` go with `github_read`, under [`piki:github`](extensions.md#session-tools)) | Refused in **Read only** messages |
| `github_merge` | Merge a GitHub pull request | Refused in **Read only** messages |
| `github_issue` | Open a GitHub issue | Refused in **Read only** messages |
| `source_read` | Read an item of one of the workspace's [document sources](repositories.md#document-sources), with the session owner's connection; it reads a kind of source while the workspace has that kind's extension ([`piki:notion`, `piki:google-drive`, ...](extensions.md#session-tools)), which comes with its first source of that kind | Nothing, during a shared message |
| `schedule` | List, create, change or delete the session's [scheduled prompts](sessions.md#scheduled-prompts), and [workspace schedules](workspaces.md#schedules) made from it or of its owner; it comes with [`piki:schedule`](extensions.md#session-tools), which a workspace adds | A message from the session owner; refused in **Read only** messages for changes |
| `sessions` | List, read, message, start, stop and archive the workspace's other sessions, as the message's sender (see [Working across sessions](sessions.md#working-across-sessions)); it comes with [`piki:sessions`](extensions.md#session-tools), which a workspace adds | A shared message; refused in **Read only** messages for changes, and to pass content between sessions whose readers differ unless the session's owner allows it |
| `publish_artifact` | Publish an [artifact](sessions.md#artifacts): `name` (lowercase letters, digits, `-` and `_`, at most 64), `kind` (`html`, `svg`, `markdown` or `text`), `content` (at most 1 MiB) and optionally `title`. It is kept with the session on its host, not in the worktree, and shows as a card in the transcript and in the session panel's **Artifacts** tab; the same name again makes its next version. It comes with [`piki:artifacts`](extensions.md#session-tools), which a workspace adds | A shared message; refused in **Read only** messages |
| Extension tools | Whatever the workspace's [extensions](extensions.md) offer. Installed extensions run in the session's sandbox on Linux hosts, and on macOS hosts with the sandbox; elsewhere, and Pikibun's own, on the host outside the sandbox | In the sandbox: any message that may act. Outside it: a message of the host's owner, or of a member they [granted host commands](hosts.md#host-admins-and-host-command-grants), in a session of theirs; anyone's where the host's owner lets every session run extension tools. Never in **Read only** messages |

A workspace's page lists the tools its sessions can use, with what each does and where it comes from, under **Settings → Workspaces →** the workspace **→ Agents → Extensions → Tools sessions can use** (see [Extensions](extensions.md)).

The program tools (`node`, `python`, `rust`, `go`, `dotnet`, `make`) take `timeout_seconds` and `env` alike. A call without `timeout_seconds` that runs a test suite or a server (`npm test`, `pnpm dev`, `node --test`, `pytest`, `cargo test`, `go run`, `make test` and the like) ends after 20 minutes, sooner where the host's command time limit is shorter; anything else runs up to the host's limit. A call that failed at the worktree's top for want of a `package.json`, `pyproject.toml`, `Cargo.toml`, `go.mod` or `Makefile` that a clone has is told to give that clone as its `directory`.

Every image that enters the conversation is fitted to the conversation model's own image limits (Pi's `inputLimits.images.resize`, at most 1568×1568 pixels and 512 KB, Pikibun's cap: a model that declares tighter limits gets those) before it is stored, so the transcript never changes later: pasted images when the message is sent and again when it runs on a model that takes smaller ones, `read`'s images and the browser's screenshots as the tool prepares them, and the images of every other tool the model calls (code mode's `image()`, extension and MCP tools) through Pi's `fit-images` hook. A resized image comes with a note on how to map coordinates back; one that can't be prepared (damaged, too large to decode, or while too many images are being prepared at once) is left out with a note saying so. Images go through one host-wide line, one at a time, with the same decode limits and timeout as before. A model without image input keeps them in the transcript, and Pi replaces each with a placeholder in its requests.

There is no shell tool: `bash` and `host_bash` were removed (#163). Sessions run Git, Node.js and Python with their own tools, move, copy and delete with the file tools, and chain tools with code mode. Saved agents, and past records, that name them stay readable.

Nothing waits for anyone's approval: a call runs, or is refused with its reason. Whatever a message's access, a session runs only the tools both its owner's [tool group](workspaces.md#tool-groups) and the message's sender's have; see [What a session may do](approvals.md). Side asks offer only the read-only tools.

Sessions started from a saved agent, before agents were removed, keep that agent's instructions and tools; any other tool they call runs as the session's other tools do.

## Prompt cache warming

Model providers keep the start of a conversation in a prompt cache for a few minutes (Anthropic: 5 minutes, an hour with long retention), and read it far cheaper than they write it. A message after a longer pause, or a run that waits on a slow tool, writes the whole conversation again at full price. To spare the host's account that, a host re-sends a session's last model request with a cap of one output token shortly before its cache entry expires:

- **When**: at 90% of the cache lifetime (and at least 10 seconds before it ends), counted from when the request, then each refresh, was sent; for up to 60 minutes after the request while the agent still works, and up to 30 minutes after it answered.
- **Only where it pays**: for models whose prompt cache has a known lifetime, and only when the refresh is expected to save at least $0.05: while the agent works the next request is certain, after it answered Pi counts on one in about seven. Anthropic models that think with a token budget are never refreshed: the replay would change the budget, and so the cache entry.
- **Never in the way**: nothing is refreshed while the session's model request is under way, and a refresh still under way when the agent sends its next request is cancelled. Refreshing stops once the next request would differ: another model or reasoning level, a compaction, a rewind, or a conversation that no longer starts with what was sent. Side asks, and sessions that agents start for sub-tasks, are refreshed only while they work.
- **Counted as the session's own**: a refresh's usage is added to its conversation's, and it leaves the provider's conversation state (such as an OpenAI response thread) as it was.

A workspace's owners and admins choose under **Settings → Workspaces →** the workspace **→ Sessions → Prompt cache** (`GET`/`PUT /api/workspaces/:id/cache-warming` with `{"mode": "idle" | "streaming" | "off"}`): **Working and waiting** (`idle`, the default), **While working** (`streaming`) or **Off**. A host's owner can also turn warming off on their host (**Settings → Hosts →** the host **→ Configuration → Prompt cache warming**, `HostConfig.cacheWarming`), as it spends their model accounts: then no session on that host is warmed, whatever its workspace chooses. Hosts learn a change within a minute. Only hosts whose connector has cache warming refresh anything, and only with a Pikibun server that has this setting. How it works: [Prompt cache warming](design/cache-warming.md).
