# Sessions

## Starting a session

Select a workspace in the sidebar (or open **New session** in it):

- **Describe the task**: the first message. Its first line becomes the session's title.
- **Host**: one of your hosts, or a host shared with the workspace. In your [private workspace](workspaces.md#your-private-workspace), the desktop app picks **This Computer** (**This Mac**) while it is your host and online. Where the workspace has [auto mode](extensions.md#auto-mode-pikiauto-mode) on, **Auto** chooses the host, and in the model menu the model, for the task you describe.
- **Visibility**: **Workspace** (members can view; the default) or **Private** (explicit grants only, apart from the workspace's owner and admins, who [manage every session](workspaces.md#managing-every-session)). See [Collaborating on a session](collaboration.md).
- **Where it runs** (on your own host, or on one whose owner granted you **Sessions on the host** once its [configuration](hosts.md#host-configuration) allows **Sessions on the host**): **Sandbox** or **On this host**, without the sandbox. It starts in the sandbox, except in your [private workspace](workspaces.md#your-private-workspace), where it starts on the host wherever it can. See [Sessions on the host](hosts.md#sessions-on-the-host).
- The model, reasoning level and access for the first message (see [Chat options](#chat-options)). The info tips show the host, the model and the repositories the session will pin.

Press Enter to start (Shift+Enter adds a line; on a phone, Enter adds a line and the send button starts it). On someone else's host, first confirm that you trust it: its operator can read the session's prompts and repository files. The session shows **Starting** while the host prepares it, then runs your message. If it fails to start (**Not started**), its owner sends a message to start it again on the same host (**Restart and send**).

## Shared messages and side asks

The composer switches between **Shared** and **Side ask**:

- A **shared** message (**Submit to session**, needs write permission) goes into the session's conversation and drives its work. Every message runs as the session owner, with their Git identity, accounts and environment, whoever sends it.
- A **side ask** (**Send side ask**, needs ask permission) asks about the work without changing it: the agent gets only the read-only tools, in a separate thread that starts from the shared conversation (**Side ask 1**, **Side ask 2**, …). Anyone who can view the session can see side asks, but share links don't show them.

Shared messages and side asks share one queue: up to 64 waiting or running, with up to 1 MiB of queued text. Accepted work goes on after you leave the page, as long as the host is online.

A shared message you send while the agent works on one of yours **steers** that work instead of waiting its turn: the agent reads it as soon as its current tool calls finish, before it answers, the way Pi's steering works, and the work goes on from there. It steers only when it has the same chat options (model, thinking level, access) as the message being worked on and has no images, and only when nothing queued ahead of it is waiting. Everything else waits in the queue and runs once the work ends: other people's messages, side asks, messages with other options or with images, and anything behind a waiting message. A steering message shows as running in the queue, so it can't be taken back to edit. If the work fails before the agent has read it, it goes back to the queue and runs next, on its own.

## Tool calls

The transcript shows each of the agent's tool calls as one row with the result that answered it: what the call did and what came of it, such as `read_file · src/app.ts L60–89 → Lines 60–89 of 975`, `git status → nothing to commit, working tree clean` or `search · "TODO" in src → 12 matches in 4 files`, with how long the tool ran. A command's row ends with the last line it printed, where commands say how they went. A call that failed shows in red: a command that failed or was denied, or a tool that reported an error. Its row ends with why it failed, the error Pi recorded for the call (such as an exception the tool threw), and the opened result lists that error, and any warnings or notes Pi added, after the tool's output. Press a row to open it: the call's arguments, one per line, then its result as the tool gave it, a command's output as it printed it and a file as it reads, without who asked (the row's message says that). A row with no result yet is a call still running or waiting on a card. A result whose call isn't shown, as when an earlier page holds it, gets a row of its own.

These lines come from the shapes of Pikibun's own tools, not from a model; another tool's row shows its first argument and the first line of its result. An up-to-date connector names which call each result answers; with an older one, results answer their calls in the order they follow them, which is how the agent gets them (update it with `npx pikibun@latest connect`).

## Images

Paste images, such as screenshots, into the composer, or pick them with its image button (on a phone, from the photo library or camera): into a new session's first message, a shared message or a side ask. They show as thumbnails above the text; **×** removes one. A message carries up to 4 images, and can be images alone. The browser scales each image to at most 1568 pixels on its longest edge and compresses it until the message fits what the host takes in one request; the host decodes and prepares each image again, and the model gets them after the message's text. The images stay on the host, in the conversation: the transcript notes each one as `[image image/png]`.

Collaborators (the session collaborator role, `write`, as the **Files** tab takes) see each image as a thumbnail in that line's place: below the message's text, and inside an expanded tool result for an image the agent looked at, such as a browser screenshot or an image file it read. The host makes each thumbnail, at most 480 pixels on its longest edge, when it scrolls into view, and keeps the latest it made; pressing one shows the image as the model got it, with the message's others a click away. Viewers, share links, archived sessions, sessions showing brief tool output (for tool results) and hosts that predate this keep the `[image image/png]` line. Brief tool output only shortens what the transcript shows: a collaborator can still read those images, as they can the files they came from.

Images need a connector that supports them on the session's host (update it with `npx pikibun@latest connect`) and a model that accepts images; otherwise the composer or the send says why.

## Files

The same button (a paperclip where the host takes files) attaches any other file, and pasting a copied file attaches it too. Images the model can look at still go with the message as above; every other file shows as a chip with its name and size, and is uploaded into the session's worktree, under `attachments/`, when the message is sent. The message then ends with a note naming where each file went, such as `attachments/report.pdf (1.2 MB)`, so the agent can read or process it with its tools. A file never replaces another: a second `report.pdf` becomes `attachments/report (2).pdf`. A message carries up to 10 files, and can be files alone; a file that fails to upload stops the send, and sending again uploads only what isn't there yet.

Each file may be at most **10 MB** until a workspace owner or admin chooses another limit, from 1 MB to 50 MB, under **Settings → Workspaces →** the workspace **→ Attachments**. Uploading writes into the worktree, so it takes the session collaborator role (`write`). Files travel in chunks of 512 KB through the server to the session's host, which keeps them outside the sandbox until the last chunk arrives and then writes the whole file into the worktree through the sandbox, like the agent's own file tools. With [Pikibun on your own computer](local.md), the server and host are both on it, so the file never leaves it. Files need a connector that supports them on the session's host (update it with `npx pikibun@latest connect`).

## Stopping the agent

While the agent works, anyone with write permission can press **Stop** (the square beside send) to stop the message running now and every message queued behind it, side asks included (connector 0.9.0 or newer). They show as stopped in the queue at once, and the transcript marks where the work stopped and who stopped it. A tool call waiting on a card ends and its card is marked interrupted; a command or push already running finishes, and its card shows the outcome. The queue line reads **Stopping...** until the host has ended the work; messages sent meanwhile wait and then run as usual. A queued message that was stopped never reaches the agent: send it again to run it. A session whose last shared message was stopped shows as **Idle**.

The host can stop a message too. When the host crashes (rather than stopping its connector) again and again while the same message is being worked on, Pi stops resuming that work so the host doesn't keep crashing: a crash during the model's answer counts as a failed attempt, so the fourth one ends the message, and five crashes in a row end any other work, such as a tool call. The transcript then says the message stopped because the host crashed, the session shows as **Failed**, and the queue moves on. Send the message again to retry it.

## Copying, going back and forking

Each message has its actions beside who sent it, as small icons (their names show on hover).

- **Copy message** (the copy icon): a message's text, or a reply's Markdown without its tool calls. Every message offers it, side asks too.
- **Go back** (the history icon, needs write permission): takes the shared conversation back, for everyone, to just before one of the messages people sent, or to just after one of the agent's final replies. Everything after that point leaves the conversation, and the next message continues from there, with the model seeing only what is left. Going back to before a message puts that message's text in your chat box, below anything already typed there, so you can edit it and send it again. Only the conversation goes back: the worktree, its clones, commits and anything pushed stay as they are, so ask the agent to undo those if you need to. Stop the session's work first: going back waits until nothing runs or is queued. The host keeps the conversation it went back from, in its backups too, but it no longer shows.
- **Fork** (the branch icon, the session's owner and anyone with write permission): starts a new session of yours from the shared conversation up to the same points, on the same host, with the model and reasoning level the conversation uses now (or the model the session started on, once the host no longer offers that one or it's disabled) and the same visibility, titled **Fork: …**, and opens it; a fork from before a message puts that message in the new session's chat box. The session you forked from stays as it is. The host copies the conversation into the new session itself, so it never passes through the server. Like every new session, the fork's worktree starts empty: its agent clones the workspace's repositories again, and only what was pushed is there. If the fork fails, the new session is archived.

  Forking someone else's session needs write permission on it: their fork's agent gets the conversation as the model saw it, with full tool output and the values the transcript shows as `[redacted]`, which someone who drives the session's agent can get from it anyway. A reader can't fork. The fork is yours, and needs what any session you start there needs: the host shared with the workspace (or yours) and its model available to you, else it starts on the model the session started on, if you may use that. A host whose connector predates this forks only for the session's owner, who alone sees the icon there until its connector is updated (`npx pikibun@latest connect`). When you fork someone else's session, the audit log also records its owner as `sourceOwnerId`.

There are no such points inside one of the agent's turns, where a tool call would lose its result, so a reply that goes on to call tools offers only **Copy** (tool call and tool result rows show their text when expanded). A host whose connector predates these actions offers only **Copy** too: update it with `npx pikibun@latest connect`.

## Chat options

Beside the composer you can pick, for each message:

- **Model**: any model the session's host offers and hasn't [disabled](hosts.md#models), or, where the workspace has [auto mode](extensions.md#auto-mode-pikiauto-mode) on, **Auto**, which chooses the model and reasoning for each message from how complex it looks.
- **Reasoning**: Off, Minimal, Low, Medium, High, Extra high or Max, as the model supports. A model starts at the level Pi on the host gives it: the level in its `enabledModels` pattern (such as `"anthropic/*:high"`), else its entry in `modelThinkingLevels`, else `defaultThinkingLevel`, else medium.
The chat box offers no access choice: every shared message you send acts. Every tool of the session runs at once, as its owner, within the [tool groups](workspaces.md#tool-groups) of its owner and of the message's sender, and the rules of [What a session may do](approvals.md). To ask without changing anything, send a side ask. **Read only** remains for [scheduled prompts](#scheduled-prompts) and messages agents send each other: there, edits, commands, commits, pushes, GitHub effects, schedules and messages to other sessions are refused. Nobody approves anything: a call runs or is refused, and what runs on the host's own machine runs only for its owner and members they granted host commands ([What a session may do](approvals.md)). Messages an agent sends with the `sessions` tool act too, unless the agent chose **Read only** or the message it is working on was Read only; the answer to a Read-only message's question comes back Read only. The agent can merge any pull request of the workspace's github.com repositories that GitHub lets the owner merge; GitHub's branch protection and required checks still apply, so protect the branches that need a person's review. Apps from before approvals were removed may still send **Ask before acting**, **Auto-approve** or **Auto-merge**: messages with them act. Hosts running a connector older than 0.3.0 keep each session's model and offer none of these options, and a connector that still asks for approvals takes no new messages until it is updated.

## Status, menu and panel

Session lists show what each session's agent is doing: **Starting**, **Not started**, **In progress**, **Done**, **Failed**, **Idle** or **Archived**. A session at rest with a [scheduled prompt](#scheduled-prompts) shows **Scheduled**, with a clock in place of its status dot. A session whose web server is online through its [tunnel](extensions.md#the-tunnel-pikitunnel) is marked **Online**. The **Sessions** page groups sessions by workspace, with a search box, **Show archived** and **Open by ID** (for a session ID someone gave you).

The session's menu offers **Copy session ID** and **Open in workspace settings**; to its owner and the workspace's owner and admins **Rename**, **Make private** or **Make workspace-visible** and **Archive** (or **Unarchive**); and to its owner **Create backup** too, and **Pack files** on an archived session (see [Packing archived sessions](backups.md#packing-archived-sessions)). Archiving makes a session read-only for everyone and hides it from lists; unarchiving brings it back as it was. A week after archiving, its files are packed on its host to save space, unless its workspace turned that off; unarchiving unpacks them.

Right-click a session in the sidebar or on the **Sessions** page for a shorter menu: **Open in new tab** (in a browser), **Copy link** and **Copy session ID**; and, to those who manage the session, **Rename**, **Make private** or **Make workspace-visible** and **Archive** (or **Unarchive**), with the same confirmations. Right-click a workspace in the sidebar, or open the options menu beside its name, for **New session**, **Collapse** or **Expand**, **Copy workspace ID** and **Workspace settings**. The context menu key or Shift+F10 opens these menus from the keyboard, the arrow keys move through them, and Escape closes them. On phones and tablets, a finger held on a row opens them, without opening the session or folding the workspace.

On phones and tablets, a session's row in the session list also slides sideways under a finger, as rows do in mail and chat apps, to show its main actions: swipe it right for **Copy link** and **Rename**, or left for **More** (the whole menu) and **Archive** (or **Unarchive**). As in the menu, **Rename**, **Archive** and **Unarchive** show only to those who manage the session. Let go past half of the actions, or flick, and they stay open; tap one to run it, or tap the row, swipe it back or scroll the list to close it. One row is open at a time.

The session panel has six tabs:

- **Details**: **Online**, while the session's server is online through its [tunnel](extensions.md#the-tunnel-pikitunnel): its public address, what serves it, who started it and until when, with a **Stop** button for those who may write to the session; **Context**, how full the shared conversation's context window is: about how many tokens it holds against its model's window (the provider's count for its last answered request, and about 4 characters a token for anything since), as a meter that turns to a warning near where Pi [compacts](hosts.md#host-configuration) it, and where that is (the window less the reserve the host's compaction settings keep for the model); then **Host**, **Repositories** (cloned on demand; a pinned session's ref, commit and folder), **People**, **Transcript** (see [Transcript size](collaboration.md#transcript-size)), **Connected sessions** (see [Working across sessions](#working-across-sessions)), **Backups**, **Export** and **Access**.

- **Files**: the session's worktree on its host, read-only. Open directories and preview files: text up to 256 KB, with line numbers and syntax highlighting chosen by file name (up to 128 KB), and PNG, JPEG, GIF and WebP images up to 2 MB, over a checkerboard that shows transparency; click an image to switch between fitting the panel and its actual size. SVG files show as an image, drawn without running scripts or loading anything, with their source a click away. Each path is read from the host as you open it (**Refresh** reads it again), inside the session's sandbox and confined to its worktree like the agent's file tools; symlinks that lead out of it don't open, and values that look like secrets are hidden as in the transcript. It takes the session collaborator role (`write`), since collaborators can already have the agent read any file; viewers and share links don't get it. It isn't offered on archived sessions, and needs a host whose connector is new enough to advertise it.
- **Browser**: what the agent's [browser](extensions.md#the-browser-pikibrowser) saw, newest call first: the page's address, title and HTTP status, its screenshot (click it for actual size), the steps it took and which failed, and the page's console messages, errors, failed requests, text and the elements the agent can act on, with the output of the app it served. **Previous** and **Next** go through earlier calls (the worktree keeps the last 30); it follows the newest as the agent works. It reads the reports and screenshots the browser leaves in the worktree's `browser-output/` directory, as the Files tab would, so it takes the same collaborator role (`write`), isn't offered on archived sessions, and shows what is on the host now. A public page's address opens in your own browser; `localhost` pages ran in the session's sandbox and exist only there. A session whose host has no Chromium for the browser yet shows a warning above its chat box as it starts, and its panel's **Extensions** section says why; the host's owner sets one up on the host's page ([A browser for sessions](hosts.md#a-browser-for-sessions)).
- **Schedules**: the session's [scheduled prompts](#scheduled-prompts).
- **Activity**: the session's audit log, newest 200 entries.

## Scheduled prompts

A scheduled prompt wakes the session's agent on a schedule: the server sends it a message, as the session's owner, as if they typed it in the chat box. Use it for recurring work such as a nightly test run or a weekly dependency report. The session owner manages them in the panel's **Schedules** tab (**New**, **Pause**/**Resume**, **Run now**, **Edit**, **Delete**), or asks the agent in the chat ("every weekday at 9, check the nightly build"), and everyone who can view the session sees them.

- **When**: a five-field cron expression (minute, hour, day of month, month, day of week, as in crontab, with ranges, steps, lists and names such as `*/30 8-18 * * mon-fri`, or `@hourly`, `@daily`, `@weekly`, `@monthly`), read in an IANA time zone (the browser's by default). Runs are at least 5 minutes apart. The form shows the next three runs as you type.
- **Access**: **Act** (the default), which runs the session's tools at once without anyone watching, or **Read only**. Read only needs a host whose connector takes chat options.
- **Runs in**: **This session** (the default) sends each run to the session's own agent. **A new session each run** leaves the session itself alone: each run starts a new session under it, as the owner, on its current model (at its reasoning level) and host, as private as it or more, and the message opens that session. Use it for recurring jobs that shouldn't interrupt, or wait for, the session's own work, each in a fresh context. Lists show the new sessions under the session whose schedule started them, and the schedule offers **Open last session**.
- **When its run is done** (for a new session each run): **Archive the session** (the default) makes each new session one-shot: once its host reports the run done, the server archives it within about 30 seconds. It stays in the list as archived and opens to read, and **Unarchive** keeps it open from then on. A run that fails stays open for you to look at, and so does a session you, or another session, send a message of your own: taking it over keeps it open. **Keep it open** leaves every new session open until you archive it. A session's schedules keep at most 20 of these sessions open: once there are 20 that aren't archived, a run starts none and says so, until some are archived. They don't count against the sessions its agent may start with the `sessions` tool. A session its host fails to start, or that takes no message, is archived again.
- **Busy sessions**: a run that comes while the agent is working is skipped, not queued, and the schedule shows why (a run in a new session goes ahead whatever the session is doing). Runs missed while the server or host was offline, or the session archived, aren't caught up: the next check sends one and moves on. The session's host must be online for its message to run.
- **From the chat**: the agent's `schedule` tool lists, creates, changes and deletes the session's schedules (connector newer than 0.9.0). Only the session owner's messages can use it, since every run is the owner's message; a collaborator's are refused, and a **Read only** message only lists them.
- Each run is audited as the owner's `session.submit` with the schedule's ID (in the new session, for a run in one, with `session.schedule.child_started` on the session itself); creating, changing and deleting schedules are audited too, marked with the tool call when the agent did it. A session keeps at most 20 schedules, and the server checks for due ones every 30 seconds.

## Working across sessions

A session's agent can work with the workspace's other sessions through its `sessions` tool: ask you which sessions exist and what they are doing, read another session's latest transcript, ask it a side question, send its agent a message, start a new session for a sub-task, wait for or be notified of the outcome, and stop or archive sessions. Use it to split work between sessions ("start a session to update the docs while you fix the tests, and tell me when both are done") or to consult a session that already knows a part of the code.

- **As the sender, never more**: every action runs as the person whose message the agent is working on, with exactly their permissions in the other session, as if they had acted themselves. A collaborator's message reaches only the sessions the collaborator can, and a session the agent starts is the sender's own, on their own host or this session's host when it is theirs. Sessions of other workspaces aren't reachable.
- **Access is capped by the message**: a **Read only** message lists, reads and asks, but never changes another session (send, start, stop, archive). A message that acts sends messages that act, unless the agent chooses **Read only** for them ([Chat options](#chat-options)).
- **Each session's own rules**: what a message runs in another session follows that session's rules: its owner's tool group and its sender's, and [what runs on the host's own machine](approvals.md).
- **Who can see what**: content passes between two sessions only when the same people can read both (a share link counts as everyone). Reading a session, or being notified of its reply, that someone reading this session can't open, or sending this session's content where people who can't read this session would see it, is refused unless the session's owner turns on **Content from sessions other people read** under its **Details → People** (`PUT /api/sessions/:id/audience-sharing` with `{"enabled": true}`). A session started by the agent is never more visible than the one that started it: a private session starts only private ones.
- **Messages say where they come from**: each message an agent sends starts with a line naming the session it comes from, its sender and its hop, and the server records it. The **Connected sessions** section of the panel shows the session that started this one, the sessions it started, and the latest messages either way, with their senders (only sessions you can open are named). Lists show sessions started by another session indented under it.
- **Models for sub-tasks**: an agent that starts a session for a sub-task picks its model, among those the sender can use, and the reasoning level its opening message runs at, which that session's conversation keeps: a capable model thinking hard for difficult work, a fast one thinking little for simple work. Whatever it leaves out is this session's current model and reasoning level. A workspace owner or admin can turn the choice off under **Settings → Workspaces →** the workspace **→ Sub-task sessions**; then every session an agent starts runs on its parent's current model and reasoning level.
- **Busy sessions and notifications**: a message to a session that is working is refused, not queued (side asks still go). With `notify`, the server sends the outcome back as a new message once the other session finished, as the same sender, when this session is idle; it gives up after 24 hours. The agent can also `wait` for an outcome, for up to 30 minutes.
- **Limits**: a message that came from another session is one hop further down a chain; at 3 hops an agent reads and lists but sends nothing further, and no message goes back to a session it came through (the notification answers it instead). One message sends at most 10 messages to other sessions, and a session starts at most 20 sessions.
- Every action is audited in both sessions: `session.cross_session.sent`, `.created`, `.stopped` and `.archived` in the sending session, and the usual `session.submit`, `session.stopped` or `session.archived` in the other, marked with the message. The tool needs a connector new enough to advertise it. See [docs/design/cross-session.md](design/cross-session.md).
