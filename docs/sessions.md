# Sessions

## Starting a session

Select a workspace in the sidebar (or open **New session** in it):

- **Describe the task**: the first message. Its first line becomes the session's title.
- **Host**: one of your hosts, or a host shared with the workspace. In your [private workspace](workspaces.md#your-private-workspace), the desktop app picks **This Computer** (**This Mac**) while it is your host and online. Where the workspace has [auto mode](extensions.md#auto-mode-pikiauto-mode) on, **Auto** in the model menu leaves the model and reasoning to a model on the host you pick, for each message.
- **Visibility**: every session is visible to the workspace's members; there are no private sessions. For work nobody else should see, start it in your [private workspace](workspaces.md#your-private-workspace). See [Collaborating on a session](collaboration.md).
- **Where it runs** (on your own host, or on one whose owner granted you **Sessions on the host** once its [configuration](hosts.md#host-configuration) allows **Sessions on the host**): **Sandbox** or **On this host**, without the sandbox. It starts in the sandbox, except in your [private workspace](workspaces.md#your-private-workspace), where it starts on the host wherever it can. See [Sessions on the host](hosts.md#sessions-on-the-host).
- The model, reasoning level and access for the first message (see [Chat options](#chat-options)). The info tips show the host, the model and the repositories the session will pin.

Press Enter to start (Shift+Enter adds a line; on a phone, Enter adds a line and the send button starts it). On someone else's host, first confirm that you trust it: its operator can read the session's prompts and repository files. The session shows **Starting** while the host prepares it, then runs your message. If it fails to start (**Not started**), its owner sends a message to start it again on the same host (**Restart and send**).

## Shared messages and side asks

The composer switches between **Shared** and **Side ask**:

- A **shared** message (**Submit to session**, needs write permission) goes into the session's conversation and drives its work. Every message runs as the session owner, with their Git identity, accounts and environment, whoever sends it.
- A **side ask** (**Send side ask**, needs ask permission) asks about the work without changing it: the agent gets only the read-only tools, in a separate thread that starts from the shared conversation (**Side ask 1**, **Side ask 2**, …). Anyone who can view the session can see side asks, but share links don't show them. To act on what a side ask found, [continue it in a new session](#copying-going-back-and-forking).

  The session list shows your three latest side asks under each session you asked in, newest first, by the first line of their question. Pressing one opens the session on that side ask; pressing the session itself opens its shared conversation. Only you see your side asks there, and only while you may still view the session; the ones an agent sent with the sessions tool are listed with the session's messages in **Details** instead. For this, Pikibun's server keeps, for each person and session, those three side asks' first lines, with values that look like passwords, tokens or keys hidden and cut to 120 characters, as it keeps a session's title; the side asks themselves stay on the host.

Shared messages and side asks share one queue: up to 64 waiting or running, with up to 1 MiB of queued text. Accepted work goes on after you leave the page, as long as the host is online.

Shared messages run one at a time, in the order they were sent. A side ask doesn't wait for them: it starts as soon as it is sent, even while the agent works on a shared message, and answers from the shared conversation as it was when you sent it. Up to 4 side asks run at once; more wait for one of them to end.

A shared message you send while the agent works on one of yours **steers** that work instead of waiting its turn: the agent reads it as soon as its current tool calls finish, before it answers, the way Pi's steering works, and the work goes on from there. It steers only when it has the same chat options (model, thinking level, access) as the message being worked on and has no images, and only when no shared message queued ahead of it is waiting. Everything else waits in the queue and runs once the work ends: other people's messages, messages with other options or with images, and anything behind a waiting shared message. A steering message shows as running in the queue, so it can't be taken back to edit. If the work fails before the agent has read it, it goes back to the queue and runs next, on its own.

## Tool calls

The transcript shows each of the agent's tool calls as one row with the result that answered it: what the call did and what came of it, such as `read · src/app.ts L60–89 → Lines 60–89 of 975`, `git status → nothing to commit, working tree clean` or `grep · "TODO" in src → 12 matches in 4 files`, with how long the tool ran. A command's row ends with the last line it printed, where commands say how they went. A call that failed shows in red: a command that failed or was denied, or a tool that reported an error. Its row ends with why it failed, the error Pi recorded for the call (such as an exception the tool threw), and the opened result lists that error, and any warnings or notes Pi added, after the tool's output. Press a row to open it: the call's arguments, one per line, then its result as the tool gave it, a command's output as it printed it and a file as it reads, without who asked (the row's message says that). A row with no result yet is a call still running or waiting on a card. A result whose call isn't shown, as when an earlier page holds it, gets a row of its own.

These lines come from the shapes of Pikibun's own tools, not from a model; another tool's row shows its first argument and the first line of its result. An up-to-date connector names which call each result answers; with an older one, results answer their calls in the order they follow them, which is how the agent gets them (update it with `npx pikibun@latest connect`).

## Images

Paste images, such as screenshots, into the composer, or pick them with its image button (on a phone, from the photo library or camera): into a new session's first message, a shared message or a side ask. They show as thumbnails above the text; **×** removes one. A message carries up to 4 images, and can be images alone. The browser scales each image to at most 1568 pixels on its longest edge and compresses it until the message fits what the host takes in one request; the host decodes and prepares each image again, and the model gets them after the message's text. The images stay on the host, in the conversation: the transcript notes each one as `[image image/png]`.

Collaborators (the session collaborator role, `write`, as the **Files** tab takes) see each image as a thumbnail in that line's place: below the message's text, and inside an expanded tool result for an image the agent looked at, such as a browser screenshot or an image file it read. The host makes each thumbnail, at most 480 pixels on its longest edge, when it scrolls into view, and keeps the latest it made; pressing one shows the image as the model got it, with the message's others a click away. Viewers, share links, archived sessions, sessions showing brief tool output (for tool results) and hosts that predate this keep the `[image image/png]` line. Brief tool output only shortens what the transcript shows: a collaborator can still read those images, as they can the files they came from.

Images need a connector that supports them on the session's host (update it with `npx pikibun@latest connect`) and a model that accepts images; otherwise the composer or the send says why.

## Files

The same button (a paperclip where the host takes files) attaches any other file, and pasting a copied file attaches it too. Images the model can look at still go with the message as above; every other file shows as a chip with its name and size, and is uploaded into the session's worktree, under `attachments/`, when the message is sent. The message then ends with a note naming where each file went, such as `attachments/report.pdf (1.2 MB)`, so the agent can read or process it with its tools. A file never replaces another: a second `report.pdf` becomes `attachments/report (2).pdf`. A message carries up to 10 files, and can be files alone; a file that fails to upload stops the send, and sending again uploads only what isn't there yet.

Each file may be at most **10 MB** until a workspace owner or admin chooses another limit, from 1 MB to 50 MB, under **Settings → Workspaces →** the workspace **→ Attachments**. Uploading writes into the worktree, so it takes the session collaborator role (`write`). Files travel in chunks of 512 KB through the server to the session's host, which keeps them outside the sandbox until the last chunk arrives and then writes the whole file into the worktree through the sandbox, like the agent's own file tools. With [Pikibun on your own computer](local.md), the server and host are both on it, so the file never leaves it. Files need a connector that supports them on the session's host (update it with `npx pikibun@latest connect`).

## Stopping the agent

While the agent works, anyone with write permission can press **Stop** (the square beside send) to stop the message running now and every message queued behind it, side asks included (connector 0.9.0 or newer). They show as stopped in the queue at once, and the transcript marks where the work stopped and who stopped it. A tool call waiting on a card ends and its card is marked interrupted; a command or push already running finishes, and its card shows the outcome. The queue line reads **Stopping...** until the host has ended the work; messages sent meanwhile wait and then run as usual. A queued message that was stopped never reaches the agent: send it again to run it. A session whose last shared message was stopped shows as **Idle**.

The host can stop a message too. When the host crashes (rather than stopping its connector) again and again while the same message is being worked on, Pi stops resuming that work so the host doesn't keep crashing: a crash during the model's answer counts as a failed attempt, so the fourth one ends the message, and five crashes in a row end any other work, such as a tool call. The transcript then says the message stopped because the host crashed, the session shows as **Failed**, and the queue moves on. Send the message again to retry it.

## Copying, going back and forking

Each message has its actions beside who sent it, as small icons (their names show on hover).

- **Copy message** (the copy icon): a message's text, or a reply's Markdown without its tool calls. Every message offers it, side asks too.
- **Go back** (the history icon, needs write permission): takes the shared conversation back, for everyone, to just before one of the messages people sent, or to just after one of the agent's final replies. Everything after that point leaves the conversation, and the next message continues from there, with the model seeing only what is left. Going back to before a message puts that message's text in your chat box, below anything already typed there, so you can edit it and send it again. Only the conversation goes back: the worktree, its clones, commits and anything pushed stay as they are, so ask the agent to undo those if you need to. Stop the session's work first: going back waits until nothing runs or is queued. The host keeps the conversation it went back from, in its backups too, but it no longer shows.
- **Fork** (the branch icon, the session's owner and anyone with write permission): starts a new session of yours from the shared conversation up to the same points, on the same host, with the model and reasoning level the conversation uses now (or the model the session started on, once the host no longer offers that one or it's disabled), titled **Fork: …**, and opens it; a fork from before a message puts that message in the new session's chat box. The session you forked from stays as it is. The host copies the conversation into the new session itself, so it never passes through the server. Like every new session, the fork's worktree starts empty: its agent clones the workspace's repositories again, and only what was pushed is there. If the fork fails, the new session is archived.

  Forking someone else's session needs write permission on it: their fork's agent gets the conversation as the model saw it, with full tool output and the values the transcript shows as `[redacted]`, which someone who drives the session's agent can get from it anyway. A reader can't fork. The fork is yours, and needs what any session you start there needs: the host shared with the workspace (or yours) and its model available to you, else it starts on the model the session started on, if you may use that. A host whose connector predates this forks only for the session's owner, who alone sees the icon there until its connector is updated (`npx pikibun@latest connect`). When you fork someone else's session, the audit log also records its owner as `sourceOwnerId`.
- **Continue in a new session** (the branch icon on your side asks' messages, for whoever may fork the session; only the person who sent a side ask continues it): forks a new session from a side ask's thread instead: the shared conversation as it was when you asked, then the side ask, up to its reply, or to just before its question, which goes into the new session's chat box. Unlike the side ask, its agent can act: edit, run commands, commit and push, while the session you asked in, and its work, stay as they are. It doesn't wait for the shared work, as a side ask doesn't: only for the side ask itself to finish. It starts as a child of the session, titled **Side ask: …**, and is listed with its children in **Details**; otherwise it is a fork like any other, with the same rules. A host whose connector predates this doesn't offer it until its connector is updated (`npx pikibun@latest connect`); the audit log marks it `sideAsk`.

There are no such points inside one of the agent's turns, where a tool call would lose its result, so a reply that goes on to call tools offers only **Copy** (tool call and tool result rows show their text when expanded). A host whose connector predates these actions offers only **Copy** too: update it with `npx pikibun@latest connect`.

## Chat options

Beside the composer you can pick, for each message:

- **Model**: any model the session's host offers and hasn't [disabled](hosts.md#models), or, where the workspace has [auto mode](extensions.md#auto-mode-pikiauto-mode) on, **Auto**, where a model on the session's host judges each message's kind of task and Auto runs it on the model and reasoning Anthropic's model guide starts that kind on.
- **Reasoning**: Off, Minimal, Low, Medium, High, Extra high or Max, as the model supports. A model starts at the level Pi on the host gives it: the level in its `enabledModels` pattern (such as `"anthropic/*:high"`), else its entry in `modelThinkingLevels`, else `defaultThinkingLevel`, else medium.
The chat box offers no access choice: every shared message you send acts. Every tool of the session runs at once, as its owner, within the [tool groups](workspaces.md#tool-groups) of its owner and of the message's sender, and the rules of [What a session may do](approvals.md). To ask without changing anything, send a side ask. **Read only** remains for [scheduled prompts](#scheduled-prompts) and messages agents send each other: there, edits, commands, commits, pushes, GitHub effects, schedules and messages to other sessions are refused. Nobody approves anything: a call runs or is refused, and what runs on the host's own machine runs only for its owner and members they granted host commands ([What a session may do](approvals.md)). Messages an agent sends with the `sessions` tool act too, unless the agent chose **Read only** or the message it is working on was Read only; the answer to a Read-only message's question comes back Read only. The agent can merge any pull request of the workspace's github.com repositories that GitHub lets the owner merge; GitHub's branch protection and required checks still apply, so protect the branches that need a person's review. Apps from before approvals were removed may still send **Ask before acting**, **Auto-approve** or **Auto-merge**: messages with them act. Hosts running a connector older than 0.3.0 keep each session's model and offer none of these options, and a connector that still asks for approvals takes no new messages until it is updated.

## Slash commands

A session's chat box takes commands named after [Pi's own](https://github.com/earendil-works/pi). Type `/` as the first character and the commands you can use here are listed above the chat box; what you type next narrows the list. On a desktop, **↑** and **↓** move through it, **Return** runs the highlighted command, **Tab** completes it without running it, and **Esc** closes the list. On a phone, press a command.

The first commands below act in the app: they are never sent to the agent or kept in the transcript.

| Command | What it does |
| --- | --- |
| `/model [provider/model]` | Sets the model of your next messages, as the chat box's model picker does. Without a name it lists the host's models; a name can be the model's reference (`anthropic/claude-sonnet`), its ID, its name, or enough of one to tell it apart. |
| `/thinking [level]` | Sets the reasoning level of your next messages, among those the model offers (`off`, `minimal`, `low`, `medium`, `high`, `xhigh`, `max`). Not while the model is **Auto**, which picks it for each message. |
| `/name [title]` | Renames the session; without a title it opens **Rename**. For the session's owner and the workspace's owner and admins. |
| `/new` | Opens a new session in this session's workspace. |
| `/clone` | [Forks](#copying-going-back-and-forking) a new session from the agent's latest finished reply, after asking. For whoever may fork the session. |
| `/copy` | Copies the agent's latest reply, as its **Copy message** does. |
| `/session` | Opens the session's panel. |
| `/settings` | Opens the settings. |

A command the list doesn't offer you still answers when typed, with why it can't run; what you typed stays in the chat box.

The session's host runs the rest, and the list shows the ones this session has, after the app's own. They are sent like a message, so they need what a message needs (write permission for a shared one), get a receipt, and can be a [scheduled prompt](#scheduled-prompts) too:

| Command | What it does |
| --- | --- |
| `/compact [instructions]` | Has Pi summarize the conversation's older messages now, keeping the most recent ones as they are, to free the model's context without waiting for it to fill (see **Context** in the session's panel). The agent keeps working meanwhile. Its line in the transcript says that compaction started, then how it ended: compacted, with the summary in the conversation; nothing to compact, for a conversation still too short to summarize; or why it failed, with the conversation as it was. Instructions say what the summary should keep. |
| An extension's command | A command one of the workspace's [Pi extensions](extensions.md) registers (`pi.registerCommand`) runs on the host. What it reports shows as a line in the transcript; what it sends as a message goes to the agent as yours. It runs where the extension's tools run: for anyone who may send messages where extensions run in the sandbox, and otherwise for the host's owner and members they granted host commands, or where the host's owner lets extension tools run in every session. |
| `/<template> [arguments]` | Sends a prompt template with its arguments filled in. Templates are Markdown files in `.pi/prompts/` of the worktree or of a repository cloned into it, in [Pi's format](https://github.com/earendil-works/pi): `$1`, `$2`, `$@` and `$ARGUMENTS` stand for the arguments, `${1:-default}` for one with a default. The transcript shows the text the agent got. |
| `/skill:<name> [arguments]` | Sends a skill's instructions, followed by the arguments. Skills are `SKILL.md` files in a folder of their own under `.pi/skills/` or `.agents/skills/` in the same places (or a Markdown file directly in one of them). The agent reads the skill's other files from the worktree. |

A command the host ran itself (`/compact`, an extension's) leaves one line in the transcript, with who ran it, and no message. A side ask and a Read-only message take templates and skills, which are only text, but not `/compact` or an extension's command. Templates and skills come from the repository, so whoever can push to it writes them, as can the session's own commands (a file needn't be committed); they do nothing until someone types their name. Where two clones (or a clone and the worktree's top) have one of the same name, the list offers each under its clone's name instead, such as `/app:review` and `/skill:api:release` (`/worktree:review` for the top's). The list names where each one is, and picks up new ones within a couple of minutes; one typed before then still works. Hosts need a connector from the release that brought these: on an older one the list has only the app's commands, and `/compact` says to update it.

Text that starts with `/` but names no command is a message like any other and goes to the agent as typed (`/usr/bin/env is missing`). To send a message that starts with a command's name, put a space before the `/`. A name the app has itself (`/new`, `/model`) is the app's, whatever a repository or an extension calls its own.

Pi's other commands aren't here: some have no meaning in Pikibun (`/quit`, `/login`, `/hotkeys`, `/reload`), and others are done elsewhere (`/fork` and `/tree` by a message's **Fork** and **Go back**, `/resume` by the session list, `/export` and `/share` in the session's panel). The prompts and skills in the host owner's own Pi folder (`~/.pi/agent`) aren't read, as they are that person's and not the workspace's. See [the design](design/slash-commands.md).

## Command palette

Every action of the app is also in one list, the command palette: **Ctrl+K** (**⌘K** on a Mac), the ⌘ button in a session's header, the one beside **New session** on a phone's session list, or **Commands** in the sidebar. Type to narrow it; on a desktop **↑** and **↓** move, **Return** runs the highlighted command and **Esc** closes it. **Ctrl+O** (**⌘O**) opens **Switch session…** directly.

- With nothing typed it lists the commands for the session in front, by group, then the app's own:
  - **Session**: **Rename…**, **Archive** (or **Unarchive**), **Create backup**, **Back up conversation only**, **Pack files**, **Copy session ID** and **Open in workspace settings**, as the session's menu has them.
  - **Panel**: **Session details** and each of the panel's tabs, opening the panel there.
  - **Sharing**: **Copy link**, and **Share link…**, which opens the panel's link sharing.
  - **Chat**: **Model…**, **Reasoning…**, **Ask on the side** (or **Send shared messages**), **Stop**, **Copy latest reply** and **Fork from the latest reply**.
  - **Slash commands**: the chat box's [slash commands](#slash-commands) for this session; choosing one puts it in the chat box, to finish and send there.
  - **Sessions** and **Settings**: **New session**, **New session in…**, **Switch session…**, **All sessions**, **Open a session by ID**, **Settings** and each of its sections, **Workspaces…** and **New workspace**.
- Typing lists the matching commands first, a title that starts with what you typed before the rest, then the sessions whose title matches: choose one to open it.
- A command that can't run right now is dimmed, with why (the session is busy, archived or read-only, nothing is running, the chat box holds a message). One that you can never use on this session, such as **Rename…** on a session you don't manage, isn't listed.
- A command that needs something asks for it in the same box: **Model…**, **Reasoning…**, **Switch session…** and **Workspaces…** a choice from a list, which typing narrows (the current one checked), and **Rename…** a line of text, starting from the session's title. **Back** (or **Esc**) returns to the commands.

See [the design](design/command-palette.md).

## Status, menu and panel

Session lists show what each session's agent is doing: **Starting**, **Not started**, **In progress**, **Done**, **Failed**, **Idle** or **Archived**. A session at rest with a [scheduled prompt](#scheduled-prompts) shows **Scheduled**, with a clock in place of its status dot. A session whose web server is online through its [tunnel](extensions.md#the-tunnel-pikitunnel) is marked **Online**. The **Sessions** page groups sessions by workspace, with a search box, **Show archived** and **Open by ID** (for a session ID someone gave you).

The session's menu offers **Copy session ID** and **Open in workspace settings**; to its owner and the workspace's owner and admins **Rename** and **Archive** (or **Unarchive**); and to its owner **Create backup** too, and **Pack files** on an archived session (see [Packing archived sessions](backups.md#packing-archived-sessions)). Archiving makes a session read-only for everyone and hides it from lists; unarchiving brings it back as it was. A week after archiving, its files are packed on its host to save space, unless its workspace turned that off; unarchiving unpacks them.

Right-click a session in the sidebar or on the **Sessions** page for a shorter menu: **Open in new tab** (in a browser), **Copy link** and **Copy session ID**; and, to those who manage the session, **Rename** and **Archive** (or **Unarchive**), with the same confirmations. Right-click a workspace in the sidebar, or open the options menu beside its name, for **New session**, **Collapse** or **Expand**, **Copy workspace ID** and **Workspace settings**. The context menu key or Shift+F10 opens these menus from the keyboard, the arrow keys move through them, and Escape closes them. On phones and tablets, a finger held on a row opens them, without opening the session or folding the workspace.

On phones and tablets, a session's row in the session list also slides sideways under a finger, as rows do in mail and chat apps, to show its main actions: swipe it right for **Copy link** and **Rename**, or left for **More** (the whole menu) and **Archive** (or **Unarchive**). As in the menu, **Rename**, **Archive** and **Unarchive** show only to those who manage the session. Let go past half of the actions, or flick, and they stay open; tap one to run it, or tap the row, swipe it back or scroll the list to close it. One row is open at a time.

The session panel has eight tabs:

- **Details**: **Online**, while the session's server is online through its [tunnel](extensions.md#the-tunnel-pikitunnel): its public address, what serves it, who started it and until when, with a **Stop** button for those who may write to the session; **Context**, how full the shared conversation's context window is: about how many tokens it holds against its model's window (the provider's count for its last answered request, and about 4 characters a token for anything since), as a meter that turns to a warning near where Pi [compacts](hosts.md#host-configuration) it, and where that is (the window less the reserve the host's compaction settings keep for the model); then **Host**, **Repositories** (cloned on demand; a pinned session's ref, commit and folder), **People**, **Transcript** (see [Transcript size](collaboration.md#transcript-size)), **Connected sessions** (see [Working across sessions](#working-across-sessions)), **Backups**, **Export** and **Access**.

- **Files**: the session's worktree on its host, read-only. Open directories and preview files: text up to 256 KB, with line numbers and syntax highlighting chosen by file name (up to 128 KB), and PNG, JPEG, GIF and WebP images up to 2 MB, over a checkerboard that shows transparency; click an image to switch between fitting the panel and its actual size. SVG files show as an image, drawn without running scripts or loading anything, with their source a click away. Each path is read from the host as you open it (**Refresh** reads it again), inside the session's sandbox and confined to its worktree like the agent's file tools; symlinks that lead out of it don't open, and values that look like secrets are hidden as in the transcript. It takes the session collaborator role (`write`), since collaborators can already have the agent read any file; viewers and share links don't get it. It isn't offered on archived sessions, and needs a host whose connector is new enough to advertise it.
On a phone, and in a window under 700 points wide, the panel is a sheet from the bottom and **Changes** and **Review** are laid out for a finger: the files are a list of tall rows under their directory's name (the folder button shows them as one list with each file's directory under its name) rather than a tree, and a diff is one column (the side-by-side viewer needs a wider window) with the file's name above it and, under the thumb, a bar with previous and next file, the number of differences, **Wrap long lines** (on when the app starts; off, long lines scroll sideways, and it stays as you set it for every diff until the app is closed) and previous and next change. On touch devices, a swipe to the right goes back one step, as the back arrow does: from a diff to the files, in **Changes** from a commit's files to the uncommitted changes, and in **Files** from a file to its directory and from a directory to its parent. Start it anywhere on the page, or at the left edge of a diff whose long lines scroll sideways; a short or slow one springs back. Android's back button, and Escape, take the same steps before they close the panel.

- **Changes**: what Git sees in a clone in the session's worktree, before any pull request: the same file tree, diff viewers and **Expand to the full window** as **Review**, read from the session's host rather than from GitHub. The header names the repository (a menu chooses among them where the worktree holds several, up to 20, looked for two directories deep), its branch and commit, and how many of its commits no remote has yet. **Files** starts on the **Uncommitted changes**: every difference between the last commit and the files as they are now, staged or not, with new files Git doesn't ignore. **Commits** lists the branch's newest 100, the ones not pushed marked; pressing one shows that commit's own changes (against its first parent), and the **×** beside its name goes back to the uncommitted changes. Side by side, the columns are `HEAD` and **Working tree**, or the commit and its parent. It reads again when the agent starts or finishes working, and on **Refresh**. The limits are **Review**'s: a file's diff over 256 KB, what comes after 300 files or about 2 MB of diffs, and all but the first 200 new files, are left out and said so; a new file over 256 KB, a binary file and a symbolic link show without a diff. Each read runs one fixed, read-only Git command on the host, in the session's sandbox with the worktree mounted read-only, behind any command the agent is running, so it can wait while a long one runs. The repository's own programs (external diff and text-conversion drivers, the file-system monitor, hooks) are not run. It takes the session collaborator role (`write`) and hides values that look like secrets, as **Files** does, and isn't offered on archived sessions. In a session that runs directly on its host, without the sandbox, only the host's owner and members granted [host commands](hosts.md) see it, since the command runs on the owner's machine. It needs a host whose connector is new enough to advertise it (a `pikibun` release after 0.34): an older host says so in the tab.
- **Review**: the session's pull request, laid out as an IDE's pull request window: its title, the branch it merges and the one it merges into, its state and checks, and three lists. **Files** is the changed files as a tree by directory, each coloured by how it changed (added, modified, deleted, renamed) with its added and deleted lines and its number of review comments; directories that hold a single directory are joined (`apps/server/src`), and the buttons above the tree show the files as one list, or expand and collapse every directory. **Commits** lists the pull request's commits, each opening on GitHub. **Info** has the description, the checks that haven't passed, the reviews, the review comments (each opens its file) and the conversation. Selecting a file shows its diff, with syntax highlighting and the words changed within a line marked: one column (**Unified viewer**) or the old and new text side by side (**Side-by-side viewer**) under the branch and commit each side comes from. The arrows step through the changes of the file and through the files. **Expand to the full window** makes the panel fill the window, the files on the left beside a side-by-side diff, with a border to drag between them; **Back to the side panel** puts it back. It is offered where the panel sits beside the conversation, so not on phones or in a narrow window. The diff is the changed lines with the lines around them that GitHub gives, not the whole file. A file's diff over 256 KB, and what comes after the first 2 MB of diffs or 300 files, isn't shown: open those on GitHub. The pull request is read from GitHub with the session owner's own sign-in when the tab opens, when its state changes and on **Refresh**; a read that finds nothing new costs none of the owner's [rate limit](github.md), but for a page of GitHub's answer over 4 MB (many files with large diffs), which is read again each time. So it takes the session collaborator role (`write`), as **Files** does, and values that look like secrets are hidden as in the transcript, line by line, on deleted lines as on added ones. Unlike **Files**, it stays available on archived sessions, and on one being restored or moved to another host, as it needs no host. It reviews pull requests on github.com in a repository of the workspace; one hosted elsewhere gets a button that opens it there. Commenting, approving and merging stay on GitHub, or with the agent.
- **Browser**: what the agent's [browser](extensions.md#the-browser-pikibrowser) saw, newest call first: the page's address, title and HTTP status, its screenshot (click it for actual size), the steps it took and which failed, and the page's console messages, errors, failed requests, text and the elements the agent can act on, with the output of the app it served. **Previous** and **Next** go through earlier calls (the worktree keeps the last 30); it follows the newest as the agent works. It reads the reports and screenshots the browser leaves in the worktree's `browser-output/` directory, as the Files tab would, so it takes the same collaborator role (`write`), isn't offered on archived sessions, and shows what is on the host now. A public page's address opens in your own browser; `localhost` pages ran in the session's sandbox and exist only there. A session whose host has no Chromium for the browser yet shows a warning above its chat box as it starts, and its panel's **Extensions** section says why; the host's owner sets one up on the host's page ([A browser for sessions](hosts.md#a-browser-for-sessions)).
- **Schedules**: the session's [scheduled prompts](#scheduled-prompts).
- **Activity**: the session's audit log, newest 200 entries.

## Scheduled prompts

A scheduled prompt wakes the session's agent on a schedule: the server sends it a message, as the session's owner, as if they typed it in the chat box. Use it for recurring work such as a nightly test run or a weekly dependency report. The session owner manages them in the panel's **Schedules** tab (**New**, **Pause**/**Resume**, **Run now**, **Edit**, **Delete**), or asks the agent in the chat ("every weekday at 9, check the nightly build"), and everyone who can view the session sees them.

- **When**: a five-field cron expression (minute, hour, day of month, month, day of week, as in crontab, with ranges, steps, lists and names such as `*/30 8-18 * * mon-fri`, or `@hourly`, `@daily`, `@weekly`, `@monthly`), read in an IANA time zone (the browser's by default). Runs are at least 5 minutes apart. The form shows the next three runs as you type.
- **Access**: **Act** (the default), which runs the session's tools at once without anyone watching, or **Read only**. Read only needs a host whose connector takes chat options.
- **Runs in**: **This session** (the default) sends each run to the session's own agent. **A new session each run** leaves the session itself alone: each run starts a new session under it, as the owner, on its current model (at its reasoning level) and host, or on the schedule's own model and level (below), and the message opens that session. Use it for recurring jobs that shouldn't interrupt, or wait for, the session's own work, each in a fresh context. Lists show the new sessions under the session whose schedule started them, and the schedule offers **Open last session**.
- **Model** and **Reasoning** (for a new session each run): each schedule can start its sessions on a model and reasoning level of its own, so one session can keep a light job (issue triage on a fast model) and a heavy one (an architecture review on a capable model thinking hard) side by side. Left at **This session's model** and **This session's level**, as every schedule made before was, runs start on the session's current ones (a schedule that chooses only a model runs it at the session's current level where the model offers it, else at the level its host starts it at). The choice is checked when you save it, as the agent's [`sessions` tool](#working-across-sessions) checks a sub-task's: a model the owner may use, on their own host or this session's, run at a level its host offers it at, and only where the workspace lets sessions others start choose their model (**Settings → Workspaces →** the workspace **→ Sub-task sessions**). A schedule that runs in this session itself takes none (changing it to run here clears them). A run whose model is gone (removed or disabled, or its host gone), or whose workspace turned the choice off, still starts, on the session's model and level; one whose model no longer runs at its level starts on its model without that level. The schedule says why under its last run (`lastError`: `model_unavailable`, `child_models_disabled` or `thinking_unsupported`) until a run goes as chosen again.
- **When its run is done** (for a new session each run): **Archive the session** (the default) makes each new session one-shot: once its host reports the run done, the server archives it within about 30 seconds. It stays in the list as archived and opens to read, and **Unarchive** keeps it open from then on. A run that fails stays open for you to look at, and so does a session you, or another session, send a message of your own: taking it over keeps it open. **Keep it open** leaves every new session open until you archive it. A session's schedules keep at most 20 of these sessions open: once there are 20 that aren't archived, a run starts none and says so, until some are archived. They don't count against the sessions its agent may start with the `sessions` tool. A session its host fails to start, or that takes no message, is archived again.
- **Busy sessions**: a run that comes while the agent is working is skipped, not queued, and the schedule shows why (a run in a new session goes ahead whatever the session is doing). Runs missed while the server or host was offline, or the session archived, aren't caught up: the next check sends one and moves on. The session's host must be online for its message to run.
- **From the chat**: the agent's `schedule` tool lists, creates, changes and deletes the session's schedules (connector newer than 0.9.0), its `model` (a model ID, as `sessions list` returns them) and `thinking` included; an empty string goes back to the session's. Only the session owner's messages can use it, since every run is the owner's message; a collaborator's are refused, and a **Read only** message only lists them.
- Each run is audited as the owner's `session.submit` with the schedule's ID (in the new session, for a run in one, with `session.schedule.child_started` on the session itself); creating, changing and deleting schedules are audited too, marked with the tool call when the agent did it. A session keeps at most 20 schedules, and the server checks for due ones every 30 seconds.

## Working across sessions

A session's agent can work with the workspace's other sessions through its `sessions` tool: ask you which sessions exist and what they are doing, read another session's latest transcript, ask it a side question, send its agent a message, start a new session for a sub-task, wait for or be notified of the outcome, and stop or archive sessions. Use it to split work between sessions ("start a session to update the docs while you fix the tests, and tell me when both are done") or to consult a session that already knows a part of the code.

- **As the sender, never more**: every action runs as the person whose message the agent is working on, with exactly their permissions in the other session, as if they had acted themselves. A collaborator's message reaches only the sessions the collaborator can, and a session the agent starts is the sender's own, on their own host or this session's host when it is theirs. Sessions of other workspaces aren't reachable.
- **Access is capped by the message**: a **Read only** message lists, reads and asks, but never changes another session (send, start, stop, archive). A message that acts sends messages that act, unless the agent chooses **Read only** for them ([Chat options](#chat-options)).
- **Each session's own rules**: what a message runs in another session follows that session's rules: its owner's tool group and its sender's, and [what runs on the host's own machine](approvals.md).
- **Who can see what**: content passes between two sessions only when the same people can read both (a share link counts as everyone). Reading a session, or being notified of its reply, that someone reading this session can't open, or sending this session's content where people who can't read this session would see it, is refused unless the session's owner turns on **Content from sessions other people read** under its **Details → People** (`PUT /api/sessions/:id/audience-sharing` with `{"enabled": true}`). Every session of a workspace is visible to all its members, so this only comes up where one of them is shared by link.
- **Messages say where they come from**: each message an agent sends starts with a line naming the session it comes from, its sender and its hop, and the server records it. The **Connected sessions** section of the panel shows the session that started this one, the sessions it started, and the latest messages either way, with their senders (only sessions you can open are named). Lists show sessions started by another session indented under it.
- **Models for sub-tasks**: an agent that starts a session for a sub-task picks its model, among those the sender can use, and the reasoning level its opening message runs at, which that session's conversation keeps: a capable model thinking hard for difficult work, a fast one thinking little for simple work. Whatever it leaves out is this session's current model and reasoning level. A workspace owner or admin can turn the choice off under **Settings → Workspaces →** the workspace **→ Sub-task sessions**; then every session an agent starts runs on its parent's current model and reasoning level.
- **Hosts for sub-tasks**: instead of naming a model, and so its host, an agent can give conditions (`placement`) and let Pikibun choose the host: a GPU the sandbox can use, a GPU vendor or its memory, CPUs, memory, free memory or disk, a platform or architecture, model patterns (`anthropic/*`), or a list of hosts. Pikibun takes every host the agent could start the session on (the sender's own hosts, and this session's host when it is theirs), keeps those that are online and meet every condition, and starts the session on the least loaded: the fewest sessions at work there (sessions started in the last two minutes count, so several sub-tasks started in a row spread out), the lowest CPU load for its size and the most free memory, from what the host [reports](hosts.md#hardware). With a model and no conditions, `placement: {}` runs that model on whichever host offering it has the most room. `list` shows each host's hardware, active sessions and load, and the result names the host chosen; when none qualifies, nothing starts and the agent is told which conditions ruled hosts out. Another member's host is never chosen this way: starting a session there stays a person's choice. The [Sub-agents](extensions.md#sub-agents-pikisub-agents) extension has the agent use this for every sub-task, with the workspace's conditions. It needs a connector from this release on the session's host.
- **Busy sessions and notifications**: a message to a session that is working is refused, not queued (side asks still go). With `notify`, the server sends the outcome back as a new message once the other session finished, as the same sender, when this session is idle; it gives up after 24 hours. The agent can also `wait` for an outcome, for up to 30 minutes.
- **Limits**: a message that came from another session is one hop further down a chain; at 3 hops an agent reads and lists but sends nothing further, and no message goes back to a session it came through (the notification answers it instead). One message sends at most 10 messages to other sessions, and a session starts at most 20 sessions.
- Every action is audited in both sessions: `session.cross_session.sent`, `.created`, `.stopped` and `.archived` in the sending session, and the usual `session.submit`, `session.stopped` or `session.archived` in the other, marked with the message. The tool needs a connector new enough to advertise it. See [docs/design/cross-session.md](design/cross-session.md).
