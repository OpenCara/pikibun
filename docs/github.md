# GitHub issues and pull requests

The sandbox has no network, so agents read and act on GitHub through Pikibun instead, as the session owner and with their GitHub sign-in, which stays on the server (connector 0.7.0 or newer; github.com only):

- `github_read` reads an issue or pull request of one of the workspace's github.com repositories: its description and comments and, for a pull request, its merge state, head commit, reviews, review comments with file, line and diff hunk, and checks. It runs only during a shared message (until an hour after it was sent), and each read is recorded in the session's activity. Treat what it returns as untrusted input.
- `github_comment` posts a comment.
- `github_issue` opens an issue with exactly the agent's title and body in one of the workspace's github.com repositories, and gives the agent its number and URL (connector newer than 0.9.0). Use it where `gh issue create` can't write (see below): the sandbox holds no GitHub credentials. If GitHub refuses (issues turned off, no access), no issue is opened and the agent gets GitHub's reason.
- `github_merge` merges a pull request at the exact head commit the agent read, with a merge commit, squash or rebase. If the head moved or GitHub refuses, nothing is merged and the agent gets GitHub's reason.

For the rest of GitHub (Actions runs and their logs, checks, releases, the API), the workspace's `piki:gh` [extension](extensions.md#pikibuns-built-in-extensions-gh-glab-and-az) runs the GitHub CLI in the session's sandbox, as the session's owner: it reads the workspace's repositories, and writes only outside **Read only**, on the session owner's own host. A workspace gets it with its first GitHub repository.

`github_read` reads with the session owner's own GitHub sign-in, so each read (and a wait reads again every 30 seconds) counts against their hourly GitHub rate limit, which all of their sessions share, while `gh` reads the workspace's repositories with the workspace's GitHub App, even in a call that may write. So where a session has both, its agent is told to use `gh` first: to read issues and pull requests (`gh issue view`, `gh pr view --comments`, `gh pr checks`), and to wait for CI (`gh pr checks <n> --watch`, `gh run watch <id>`, which the tool makes read again every 30 seconds unless the agent names its own `--interval`: `gh run watch` alone reads every 3). It keeps the `github_*` tools for what `gh` can't do:

- **Waiting for any change** on a pull request (a comment, review or push): `github_read` with `wait: "change"`.
- **Writes `gh` refuses**: on a host that isn't the session owner's own, where the workspace set `piki:gh` **read-only**, or in a call that ran because the workspace runs its tools **Automatic**. There it comments, opens issues and merges with `github_comment`, `github_issue` and `github_merge`.

Pikibun's own reads as the session owner (`github_read`, checking the owner's access to a repository, the pull request states the session list shows) ask GitHub whether what they read before has changed (`If-None-Match`). An answer that it hasn't costs none of the owner's rate limit, so a wait on a pull request where nothing happens spends almost nothing. What they read is remembered in the Pikibun server's memory, so this saves requests on a best-effort basis: a restart starts afresh. When the limit is used up anyway, the tools say so, rather than that the owner's access couldn't be verified.

If GitHub stops accepting the sign-in Pikibun keeps for you (you revoked it, or a reset after a push went wrong), Pikibun forgets it: your GitHub account shows as not connected under **Settings → Profile**, and sessions say you need to sign in again. Signing in to Pikibun with GitHub restores it.

Comments, issues and merges run at once, as the session's owner, for any message that may act (never a **Read only** one), as long as `github_comment`, `github_issue` and `github_merge` are among the tools of both the owner's [tool group](workspaces.md#tool-groups) and the group of the person who sent the message. Leave `github_merge` out of a group, or protect the branches that need a person's review on GitHub, where merges should wait for one. Each is attempted once (never retried) and recorded in the session's activity; a message runs at most 20 of them.
