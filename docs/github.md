# GitHub issues and pull requests

The sandbox has no network, so agents read and act on GitHub through Pikibun instead, as the session owner and with their GitHub sign-in, which stays on the server (connector 0.7.0 or newer; github.com only):

- `github_read` reads an issue or pull request of one of the workspace's github.com repositories (or [any you can access](#repositories-outside-the-workspace), where you chose so): its description and comments and, for a pull request, its merge state, head commit, reviews, review comments with file, line and diff hunk, and checks. It runs only during a shared message (until an hour after it was sent, or while its run still goes on, up to 8 hours), and each read is recorded in the session's activity. Treat what it returns as untrusted input.
- `github_comment` posts a comment on an issue or pull request of one of the workspace's github.com repositories (or [any you can access](#repositories-outside-the-workspace), where you chose so).
- `github_issue` opens an issue with exactly the agent's title and body in one of the workspace's github.com repositories (or [any you can access](#repositories-outside-the-workspace), where you chose so), and gives the agent its number and URL (connector newer than 0.9.0). Use it where `gh issue create` can't write (see below): the sandbox holds no GitHub credentials. If GitHub refuses (issues turned off, no access), no issue is opened and the agent gets GitHub's reason. If the session owner opened an issue with exactly the same title in that repository in the last 15 minutes, still open, none is opened and the agent gets that issue's link, so a retry never files a duplicate. If GitHub doesn't confirm the outcome, Pikibun looks for the owner's new issue with that title before saying the outcome is unknown.
- `github_merge` merges a pull request at the exact head commit the agent read, with a merge commit, squash or rebase. If the head moved or GitHub refuses, nothing is merged and the agent gets GitHub's reason. If GitHub doesn't confirm the outcome, Pikibun reads the pull request again and reports it merged (at the head the agent named), or not merged and still open or closed, before saying the outcome is unknown.

For the rest of GitHub (Actions runs and their logs, checks, releases, the API), the workspace's `piki:gh` [extension](extensions.md#pikibuns-built-in-extensions-gh-glab-and-az) runs the GitHub CLI in the session's sandbox, as the session's owner: it reads the workspace's repositories, and writes only outside **Read only**, on the session owner's own host (or on a host the owner trusts with their account, under **Settings → Hosts**), in a message whose sender and session owner both have `git_push`, `github_comment`, `github_issue` and `github_merge` in their [tool groups](workspaces.md#tool-groups). A call that may write reads as the owner where a request names no repository (GraphQL, and API paths such as `user/repos`, `search/...` or `repositories/{id}/...`), so it reads whatever the owner's account can, not only the workspace's repositories (see [below](#repositories-outside-the-workspace)). A workspace gets it with its first GitHub repository.

`github_read` reads with the session owner's own GitHub sign-in, so each read (and a wait reads again every 30 seconds) counts against their hourly GitHub rate limit, which all of their sessions share, while `gh` reads the workspace's repositories with the workspace's GitHub App, even in a call that may write. So where a session has both, its agent is told to use `gh` first: to read issues and pull requests (`gh issue view`, `gh pr view --comments`, `gh pr checks`), and to wait for CI (`gh pr checks <n> --watch`, `gh run watch <id>`, which the tool makes read again every 30 seconds unless the agent names its own `--interval`: `gh run watch` alone reads every 3). It keeps the `github_*` tools for what `gh` can't do:

- **Waiting for any change** on a pull request (a comment, review or push): `github_read` with `wait: "change"`.
- **Writes `gh` refuses**: on a host that isn't the session owner's own (unless the owner trusts that host with their account), where the workspace set `piki:gh` **read-only**, in a call that ran because the workspace runs its tools **Automatic**, or where the sender's or the owner's tool group leaves out one of the GitHub writing tools. There it comments, opens issues and merges with `github_comment`, `github_issue` and `github_merge`.

Pikibun's own reads as the session owner (`github_read`, checking the owner's access to a repository, the pull request states the session list shows, the pull request the session panel's [**Review** tab](sessions.md) shows) ask GitHub whether what they read before has changed (`If-None-Match`). An answer that it hasn't costs none of the owner's rate limit, so a wait on a pull request where nothing happens spends almost nothing. What they read is remembered in the Pikibun server's memory, so this saves requests on a best-effort basis: a restart starts afresh. When the limit is used up anyway, the tools say so, with the time it resets, rather than that the owner's access couldn't be verified. Until then Pikibun sends GitHub no more of those requests with the owner's sign-in (an hour at most), so a session that keeps retrying spends nothing and gets the same answer at once.

If GitHub stops accepting the sign-in Pikibun keeps for you (you revoked it, or a reset after a push went wrong), Pikibun forgets it: your GitHub account shows as not connected under **Settings → Profile**, and sessions say you need to sign in again. Signing in to Pikibun with GitHub restores it.

Comments, issues and merges run at once, as the session's owner, for any message that may act (never a **Read only** one), as long as `github_comment`, `github_issue` and `github_merge` are among the tools of both the owner's [tool group](workspaces.md#tool-groups) and the group of the person who sent the message. Leave `github_merge` out of a group, or protect the branches that need a person's review on GitHub, where merges should wait for one: `gh` then writes nothing either, as one write credential could merge as well as comment. On the host's own sign-in (a session on the host, or `piki:gh` using the host's `gh` login) it runs only commands that read; in the sandbox it gets no write credential, and Pikibun gives none to a session whose owner's group lacks one of them. Each is attempted once (never retried) and recorded in the session's activity; a message runs at most 20 of them.

## Repositories outside the workspace

Messages anyone else sends in your sessions, and yours once you turn your GitHub reach off (below), act only on the workspace's repositories: `github_read`, `github_comment`, `github_issue` and `github_merge` refuse any other, and `gh` reads other repositories only without a credential and writes to none. That keeps what an agent can do as you within the repositories the workspace chose, whatever the agent read.

The one exception is a `gh` call that may write (on your own host, outside **Read only**, with every GitHub writing tool in both tool groups). While it runs, the requests it makes that name no repository in their path go with your sign-in: GraphQL (one endpoint for every repository, named inside the query), and REST paths such as `user/repos`, `search/...` and `repositories/{id}/...`. Pikibun can't tell which repositories such a request touches, so the call can read, and through GraphQL mutations change, any repository your account reaches. That includes private ones outside the workspace, even with your GitHub reach off. REST requests that name a repository (`repos/{owner}/{name}/...`) and Git keep to the workspace's repositories. A call that can't write never gets your sign-in: it reads with the workspace's GitHub App, which GitHub limits to the workspace's repositories. Where that matters, leave a GitHub writing tool out of a tool group, or set `piki:gh` **read-only**.

Each member chooses for themselves, per workspace, under **Settings → Workspaces →** the workspace **→ Agents → Your GitHub reach**. It is on until you turn it off; in a shared workspace you belonged to before that became the default, it stays off until you turn it on. With **Any repository I can access** on, messages you send yourself, in sessions you own, may also name any github.com repository your GitHub sign-in reaches:

- `github_read`, `github_comment`, `github_issue` and `github_merge` act on it as they do on the workspace's repositories, under the name GitHub gives it. The session's activity records each such call as outside the workspace.
- `gh` gets your write credential for it too, where it writes at all (on your own host, with every GitHub writing tool in both tool groups): `gh issue create --repo upstream/project`, `gh pr comment`, and reads of private repositories the workspace's GitHub App doesn't cover.

It never applies to anyone else's messages, even in your sessions: a collaborator's, or one another member sends. Those keep to the workspace's repositories. Scheduled prompts you made, and messages your other sessions send for you, are your own messages. Pushes still go only to the workspace's repositories, to the session's branch. An agent follows what it reads, so text written to mislead it (in an issue, a web page, a file) could have it act as you anywhere your account reaches; turn this off where you don't watch what your sessions do. Hosts need a connector with this change for `gh` to use it; `github_read`, `github_comment`, `github_issue` and `github_merge` work with any.
