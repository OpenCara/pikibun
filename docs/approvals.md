# Approvals and permission requests

## Approvals

Commands, pushes, GitHub comments, merges and issues, and host commands each need an approval: a card above the transcript (and under **Approvals**) that shows the exact operation, such as the command, or the repository, branch and commit of a push. **Approve** runs exactly that operation, as the session owner (a host command as the host's OS user); **Deny** drops it.

| Operation | Who can decide |
|---|---|
| Commands, commits, pushes, GitHub comments, merges | Anyone with approve permission on the session (the owner always has it) |
| Commands without [resource limits](hosts.md#the-sandbox) in a session on someone else's host | The host's owner, or a member they [granted host commands](hosts.md#host-admins-and-host-command-grants), either with approve permission on the session |
| Host commands | The host's owner, in any session on their host they can see (connector newer than 0.9.0; with an older one they also need approve permission on the session), or a member they [granted host commands](hosts.md#host-admins-and-host-command-grants) who has approve permission on the session |

The agent's tool call waits for the decision, and its message waits with it (connector 0.9.0 or newer). **Approve** runs the operation at once: its output appears on the card and goes back to the agent, which carries on. Commands, pushes and host commands run in the background (connector newer than 0.9.0 for commands), so the card shows them running until they end. After **Deny**, the agent learns the operation was denied. The card can be decided until an hour after its message was sent; a card whose call stops first (the message is stopped, the session restarts, or the hour passes) is marked interrupted and can no longer run. An operation you request yourself, outside a message, can be approved once the session's queue is idle. Approving also checks that whoever requested it still has write permission. You can request an operation yourself under **Details → Operation request** (**Bash command** or **GitHub comment**), with write permission; it needs approval like the agent's.

## Always approving another member

Approved operations run as the session's owner, so by default only the owner's own **Auto-approve** messages run without asking. A workspace's owner or an admin can let session owners there go further: **Settings → Workspaces →** the workspace **→ Approvals → Auto-approve other members' requests** (`PUT /api/workspaces/:id/approvals` with `{"requesterAutoApprove": true}`; off by default).

With it on, the session owner's card for another member's command, push, or GitHub comment or issue also offers **Always approve** *name*. It approves that card and, from then on, that member's messages in that session run those operations without asking, as the owner, recorded as automatic under the member's name. Their merges, host commands, commands of a session running on its host, commands without the host's [resource limits](hosts.md#the-sandbox), and anything the session doesn't allow yet (a [permission request](#permission-requests)) still ask. Only the owner chooses it, member by member and session by session; the workspace setting alone auto-approves nobody. The session's **Details → People** (in the mobile app, its **Approvals**) lists who is always approved, and the owner's **Stop** ends it (`DELETE /api/sessions/:id/auto-approved-requesters/:userId`). Turning the workspace setting off makes every such member ask again everywhere; the owners' choices are kept and apply again if it's turned back on. Each choice and stop is recorded in the session's activity, and each change of the setting in the workspace's. The host re-checks with Pikibun before each such operation, so a stop, or a member losing write access, takes effect at the next one. This needs a connector advertising `requesterAutoApprove`; older ones keep asking.

## Permission requests

When a tool call needs more than the session allows (a tool its agent doesn't include, a change in a **Read only** message, a shell command on a host without resource limits, or passing content between this session and another one [whose readers differ](sessions.md#working-across-sessions)), the agent asks instead of failing, and the session owner gets a card with **Allow once**, **Allow for this session** and **Deny**. Only the session owner decides these, and only a host's owner, or a member they granted host commands there, can let commands run without resource limits, in their own sessions.

The call can wait for the answer until an hour after its message was sent, and the session's queue waits with it. **Allow once** lets that call use the tool, but what it does still needs its own approval; the permission then shows on that operation's card instead of a card of its own. **Allow for this session** also approves what the tool does in the session owner's later messages, as **Auto-approve** would: its commands and pushes run without asking, while GitHub comments, merges and issues still wait for a decision (they run automatically only under **Auto-approve** itself), and other people's messages still ask for approval. Host commands (`host_bash`) can only be allowed once, so each one asks again. Messages the session owner sends with **Auto-approve** raise no permission requests. A session restored from a backup asks again.
