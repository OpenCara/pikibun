# Host commands

Host commands need connector 0.8.0 or newer. When a task needs an SDK installed on the host or network access, ask the agent to use `host_bash`, for example for `dotnet --info`; ordinary `bash` stays in the sandbox, with only the workspace's [network access](hosts.md#network-access). Each exact command and timeout (five minutes by default, `timeout_seconds` up to 3600) needs the approval of the **host owner**, or of a member they [granted host commands](hosts.md#host-admins-and-host-command-grants) who also has approve permission on the session. The command runs as the host's OS user, so the host owner decides it in any session on their host they can see, without a session role (connector newer than 0.9.0; an older one also asks them for approve permission on the session). The session owner's **Auto-approve** skips this only on their own host, or where they hold an automatic host command grant.

Host commands run **outside the sandbox, as the connector's OS user**, in the session's worktree: they can read and change host files and credentials, use the network, and run without CPU, memory, process or disk limits. The agent can change the worktree's files and Git configuration, so builds, package scripts and Git hooks there can run its code on the host, even for a command as harmless-looking as `git status`. Approve a host command only if you would run it yourself in that directory. Commands get the host's `PATH` and `HOME`, not the connector's whole environment, and Bash starts without shell profiles.
